### [CONFIRMED] core/input/ws_handler.py:333（来源：b2）

**✅ 批次 8b 已修复（2026-08-07，`8cb42cf` D1）：** 断连按归属取消——`current_generation_user_message_id` + 每连接已发消息集合，仅发起连接断开才取消。

- **问题：** v2 连接断开时无条件取消当前在途 generation，会误杀其他连接的生成
- **失败场景：** Tab A(v2) 发起一个慢生成，agent 处于 THINKING/SPEAKING；Tab B(v2) 此时关闭连接 → handle_ws finally 块（333-340）post InterruptData(source='disconnect')，agent._handle_interrupt（agent.py:495）→ cancel_current 取消的是『当前』认知任务——即 Tab A 的生成，Tab A 收到 generation.failed{GENERATION_CANCELLED} 且 registry 被标 interrupted。断开连接的客户端与 generation 无归属关联，导致一个用户多标签/多设备场景下 A 的回复被 B 的关闭打断。
- **验证依据：** The defect is real and reachable. Chain verified in code:  1. Multiple simultaneous WS connections share one Agent: server.py:318 passes the same singleton `agent` to every /ws handler; handle_ws adds a per-connection channel (ws_handler.py:130-132) to a list-based OutputManager._channels (manager.py:31). Multi-tab/multi-device/multi-session is an explicit feature (batch 3).  2. ws_handler.py:333-340 (the cited finally block) posts InterruptData(source="disconnect") for ANY v2 connection close whenever `not agent.status.is_completely_idle`. is_completely_idle (fsm.py:39-40) is the GLOBAL FSM state of the single shared Agent — so if Tab A's generation holds the agent in THINKING/SPEAKING, Tab B's disconnect passes the guard.  3. No ownership check exists anywhere in the interrupt path: InterruptData carries only `source` (event.py:13-15); agent.py:495 calls cancel_current(source=data.source); loop.py:313-334 cancels the single global self._current_task regardless of which connection initiated it. The cognitive loop tracks no connection/client (grep over loop.py found none).  4. Consequence matches the finding: the cancelled generation's cleanup (loop.py:1424-1438) calls turn_cancelled (manager.py:518-533), which broadcasts on_generation_failed{GENERATION_CANCELLED} to v2 channels and marks the generation registry "interrupted" when source=="disconnect".  The reconnect-cancel semantics (comment ws_handler.py:331-332) implicitly assume the disconnecting client is the source of the in-flight generation; that assumption is violated in the supported multi-client scenario, so Tab B's close kills Tab A's reply.

### [CONFIRMED] core/input/ws_handler.py:603（来源：b2）

**✅ 批次 8b 已修复（2026-08-07，`4e59ed4` §3.7）：** 纯文本/附件统一先 process 后判定 ACK，队列满/抛异常 → 删幂等 entry + rejected（QUEUE_FULL/INTERNAL）。

- **问题：** 纯文本 v2 路径忽略 process_message 返回的 False（队列满），仍发 accepted ACK
- **失败场景：** agent 忙时排队且队列已满（max_pending_messages=32，config.yaml:9）→ process_message 返回 False 消息被丢弃（agent.py:343-345），但 _route_v2_text 已先发 user_message.ack{status:'accepted'} 且幂等 entry 已 store（574-576）；此后客户端按场景 B 用同一 clientRequestId 重试 → lookup 命中 → 重发原 accepted ACK 但不生成，客户端永远等不到回复也无任何错误。对比 has_media 路径（594-601）明确处理了 QUEUE_FULL：store.delete + rejected ACK。
- **验证依据：** The defect is real and reachable. In `_route_v2_text` (core/input/ws_handler.py:603-606), the plain-text path stores the idempotency entry (lines 574-576), sends an `accepted` ACK (603-604), then calls `await agent.process_message(...)` at line 605 WITHOUT checking its return value. `agent.process_message` (core/agent/agent.py:340-345) returns `False` when the agent is not accepting input and the pending queue has reached `max_pending_messages` (default 32, config.yaml:9), logging "消息队列已满 — 丢弃消息" and dropping the message with no other side effect. The same function's `has_media` branch (ws_handler.py:578-601) explicitly handles this case for attachment/sticker messages: it checks `accepted`, and on `False` calls `store.delete(client_request_id)` and sends a `rejected` ACK with `QUEUE_FULL`/`retryable: True` — proving the queue-full state is an anticipated, real runtime condition, and demonstrating the plain-text path is an oversight. The client-facing consequence is directly provable: the client receives `accepted` for a message that was silently dropped; no error is ever sent. If the client retries with the same clientRequestId (the spec's idempotent-retry scenario), the process-local store (TTL 3600s, idempotency.py:36) still holds the entry and lines 556-561 resend the original `accepted` ACK without regenerating, so the message is permanently lost and the client waits forever. The core defect — accepted ACK for a dropped message with no error path — holds regardless of client retry behavior.

It is true that mongodb.py:92 `if limit:` skips `cursor.limit(0)`, leaving the server cursor unbounded — but the very next line is `docs = await cursor.to_list(length=limit)` = `to_list(length=0)` (mongodb.py:94), and motor's `_to_list` computes `n = min(length - len(the_list), result) = min(0, result) = 0`, then `reached_length = (len(the_list) >= length) = (0 >= 0) = True` → `future.set_result([])`. So `to_list(length=0)` deterministically returns an empty list regardless of cursor state — the "整个会话历史被当上下文窗口返回" outcome is impossible. The claimed real/fake divergence is also false: the fake backend slices `docs[skip:skip+limit]` = `docs[0:0]` = `[]` (_fake_documentdb.py:116), identical to real motor's `[]`. `before=0` returning an empty pre/post window is well-defined and exactly the requested "take 0 messages" semantics, not undefined behavior. The only genuine issue at this site is that negative values (`before=-5`) reach `to_list(length=-5)`, which raises `ValueError("length must be non-negative")` → unhandled 500; but the finding's failure scenario is specifically `before=0`, which does not trigger that path, and its predicted outcome ("整段历史或空") does not match the negative path either (a 500, not a history window). The finding as stated is refuted; the real negative-value→500 bug is a different, more mundane defect than described.

- **Module/llm/openai_compat.py:296**（x-security）：The same SSRF-guarded httpx client/transport is shared between _client and _beta_client, so a legitimately configured cross-origin beta_url is misclassified as a cross-origin redirect and has its Authorization header stripped.
  - 推翻理由：The mechanism the finding describes is structurally real, but the specific failure scenario it claims is unreachable in the current codebase — no supported configuration can produce it.  The mechanism: `_create_clients` (Module/llm/openai_compat.py:296-300) passes the SAME `self._injected_client` as `http_client` to both AsyncOpenAI constructors, so `_client` and `_beta_client` share one httpx.AsyncClient with one `_SSRFTransport`. That transport's `_origin` is sticky-first-request (core/input/ssrf.py:150-152, never reset), and any subsequent request to a different origin gets Authorization stripped (ssrf.py:156). Test `test_injected_http_client_used_by_clients` (Module/llm/tests/test_llm.py:694-695) confirms both wrappers share the same underlying client. So IF a single guarded client were given to a backend with a cross-origin beta_url, the second client's requests would lose their Authorization header. This part of the claim is true.  But the triggering configuration is impossible. The finding's scenario requires a provider that simultaneously (a) receives the SSRF-guarded client, (b) has a beta_url, and (c) has supports_prefix=true. No such provider exists:  1. Only the `custom` provider ever receives the guarded client. The guarded `http_client_factory` is injected only for `custom`+backend in both production paths — `_resolve_switch_params` in core/agent/server.py:59-63 (factory only when `params.get("base_url")` is non-empty, and resolve_model_params returns `{}` for non-custom) and /api/providers/test in core/input/api_routes.py:409 (gated on `provider == "custom"`). Startup (`LLMAdapter.__init__` → `LLMFactory.create`, core/adapter/llm_adapter.py:54) injects nothing at all. But `custom` is hardcoded `supports_prefix: false` (Module/config/providers.yaml:48) and has NO beta_url mechanism: custom_providers.yaml entries carry no beta_url field, `resolve_model_params` returns only base_url/api_key/runtime (core/input/custom_providers.py:159-171), LLMConfig has no beta_url field (Module/llm/config.py), and `_BACKENDS["custom"]` has no `beta_url`/`beta_url_key` (providers.yaml:44-50). So for custom, `_beta_url` always resolves to "" → `_beta_client` is never created (openai_compat.py:299) → only ONE client exists → no cross-origin sharing. I verified this empirically: `custom supports_prefix: False`, `beta_url_key: None`.  2. The only provider that can have a beta_url AND supports_prefix=true is `deepseek` (providers.yaml:12, `beta_url_key: DEEPSEEK_BETA_URL`) — this is genuinely a legitimate cross-origin config (e.g. DEEPSEEK_URL=a.example.com, DEEPSEEK_BETA_URL=b.example.com). But `deepseek` NEVER receives the guarded client: `resolve_model_params` short-circuits to `{}` for non-custom model ids (core/input/custom_providers.py:154-155), so `_resolve_switch_params` yields `http_client_factory = None` (server.py:59-63) and api_routes.py:409 skips the factory. With `_injected_client` None, `_create_clients` does not pass `http_client` (openai_compat.py:296), so each AsyncOpenAI self-builds a separate plain httpx client with its own transport — no `_SSRFTransport`, no `_origin`, no header stripping. Prefix continuation to the cross-origin beta_url works normally. I verified empirically: `resolve_model_params('llm','deepseek/deepseek-v4-flash')` → `{}`.  So the premise ("legitimately configured cross-origin beta_url") exists only for deepseek, which is never guarded, and the guard exists only for custom, which can never have a beta_url or prefix support. The two halves of the failure scenario cannot coincide. The direct-construction path that would trigger it is exercised only in tests with a plain (non-guarded) httpx.AsyncClient and same-origin URLs. The described 401-on-prefix-continuation defect therefore has no reachable trigger; the finding overstates the hazard as a current defect rather than a latent design constraint.
