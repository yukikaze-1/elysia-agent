## 总体评价

**评分：B+ → A-（有提升空间）**

这是一个设计良好的项目。三层架构（L0 Module / L1 Core / L2 Memory）清晰，Protocol-Registry-Backend 模式统一，708 个测试通过，文档齐全。开发者在 10 天内完成了从底层基础设施到前端 UI 的完整闭环，工程质量在同规模个人项目中属于上乘。

但高速迭代也留下了技术债务：部分模块耦合过紧、错误处理不一致、安全风险、以及一些"预留但未实现"的半成品代码。

## 一、架构设计评估

### 1.1 做得好的地方

| 方面 | 评价 |
|------|------|
| **三层分离** | L0（基础设施）/ L1（认知控制）/ L2（记忆持久化）分层清晰，职责明确 |
| **Protocol-Registry-Backend** | Module/ 下的每个服务都遵循统一模式，替换后端只需改 registry |
| **事件总线 + 状态机** | EventBus（优先级队列）+ AgentFSM（5 状态）是认知管线的优秀抽象 |
| **ReAct 循环** | CognitiveLoop 正确实现了 Think → Act → Observe 循环，最多 3 轮工具调用 |
| **流式 TTS 管线** | 逐句拆分 → 后台合成 → 绑定发送，经过多轮迭代后设计成熟 |
| **优雅降级** | MongoDB/Milvus 不可用时自动回退到内存模式 |
| **记忆系统** | SessionMemory + LongTermMemory + MemoryConsolidator 三级记忆架构合理 |
| **测试覆盖** | 708 个测试，覆盖核心路径、边界条件、并发场景 |
| **文档** | docs/architecture.md（~900 行）、README.md、CLAUDE.md、sync-lessons.md 都很详尽 |

### 1.2 架构问题

#### 问题 1：组件耦合过紧（中）

`agent.py` 大量使用私有属性访问：
```python
self._cognitive._current_task   # 应通过方法访问
self._scheduler._tool_ctx       # 直接赋值绕过封装
self._cognitive._ctx = ...      # 同上
```

**建议**：给 CognitiveLoop 和 TaskScheduler 增加公开方法（如 `cancel_current()`、`set_tool_context()`），而不是直接戳私有属性。

#### 问题 2：无依赖注入（低）

所有组件在 `Agent.__init__` 中硬编码创建。测试时只能通过属性注入替换（`agent._llm._backend = FakeLLMBackend()`）。

**建议**：如果未来需要多 Agent 实例或更灵活的测试，考虑引入简单的 DI 容器或工厂模式。当前规模下不是紧急问题。

#### 问题 3：FSM 是"观察型"而非"控制型"（中）

FSM 只验证状态转换是否合法，但不强制执行"每个状态下应该做什么"。实际的状态机逻辑散落在 `cognitive_loop.py` 和 `agent.py` 中。

**建议**：考虑将状态行为内聚到 FSM 或引入 State 模式，减少跨文件的状态逻辑分散。

#### 问题 4：SPEAKING 状态设计不够精确（低）

FSM 允许 `SPEAKING → THINKING` 和 `SPEAKING → EXECUTING` 的转换，这在语义上有矛盾——"正在说话"时不应该同时"思考"。

**建议**：审查这些转换是否真的需要，或者应该经过 INTERRUPTED 中间状态。

## 二、TaskScheduler 深度分析

### 2.1 设计意图

TaskScheduler 是一个 5-worker 的优先级任务执行池，被 CognitiveLoop 调用来并行执行 AI 规划的工具调用。支持：
- 优先级队列（`asyncio.PriorityQueue`）
- Future 双向绑定（取消传播）
- 重试（指数退避，cap 30s）
- 超时保护（60s）
- 级联取消（父任务取消 → 子任务递归取消）
- Checkpoint 持久化（仅 BACKGROUND 任务）

### 2.2 做得好的地方

- **Future 模式**：`dispatch_tool_calls()` 创建子任务 → `asyncio.gather` 等待 Future → 返回结果，接口清晰
- **取消传播**：`cancel()` 递归取消子任务 + cancel Worker asyncio.Task + cancel Future，三层保护
- **原子写入**：checkpoint 使用 `tmp + os.replace` 保证不写坏文件
- **测试充分**：24 个 scheduler 测试 + 12 个 task model 测试

### 2.3 TaskScheduler 设计问题

#### 问题 5：`dispatch_tool_calls` 阻塞调用者（高）

`dispatch_tool_calls` 内部用 `asyncio.gather` 等待所有子任务完成。如果一个工具调用 hang 住（虽然有 60s 超时），整个 CognitiveLoop 的当前轮次就卡住了。认知任务在等待工具结果期间完全阻塞，无法响应任何中间状态更新（如进度回报）。

#### 问题 6：`depends_on` 和 `run_in_background` 是完全的 dead code（中）

Task 模型定义了 `depends_on: list[str]` 和 `run_in_background: bool`，标注为"预留"。但 `depends_on` 在 Scheduler 中从未被检查，`run_in_background` 在 Worker loop 中从不改变行为。

#### 问题 7：Checkpoint 只保存 BACKGROUND 任务（中）

TOOL_CALL 任务从不持久化。如果 LLM 发起了一个工具调用链（如 web_search → web_fetch），crash 后丢失全部上下文。

#### 问题 8：`_prune_tasks` 并发安全性（低）

`_completed_count` 在多个 Worker 之间共享但无锁保护。modulo 检查和 prune 之间可能有竞态。

#### 问题 9：`can_retry()` 不检查状态（低）

COMPLETED 任务如果 `retry_count < max_retries` 会返回 `True`。这是一个 API 层面的 footgun。
