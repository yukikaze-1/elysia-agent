## 1. Executive Summary

| 问题 | 结论 |
|---|---|
| Failed task still reported as completed? | **修复前：是**（100% 复现，与本批前四批的全部保证同时成立）。**修复后：否** |
| Cancelled task semantics correct? | **修复后：是**——`cancelled` 独立成第三档，既不谎报成功、也不默认降级为 failed |
| Live vs recovery consistent? | **是**——三条投递路径（live 排空 / Mongo 补投 / WAL 硬杀补录）都带终态 kind，措辞逐字一致（`_tail` 相等） |
| Schema changed? | **是，最小**：`TaskResultData` 增一个 `status: str = ""`（+ 一个纯函数与一个三值 StrEnum）。**不触前后端契约** |
| Any reclassification? | **有一处，且是有意的**：`interrupted`（停机/硬杀补记的"未产生结果"）归入用户级 `failed`。它本来就是**会补投给用户的终态记录**，对用户就是"没做成"；不新立第四档（§17 以真实代码为准） |

**缺陷的确切位置**（三层各丢一半，最后一层反转）：

```text
引擎终态 kind ──► terminal_payload()  ✅ 三种终态各有专属措辞
                     │
                     ├─ TaskResultData      ❌ 只有 is_error 一个布尔 → failed 与 cancelled 无法区分
                     ├─ Mongo 落库          ✅ status 一直在写（completed/failed/cancelled/interrupted）
                     ├─ 启动补投            ❌ 明明读得到 status，却从不读回（恢复 truth 在最后一跳丢）
                     ├─ WAL 硬杀补录        ❌ 手上有 event/status，构造 payload 前丢掉
                     └─ _build_wake_up_message ❌❌ 连唯一活着的 is_error 都不看，恒定宣布成功
```

**为什么用户真的会看到**：唤醒消息不是给人看的固定文案，而是**模型上下文**——它是本轮
`process()` 的 user message，LLM 据此生成对用户的自然语言回复（TTS + WS + `message_archive`）。
修复前的消息**自相矛盾**：同一串里既有 `结果摘要: 任务执行失败: 工具崩了`，
又有 `请自然地告知用户任务已完成`，而 LLM 只会照着后半句复述。

## 3. Terminal Semantic Matrix（最终表）

| Internal outcome | error_type / reason | TaskResultData carries | Wake-up meaning | User should perceive | 实测消息（节选） |
|---|---|---|---|---|---|
| `completed` | 无 | `status="completed"`, `is_error=False` | success | success | `…（整理纪要）已执行完毕。结果摘要: …。请自然地告知用户任务已完成，询问是否现在汇报详细结果，还是稍后再说。` |
| `failed` / `planning_failed` | `planning_failed` | `status="failed"`, `is_error=True` | failure | failure | `…（整理纪要）未能完成。失败信息: 任务执行失败: 规划失败: …。请自然地告知用户任务未能完成，并简短说明失败原因；如实转述即可，不要把它说成成功。` |
| `failed` / `execution_failed` | `execution_failed` | `status="failed"`, `is_error=True` | failure | failure | 同上（失败信息取自 `data.error`） |
| `failed` / `timeout` / `internal_error` / … | 任意 | `status="failed"`, `is_error=True` | failure | failure | 同上——**不按 error_type 分支**，全部压进同一档 |
| `cancelled` | `cancelled`（`reason`） | `status="cancelled"`, `is_error=True` | cancelled | cancelled | `…（整理纪要）已被取消，未产出结果。取消信息: 任务已取消: 用户取消。请自然地告知用户该任务已被取消，并简短说明取消原因；如实转述即可，不要把它说成成功。` |
| `interrupted`（停机/硬杀补记） | — | `status="interrupted"`, `is_error=True` | failure | failure（"被中断，未产生结果"） | `…未能完成。失败信息: 任务因服务重启被中断，未产生结果。…` |
| 未标注（reminder 合成事件 / 旧记录） | — | `status=""`，`is_error` 兜底 | 按 `is_error` | 按 `is_error` | reminder：`status=""` + `is_error=False` → success 语义（提醒确实到期了） |
| 未知 status（外力改坏 / 未来新码） | 任意 | 原样 | 按 `is_error` 兜底；`is_error=True` 时**取失败** | — | 绝不翻成成功 |

> 用户级三档与 `TaskUserOutcome`（`completed` / `failed` / `cancelled`）一一对应；
> 内部 taxonomy（`planning_failed` / `execution_failed` / `timeout` / `plan_too_large` / …）
> **只用于日志与归因**，不作为用户级状态判断的依据（§10）。

## 4. Root Cause

**单点**：`core/cognitive/loop.py::_build_wake_up_message` 对**所有**终态输出同一句话——
`已执行完毕 … 请自然地告知用户任务已完成`。它读了 ctx 里的 `original_intent` 与 `result`，
**从不读 `is_error`**。

但它之所以能一直"不带信息地"工作，是因为上游把区分信息丢干净了：

1. **`TaskResultData` 结构上装不下终态 kind**（`core/schema/event.py`）：只有
   `is_error: bool`。`failed` 与 `cancelled` 在这个布尔上**不可区分**——这是本批
   唯一"现有字段确实不足"的证据（§6/§7 的前置条件）。
2. **恢复路径把手上唯一的真相丢了**（`_lifecycle_task_system.py::_redeliver_pending_task_results`）：
   `upsert_pending` 一直在写 `status`，`list_pending` 一直原样返回它，
   而构造 payload 时只挑 5 个键，**唯独不挑 `status`**。
3. **硬杀补录同理**：`cand["event"]` / `status` 就在手里，构造 payload 前丢掉。
4. **live 路径**：`kind` 只赋给局部变量 `status` 传给仓储，不进 payload。

于是"内部 truth = failed、持久化 truth = failed、恢复 truth = failed，用户看到'已完成'"
三者同时成立——**失败语义不是被算错的，是在最后一跳被结构性地丢掉的**。

**为什么没有被测试拦住**：全仓只有 1 条测试碰唤醒文案
（`core/tests/test_phase3.py::TestWakeUpMessage`），它**不传 `is_error`**、只断言
`original_intent` / `result` 两个子串被拼进去了——对终态语义零覆盖。其余终态测试
（durable / closure / interrupt-delivery / shutdown-mailbox）全部止步于
`TaskResultData` 字段或仓储行，**没有一条走完到措辞**。

## 5. New Invariants

1. **U1 — 用户可见 outcome 等于 logical terminal outcome。**
   `completed → success` / `failed → failure` / `cancelled → cancellation`。
   禁止 `failed → "已完成"`、`cancelled → "已完成"`。
2. **U2 — 内部细节可以压缩，但不得反转。**
   `planning_failed` / `execution_failed` / `timeout` / `interrupted` 一律压成"失败"，
   但**永不允许**压成成功。方向不对称：**失败是黏性的**——矛盾输入（`status="completed"`
   ∧ `is_error=True`）取失败。
3. **U3 — live 与 replay 语义一致。**
   同一条终态：实时投递、重启补投、硬杀补录，最终用户可见语义（逐字）相同。
4. **U4 — at-least-once 重投不改变语义。**
   可以重复告知，两次的 high-level outcome 必须一致。
5. **U5 — 单一映射点。** 内部终态 → 用户级语义只经
   `core.schema.event.task_user_outcome`；措辞层不猜字符串、不按 `error_type` 堆 case。
6. **U6 — 向后兼容。** 旧持久化记录 / 旧 WAL 行缺新字段时照常解析，且失败不得退化成成功。

## 6. Changes

### 6.1 `core/schema/event.py`（+45）

- 新增 `TaskUserOutcome(StrEnum)`：`completed` / `failed` / `cancelled`——**用户级**三档。
- 新增 `_INTERNAL_TERMINAL_OUTCOMES`：内部终态 kind → 用户级语义的**唯一映射表**
  （`interrupted` → `failed`）。
- 新增 `task_user_outcome(status, is_error)`：纯函数。未知/空 status → 按 `is_error`
  兜底；`is_error=True` ∧ `status="completed"`（矛盾输入）→ `failed`。
- `TaskResultData` 新增 `status: str = ""`：内部 logical terminal kind。
  **默认空串**是关键——reminder 合成事件与旧持久化记录都照常构造/解析。

### 6.2 `core/agent/_lifecycle_task_system.py`（+13）

四个构造点全部带上终态 kind：

| 构造点 | 值 |
|---|---|
| `drain_mailboxes_once`（live） | `status=kind` |
| `_stop_mailbox` stranded（interrupted） | `status="interrupted"` |
| `_redeliver_pending_task_results`（Mongo 补投） | `status=str(doc.get("status") or "")` ← **恢复路径接回真相** |
| `_replay_task_result_wal`（硬杀补录） | `status=status` |

`terminal_payload`（Batch 1.7 的措辞唯一实现点）**未改**——它已经是对的，本批只是不再
在它之后把信息丢掉。

**附带的相邻加固（Challenger D1 攻出，落在同一段构造点上）**：`_redeliver_pending_task_results`
的逐条构造加 try/except → **跳过坏文档 + warning**。`doc.get(k, default)` 在「键存在但值为
null」时返回 `None` 而不是 default，pydantic 随即抛 `ValidationError`；修复前它冒泡出启动
步骤循环（`lifecycle.start()` 对启动步骤的 BaseException 回滚）→ **一条坏文档让整个 Agent
起不来**，且排在它后面的正常记录一条都补投不出去。坏文档刻意**不**渲染成内容残缺的宣告
（那是对用户编造内容），而是保持 `delivered=False`、每次启动重试并留 warning——不静默、不丢、不阻断。

### 6.3 `core/cognitive/loop.py`（+46/−3）

- 新增模块级 `_WAKE_UP_FRAMING: dict[TaskUserOutcome, tuple[str, str, str]]`：
  **只按用户级 outcome 分支**（3 档），值 = (终态陈述, 细节标签, 对 LLM 的行为指令)。
- `_build_wake_up_message` 改为：`outcome = task_user_outcome(ctx["status"], ctx["is_error"])`
  → 取框架拼装。时间注入、`original_intent` / `result` 插值、成功分支的结尾问句
  **逐字保留**（对既有产品风格与既有测试零破坏）。

### 6.4 `core/schema/__init__.py`（+2）

re-export `TaskUserOutcome` / `task_user_outcome`。

（`_semantic(msg) == FAILED/CANCELLED`），避免"只要不出现某词就算过"的空洞通过。

| 是否需要迁移？ | 不需要（ARCH-INC-P1-04：新增字段由 `ensure_index`/读写两侧的默认值覆盖） |

## 11. Keep As-Is

以下都是本批**看到但在范围内刻意不动**的：

1. **`terminal_payload` 的措辞与 `is_error` 折叠**（Batch 1.7 的唯一实现点）。
   本批只保证"它产出的信息不再在下游被丢"，不改它的文本。
2. **`error_type` 机器码不进 `TaskResultData` / 不进 Mongo**（§16）。
   引擎事件与 WAL 里有，但下游一律拿不到结构化阶段码——本批**刻意不扩协议**：
   `failed remains failed` 只需要终态 kind，不需要内部 taxonomy。
   代价：失败文案里的阶段信息只以自然语言存在（"规划失败: …"）。
3. **失败细节不做脱敏/截断**（§19）。已核查：`data["error"]` 的来源是引擎**编写的
   诊断字符串**（`task_state.fail(reason, code)`、`collect_failure_info` 的
   `f"{node_id}: {ns.error}"`），grep `Module/workflow_engine/` 生产代码中
   `str(exc)` / `f"{e}"` **零命中**——没有 stack trace / provider exception 直灌。
   且这段文本**在修复前就已经**出现在用户可见路径上（旧的"结果摘要: …"），本批未增加暴露面。
4. **唤醒文本参与记忆沉淀 / 性格反思 / mood 关键词判定**。
   `_finalize_turn` 拿到的是**重绑后的** `user_message`（= 唤醒文本），于是它被当作
   "用户消息"进 `MemoryConsolidator` / `CharacterEngine.buffer_message` / `analyze_user`。
   修复后流进去的是**正确的失败事实**（比原来流进去"任务已完成"更正确），
   但"系统注入文本被当成用户发言"这个更大的问题不在本批范围。
5. **reminder 结果无持久化**（Batch 1.7 已登记的 G6）。本批不改：它 `status=""` →
   按 `is_error=False` 走 success 语义，事实正确（提醒确实到期了）。
6. **`_EMPTY_RESPONSE_FALLBACK` 会吞掉宣告**：任务唤醒轮若 LLM 连续空响应，用户收到
   "我刚才走神了，你能再说一遍吗？"，终态永不告知。属空响应守卫的既有行为，本批不动。
7. **`terminal_payload` 的 None 默认值陷阱**（D4，见 §10.4）——不可达、方向不反转，登记为 F16。
8. **可选节点失败仍算任务完成**（R1，见 §10.4）——引擎的终态定义问题，U1 不因此破。
9. **debug 面板本来就是对的**：`/debug/api/tasks/stream` 一直带 `status` / `error` /
   `error_code`。本批修的是**聊天侧**用户可见语义，两者不共用代码。
