## 1. 结论

`bbe3cb22` 已通过第二轮 Windows Electron 真实联调中的主要产品路径：generation/tail busy、UserIdentity Mongo 持久化与 Prompt 投影、角色校验与 preview、Mongo 离线恢复、默认角色归档回退，以及不同角色 Engine/Prompt 隔离。

当前剩余阻塞集中在**后端联调基础设施与验收口径**，不是新的公开产品契约缺失：

1. `scripts/dev/seed_stage_h_pinned.py` 写入 `createdBy="fixture"`，而公开 `CharacterCreatedBy` 只允许 `system | user | migration`；seed 后 `GET /api/characters` 会因响应模型校验失败返回 `INTERNAL_ERROR`。
2. 同一脚本的 `--cleanup` 只删除固定 revision 1。H-44 按设计把 Definition 推进到 revision 2 后，cleanup 会遗留 revision 2 孤儿记录。
3. 现有公共会话激活接口在 generation tail lease 释放前返回 retryable `AGENT_BUSY`，因此无法自然形成“tail 仍运行但已激活 B”的窗口。应冻结为强串行验收，或提供显式 opt-in 的内部测试 gate，不能靠随机延时碰撞。

修复不得扩大 `character-contract-v1` 的枚举、削弱 tail lease，或引入产品环境可调用的调试入口。

## 3. 后端必须完成的改动

### BE-H2-01：修复 pinned fixture 的 `createdBy`（P0）

**现状与根因：**

`scripts/dev/seed_stage_h_pinned.py::_fixture_revision()` 调用：

```python
CharacterService._revision_from_draft(
    FIXTURE_CHARACTER_ID,
    draft,
    revision=FIXTURE_REVISION,
    created_by="fixture",
)
```

领域 `CharacterRevision.createdBy` 当前是宽松 `str`，因此写库成功；公开 REST 在构造 `CharacterRevisionContent`/summary 时使用 `CharacterCreatedBy`，只接受 `system | user | migration`，导致整页角色目录序列化失败。现有脚本单测只验证 repository 写入，没有经过公开响应模型，因而漏检。

**实施要求：**

1. fixture revision 使用已有合法来源，推荐 `created_by="migration"`；它准确表达“由受控脚本注入”，且无需污染公开枚举。
2. 不得把公开 `CharacterCreatedBy` 扩为 `fixture`。联调夹具不是产品领域来源，前端也不应为了夹具增加分支。
3. 如希望从类型层提前拦截，可把内部 revision builder 的 `created_by` 参数收窄到与公开枚举同源的类型；但不得造成合同双源。
4. seed 完成后必须验证生成的 revision 能通过当前公开 `CharacterRevisionContent`/`CharacterSummary` 构造路径。
5. 对已有坏 fixture 不做产品数据迁移；开发阶段运行修复后的 `--cleanup` 后重新 seed。

**最小测试：**

- `_fixture_revision()` 的 `createdBy == "migration"`；
- `_fixture_revision()` 可通过公开 REST response model 校验；
- seed 后 CharacterService list/detail summary 不抛 ValidationError；
- 真实运行后 `GET /api/characters?status=active` 返回 200 且包含 `chr_stage_h_fixture`。

### BE-H2-02：cleanup 删除该 fixture 的全部 revisions（P0）

**现状与根因：**

`cleanup_fixture()` 只执行：

```python
await revisions.delete_revision(FIXTURE_CHARACTER_ID, FIXTURE_REVISION)
removed["revisions"] = 1
```

但 H-44 的必要步骤就是把同一 Definition 从 revision 1 推进到 2，所以正常验收结束后一定可能存在 revision 2。当前 cleanup 删除 definition 后留下不可从目录访问的孤儿 revision，且返回的 `removed.revisions=1` 不是实际删除数量。

**实施要求：**

1. 清理顺序保持：两个 fixture session → 两个 fixture instance → 该 characterId 的全部 revisions → fixture definition。
2. 使用 `list_revisions()` 分页/循环取得该固定 characterId 的所有 revision，再逐条调用正式 repository 的 `delete_revision()`；不得扫描或删除其他角色。
3. 必须处理超过单页的情况，不能假设只有 revision 1/2。
4. `removed.revisions` 返回实际发现并删除的条数；零条是合法幂等结果。
5. 任一步存储失败时命令非零退出，不得打印看似成功的汇总。
6. cleanup 完成后再读取 definition、revisions、instances 和 sessions，确认全部为空；发现残留则非零退出。
7. 第二次执行 cleanup 仍应成功并返回全零，证明幂等。

**最小测试：**

- 预置 revision 1、2、3，cleanup 后三者均不存在；
- 同库另一 character 的 revision 保持不变；
- cleanup 两次均成功，第二次计数为零；
- sessions/instances 删除失败时不谎报完整成功；
- 实际删除计数与 repository 复查一致。

### BE-H2-04：冻结 A/B tail 验收语义（P1 决策）

**推荐方案：公共 API 强串行，作为正式产品语义。**

当前 `sessions_activate_handler`/WS activate 在 `is_accepting_input=False` 时返回 `AGENT_BUSY`，tail lease 又把 busy 延长到反思/归档完成。该组合阻止 A tail 运行时把全局活动 Engine 切到 B，安全性强于“允许切换但依赖闭包捕获正确 Engine”。

采用推荐方案时：

1. 在设计与验收文档明确 `generation.completed` 只代表可见生成终态，不保证后台 tail 已完成；
2. tail lease 释放前 activate/reset 均可返回 retryable busy；
3. 客户端不得把 completed 当作立即可切换承诺；
4. 后端保留 `test_tail_captures_turn_engine_not_next_turn_engine`，作为纵深防御；
5. 真实验收改为“busy 期间拒绝切换，tail 后切换成功，B Engine/Prompt 不含 A 标记”。

如果产品决定允许 tail 期间切换，则需要另立设计变更：区分 generation busy 与 activation busy，审计所有 `self._engine` 晚绑定访问，并提供只在 `STAGE_H_FIXTURES=1` 下启用的受控 tail gate。该方案扩大并发状态空间，本批次不推荐。

### 9.3 本轮 smoke 暴露的两个真实执行顺序问题（已在本轮判定并纳入验收口径）

这两条都不是某个函数的 bug，而是**验收顺序**问题；单测（内存假后端）与脚本单测都看不见。

**S1 — cleanup 会「复活」：必须在服务停止后执行。**
跑过 fixture 会话的 agent 在 `agent.stop()` 时会把内存里的 session 与 character runtime
状态 flush 回 Mongo。若先 `cleanup_fixture` 再关机，刚删掉的 2 个 session + 2 个 instance
会被关机回写重新创建（实测 `updated_at` 正是关机时刻，`state_version` 已被 reflector 推进）。

- **验收口径：** cleanup 必须在服务停止**之后**执行；或 cleanup 后重启服务再复查。
- **smoke 已按此顺序实现**，并加了 `BE-R4.no_resurrection.*` 断言：冷启动服务从未装载过
  fixture 会话，它的关机会话也不得把行造回来。

**S2 — 在运行中的服务上跑 cleanup，detail 会返回 503 而不是 404。**
`CharacterRepository` 有进程内 LRU 缓存（`core/storage/character_repo.py` `_cache`）。
夹具脚本按真实形态用**自己的** repository 实例（真实用法里是独立进程）写库，服务端进程的
缓存不会随之失效 → 缓存里 definition 还在、revision 已删 → `get()` 抛
`CharacterStorageUnavailableError` → **503**。

- **判定：** 不是产品缺陷——生产只有一个写入方，删除走同一实例自行失效；仅「另一进程
  外部改库」才可见。故**不为夹具加产品分支**，也不做缓存按需回查。
- **验收口径：** 若确实要在服务运行中跑 cleanup，之后必须重启服务（或等 LRU 淘汰）再看
  404。smoke 用**冷启动的第二个服务**做 BE-R3，天然避开该状态。

### 9.5 A/B tail 验收口径（BE-H2-04 冻结）

1. `generation.completed` **只代表可见生成终态**，不保证后台 tail（记忆沉淀 / 反思 / 会话
   归档）已完成；
2. tail lease 释放前，`activate` 与 `reset-evolution` 均可返回 retryable busy
   （`AGENT_BUSY` / `CHARACTER_BUSY`）；
3. 客户端不得把 `completed` 当作「立即可切换」的承诺；retryable 409 是合法状态，不是连接失败；
