## 2. BE-S3-INT-P0-01：搜索端点支持贴图分类

前端阶段 3 已冻结 `HistoryCategory`，并通过：

```http
GET /api/search/messages?category=sticker
```

实现“当前会话/全部会话”的贴图历史分页和来源跳转。当前后端存在两处拒绝：

- `core/input/session_routes.py` 的搜索 category 白名单只有 `text/image/video/audio/file/link/tool`；

因此请求在 handler 层直接得到 400 `CONTRACT_VALIDATION`，前端贴图历史 tab 无法联调。

### 2.2 已拍板的目标行为

后端按前端现有查询模型补齐 `sticker`：

1. `/api/search/messages` category 白名单增加 `sticker`；

3. 保持现有 keyset cursor、`conversationId`、日期与关键词组合查询语义；
4. 保持现有 `SearchMessageItem` 响应形状，不要求本批增加 `kind/url/stickerId`；
5. `snippet` 允许为空，前端本批按文本行 + category chip 展示，并使用 `conversationId/messageId` 跳转来源；
6. 不改变 `/api/stickers` 与 `/api/sessions/{id}/resources?category=sticker` 的现有行为。

### 2.3 必须补充的测试

## 3. BE-S3-INT-P0-02：混合附件批次按每文件 `kind` 对齐前端

### 3.1 当前问题

前端 `RealBackend.uploadAttachments()` 对每个文件依次追加：

```text
kind=<file-1-kind>
files=<file-1>
kind=<file-2-kind>
files=<file-2>
...
```

当前后端只保存一个标量 `kind`。每遇到新的 `kind` 字段就覆盖旧值，随后将最终值用于整个批次：

- 混合批次可能用最后一个文件的上限预检前面的文件；
- `audio/webm` 与 `video/webm` 依赖 kind 提示消歧时，可能被统一归到最后一个 kind；
- 与前端“≤10 个混合附件、一次原子上传”的产品语义不一致。

### 3.2 已拍板的目标行为

前端每文件语义为权威，后端 multipart 解析需支持两种形态：

1. **当前形态（权威）**：每个 `kind` 紧邻并作用于其后的一个 `files`/`files[]` part；重复多组形成逐文件提示；
2. **旧形态（兼容）**：整个请求只有一个 `kind` 时，继续把它作为全部文件的共同提示；
3. `files` 是当前前端发送的字段名；后端继续兼容既有 `files[]`；
4. 解析结果改为逐文件保存，例如 `(filename, bytes, kind_hint)`，尺寸预检与 WebM 消歧只能读取该文件的 hint；
5. 魔数与后端附件记录仍是最终权威，客户端 kind 只是提示，不能绕过 MIME、扩展名或大小复核；
6. 多个 kind 与文件无法按上述规则无歧义配对、出现悬空 kind、非法 kind 时，返回 400 `CONTRACT_VALIDATION`；
7. 继续保持整批原子性：任一文件失败，不留下本批文件、记录或 resolver 映射。

### 3.3 必须补充的测试

- `image + video + file` 混合批次成功且逐项 kind 正确；
- `audio/webm + video/webm` 同批上传时分别归为 audio/video；
- 当前 `files` 与旧 `files[]` 字段均可用；
- 旧“单 kind + 多文件”仍兼容；
- kind 数量/顺序歧义、悬空、未知值均 400；
- 前一个大视频不会因最后一个图片的 10MB 提示被误拒；
- 魔数与提示冲突时仍以服务端记录真值为准；
- 混合批次中途失败仍完整回滚。

## 4. BE-S3-INT-P1-01：日期参数保持后端自然日契约并 fail-fast

日期方向按后端现有契约冻结：

```text
date_from = YYYY-MM-DD（含当天）
date_to   = YYYY-MM-DD（含当天）
timezone  = IANA timezone
```

后端负责把自然日转换为 UTC 半开区间。前端不得预先发送 UTC ISO 时间戳。

除前端修复外，后端 handler 应在进入 repository 前显式验证 `date_from/date_to`：

- 非 `YYYY-MM-DD` 返回 400 `CONTRACT_VALIDATION`；
- 未知 timezone 保持 400 `INVALID_TIMEZONE`；
- 不再把错误日期吞成 200 空结果，以免未来契约漂移被误判为“没有历史”。

测试至少覆盖 UTC、`Asia/Shanghai`、DST 时区边界、仅 from、仅 to、同一天 from/to，以及 ISO datetime 负例。
