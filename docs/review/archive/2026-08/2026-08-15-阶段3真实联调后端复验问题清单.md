## 3. BE-S3-RUN-P0-01：视觉工具必须按每轮目标会话换绑

### 3.1 真实现象

1. 在新建的非默认会话上传并发送有效 PNG；
2. 后端消息归档中存在正确的 `ImagePart` 和附件引用；
3. 文本模型按提示调用了 `describe_image`；
4. 工具侧最终得到图片数 0，无法描述用户刚发送的图片。

因此，上传、附件关联和消息持久化并未丢图；故障发生在工具执行时读取会话的位置。

### 3.2 根因

- `core/agent/_lifecycle_tools.py::_start_tool_context()` 只在 Agent 启动时把当时的 `self.session` 注入 `extra_services["session"]`；
- `core/cognitive/loop.py::process()` 每轮解析实际目标会话后，只更新 `self._session = target`、Prompt 与 `trace_id`，没有同步更新复用中的 `tool_context.services["session"]`；
- `core/tools/vision/plugin.py::DescribeImageTool.execute()` 从 `ctx.get("session")` 读取最近用户消息，所以仍在启动时的旧会话里找图。

关键位置：

- `core/agent/_lifecycle_tools.py:67-76`
- `core/cognitive/loop.py:437-463`
- `core/tools/vision/plugin.py:89-102`

### 3.3 必须修改的行为

1. 每轮完成目标会话解析后、任何模型/工具执行前，将同一个目标 `SessionMemory` 原子地绑定到本轮 `ToolContext`；
2. v2 显式 `conversationId` 指向非活动会话时，工具必须使用显式目标，而不是全局 active/default 会话；
3. 切换会话后不得残留上一轮的 session；失败、取消和下一轮也不能串会话；
4. 与会话共同派生的运行时服务值（至少 `_session_msg_count`）同步按目标会话更新，避免修复一个引用后继续留下不一致快照；
5. 不要在 vision 插件里反查全局 Agent 作为补丁；会话归属应由 cognitive loop 在统一的 per-turn 上下文边界完成。

### 3.4 必须补充的测试

- Agent 启动于 `default`，随后在新建会话发送 PNG：`describe_image` 能取得当前用户消息中的 1 张图；
- 连续在会话 A、B 各发不同图片：B 的工具调用只看到 B，不读到 A；
- v2 显式向非 active 会话发图：工具读取显式目标会话；
- 图片消息与纯文本消息交替，下一轮不残留上一轮图片；
- generation 取消/失败后再发图，session 绑定仍正确；
- 保留纯文本模型调用 `describe_image` 的链路测试；多模态模型直看图片的既有分支不得回归。

### 3.5 完成验收

真实 Electron 在一个新建非默认会话上传 PNG 并提问图片内容；后端日志、工具结果和公开回复均证明工具读取的是本轮图片，且切换到另一会话后不串图。

## 4. BE-S3-RUN-P0-02：音频 `kind` 与 MIME 必须输出同一套规范值

### 4.1 真实现象

| 文件 | 前端逐文件 hint | 上传响应/记录 kind | 上传响应/记录 MIME | 实际结果 |
|---|---|---|---|---|
| WebM 音频 | `audio` | `audio` | `video/webm` | kind 正确，但前端音频白名单不接受视频 MIME，首次发送显示“不支持的文件” |
| WAV | `audio` | `audio` | `audio/x-wav` | 前端冻结值为 `audio/wav`，首次发送显示“不支持的文件” |

复验样本：

- WebM audio：`att_cef8e6775bf14ed8b0439af4f8`
- WebM video：`att_fb222b9074d545d68f490e6cb4`
- WAV：`att_a84070305526490c9d48510fb9`

WebM audio/video 已正确得到不同 `kind` 与不同附件 ID，说明逐文件 hint 和 kind 消歧本身已经通过。问题是消歧后仍把 `filetype` 的容器探测值 `video/webm` 原样写入 audio 记录。

WAV 的探测值则为 `audio/x-wav`。这两个值都不属于 `core/schema/part.py::AudioMime` 的冻结枚举。REST/WS 恢复时，`core/input/ws_v2.py::_attachment_part()` 捕获校验异常后静默不写 MIME，最终退回 `AudioPart` 默认 `audio/wav`。因此同一附件会出现“上传即时值”和“重载恢复值”不一致。

关键位置：

- `core/input/upload_routes.py:238-280`：探测 MIME 直接进入记录和响应；WebM 只改变 `final_kind`
- `core/input/upload_routes.py:414-444`：当前探测 MIME 表
- `core/schema/part.py:54-59,102-106`：Audio MIME 权威枚举
- `core/input/ws_v2.py:197-225`：非法 MIME 被静默丢弃并回退默认值
- `core/input/attachment_routes.py:157-169`：下载 `Content-Type` 直接使用记录 MIME

### 4.2 已冻结的目标口径

`kind` 继续以前端逐文件语义为准，魔数仍负责真实性校验；在最终 `kind` 确定后，将面向 wire/持久化/下载的 MIME 规范化为与 kind 一致的值：

| 最终 kind | 探测/历史别名 | 规范 MIME |
|---|---|---|
| `audio` | `video/webm`（由 `kind=audio` 消歧） | `audio/webm` |
| `audio` | `audio/x-wav` | `audio/wav` |
| `video` | `video/webm` | `video/webm` |

约束：

1. `detected_mime` 可保留为校验过程内部值，但 `AttachmentInfo.mime`、Mongo 附件记录、消息 `AudioPart.mime` 与下载 `Content-Type` 必须使用同一规范值；
2. 规范化不能绕过魔数、扩展名、大小和逐文件 kind 复核；
3. 对既有记录显式兼容：`kind=audio + mime=video/webm` 恢复为 `audio/webm`，`audio/x-wav` 恢复为 `audio/wav`；不能继续依赖“构造失败后静默用默认值”；
4. 未知且无法安全规范化的 MIME 要有可诊断日志/错误，不得悄悄把任意音频伪装成 WAV；
5. 同步更新 `docs/electron-backend-protocol-v2.md` 的音频 MIME 表，避免文档继续冻结 `audio/x-wav`。

### 4.3 必须补充的测试

- `audio/webm + video/webm` 同批上传：响应、记录、消息恢复、下载头分别为 `audio/webm` 与 `video/webm`；
- WAV：响应、记录、消息恢复、下载头均为 `audio/wav`；
- 上传即时消息与重启/REST/WS replay 后的 `kind/mime` 完全一致；
- 既有 `audio/x-wav`、`kind=audio + video/webm` 记录可兼容恢复，且不会把整个消息页炸掉；
- hint 与魔数冲突、未知格式、扩展名不匹配仍按原契约拒绝；
- 混合批次任一项失败继续完整回滚。

### 4.4 完成验收

真实 Electron 分别发送 WAV、WebM audio 和 WebM video；首次发送、切会话、Renderer reload、后端重启恢复后类型均一致，音频不再显示“不支持的文件”。
