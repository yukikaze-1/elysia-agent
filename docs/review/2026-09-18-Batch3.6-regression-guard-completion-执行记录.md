## 2. N-4 Invariant

### 2.1 表的职责（先确认，再守）

`EXPECTED_INDEX_OPTIONS` 的形状是 `{集合: {索引名: {选项: 值}}}`；运行期
`check_schema_drift()` 以 `EXPECTED_INDEX_OPTIONS.get(collection, {})` 取该集合的声明，
`_option_mismatches()` 再以索引名 `expected.get(name)` 取该索引的声明。

⇒ **两级都是运行期查找键**。任一层不存在，对应选项就**一个都不比**，而
`check_schema_drift()` 照常跑完并报健康——即 B3-CB-2 的"扫了、没比、报健康"。
所以 invariant 不是"表非空"，而是**表只许指向真实存在的 schema 实体**，且
**代码声明了选项的索引必须真的被登记**（后者是前者的镜像：整条漏登记的运行期后果
与键写错完全相同）。

**第三级（Challenger 补出来的）**：登记了索引名还不够。`_option_mismatches()` 的第一行是
`want = expected.get(name); if not want: continue` —— **空字典（falsy）与拼错的选项键
都会让它直接跳过**该索引。即"索引名已登记"与"选项真的在被比"之间还隔着一层，
它同样是"扫了、没比、报健康"（下沉一层）。见 §7.2。

### 2.2 canonical authority：生产代码的 AST，不是第二张手写表

判据来源是 `_derive_option_table_from_code()`：解析 `core/storage/*.py` 里真实的
`ensure_index(COLLECTION, [(field, dir)], unique=…/expireAfterSeconds=…)` 调用
（集合名解析同目录模块级字面量常量）。**没有**在测试里手写一份集合/索引清单。

**为什么不会共同漂移**：手写表 A vs 手写表 B 的守卫，在"把集合改名"时两张表会一起
改错、互相印证为绿；AST 判据读的是仓储 `connect()` 真正要建的东西。实测 M4-5：
把 `idempotency_repo.COLLECTION` 改成 `idempotency_v2`（**代码侧**单边改名）→ 守卫红。
若判据是第二张静态表，这种改法永远不会被发现。

```
EXPECTED_INDEX_OPTIONS ──compare──▶ core/storage/*.py 的 ensure_index AST
        (被测表)                          (canonical schema source)
```

### 2.3 判据的五条规则

| 规则 | 挡住的形态 | 变异实测 |
|---|---|---|
| **R1** 集合键必须存在于 AST 声明 | 历史 typo、任意假集合 | M4-1 / M4-2 红 |
| **R2** 索引名必须存在于该集合的 AST 声明 | 索引名错拼（集合对、名字错） | M4-3 红 |
| **R3** 代码声明了选项的索引必须已登记（减去显式记账的已知缺口） | **整条漏登记**、**清空全表**（与键写错运行期等价） | M4-4 / M4-5 红 |
| **R4** 已知缺口登记不得陈旧（补进表后不删条目即红） | 登记表退化成永久豁免单 | `test_unregistered_option_ledger_has_no_stale_entries` |
| **R5** 登记条目的**选项键集**必须与代码声明一致（Challenger F-A1 后补） | 索引名对但选项被清空 `{}` / 键拼错 ⇒ 运行期静默跳过 | M4-7 / M4-8 红 |

**AST 稳定性**：规则只依赖调用形态（集合名、键列表、kwargs），不依赖行号/格式/顺序。
`test_parser_survives_reformatting_and_reordering` 用一段多行、kwarg 在后的代码做定点
验证；M4-6 的改名实验则是端到端证明（Challenger 另用单行化/注释/kwarg 重排复验：34 passed）。

**解析器拒答**：新增的 `ensure_index(非字面量集合, …, unique=…)` 会被收进 `unresolved`
并让守卫**直接失败**（不打印通过标记）——静默跳过等于给守卫开后门（"判据无从成立"型假绿）。
同一策略下 `[("ttl_expires_at", pymongo.ASCENDING)]` 这种**合法但非常量**写法会报红
（拒答方向：宁可误报也不假装判过），列入 §12 的 accepted risk。

### 2.4 刻意**不**守的东西（以及为什么）

- **运行期漂移语义**（构造冲突 → 断言被报出）继续由 `TestIndexOptionConflicts` 承担，
  本批不重复整套 Mongo/index integration（§10）。
- **选项值是否与代码一致**：R5 只比**键集**，不比**值**。值写错会让
  `_option_mismatches` 报出选项冲突（**鸣笛**方向，不是假绿）；且 TTL 按设计只比
  "有没有"、不比秒数，`expireAfterSeconds` 的值本就不该钉死；`character_versions` 的
  唯一性是**运行期动态决定**的（`unique=desired_unique`，重复探测后才降级），静态判不了
  就不该假装判得了——该条目作为 `_DYNAMIC` 参与"实体存在"检查，但不参与覆盖/键集断言。
  （Challenger 用运行时探针确认了这条边界：`{"unique": False}` 走的是**误报**方向，
  与 R5 要堵的静默方向相反。）

## 4. N-8 Invariant

```text
ELYSIA_PATH_DATA_UPLOADS_IMAGES 覆盖（运行期设置，import 之后）
        │
        ▼
  create_app(agent)                      ← 静态挂载也必须在**调用期**解析
        │
        ▼
  POST /api/images  →  image_upload_handler  →  _images_dir()
        │                                              │
        │                                              └─ 每次调用现解析（不缓存）
        ▼
  文件写入 ◀── 必须落在重定向目录 ──┐
                                   └── 真实默认目录 before/after 快照必须相同
```

**为什么旧实现能潜伏**：`_IMAGES_DIR = ProjectPath.DATA_UPLOADS_IMAGES.resolve()` 在
**import 期**求值，而测试的 `monkeypatch.setenv` 发生在运行期 ⇒ 隔离**从未生效**，
测试以为写 tmp、实际写真实 `data/uploads/images/`（累计 441 个 PNG）。改回这种写法，
**当时整套图片测试仍然全绿**——所以本批的守卫必须能抓住"行为"而不是"某行代码"。

**守卫的形态**（`core/input/tests/test_upload_dir_isolation.py`）：

| 用例 | 证明什么 |
|---|---|
| `test_image_upload_writes_redirected_dir_and_leaves_real_dir_untouched` | **走真实上传路径**（env → create_app → POST → 落盘）。正对照：重定向目录**真的**出现 1 个 PNG 且内容一致；负证据：真实默认目录快照不变 |
| `test_images_dir_follows_runtime_env_not_import_time` | 定点诊断（同进程内改两次 env，函数必须跟随）。**单独它不算守卫** |
| `test_fresh_process_import_then_override_still_redirects_upload` | fresh 子进程：**先 import、后设 env**、再真实上传——守的是行为，不依赖当前 pytest 进程的偶然加载状态 |
| `test_guard_precondition_module_imported_at_collection_time` | 守卫前提自检：被测模块必须在任何 fixture 之前加载（否则旧实现会被冻到 tmp 上、守卫退化成假绿） |

**快照语义**：`None`（目录不存在）≠ `[]`（空目录）——旧实现把真实目录**创建出来**也算变化。
**只读纪律**：真实默认目录只做 `iterdir()` 快照，测试全程不创建/删除/清空其中的任何文件
（开发机当前该目录只有 `.gitkeep`，跑完仍只有 `.gitkeep`）。

### 自查发现的一个弱点（本批内已修，`210e9c37`）+ Challenger 对它的**纠正**

第一版守卫把被测模块的首次 import 放在 `_make_images_app()` **内部**——即 env 已被
`monkeypatch` 覆盖**之后**，于是把它改成模块顶部显式 import，并加前提自检用例。

Challenger 复验后指出：**当时的理由被我说重了**。实测在 `6c559816` 那一版里，即便 import
在 fixture 内，端到端用例**照样红**——因为 `core/input/tests/__init__` → `core/input/__init__`
→ `server` 这条包链已在收集期把模块加载了（隐式链）。真正会静默退化的形态是**包链也被
改惰性/精简**：实测把 `from .server import create_app` 从 `core/input/__init__.py` 移除后，
端到端用例 `1 passed` 变绿，而前提自检报红。⇒ 顶部 import 是**冗余保险**（把时序显式化），

### 7.2 F-A1（真漏洞）：只钉索引名、不盯选项 ⇒ 假绿

**攻击**：把 `EXPECTED_INDEX_OPTIONS["attachments"]["attachment_id_1"]` 从
`{"unique": True}` 改成 `{}`（或 `{"unicorn": True}`），跑守卫 → **34 passed / 守卫类 9 passed**。
而运行期探针（mock 库里该索引**不是** unique 的真实漂移）：

```text
# 真表
option_conflicts = {'attachments': ('attachment_id_1',)}
summary          = **选项冲突** 1 个（会导致对应仓储 connect() 失败）
# 条目值清空后
option_conflicts = {}          （attachments 整个消失）
summary          = 索引 schema 无漂移（13 个集合）
```

根因在运行期函数自身：`_option_mismatches` 写的是
`want = expected.get(name); if not want: continue` —— **空字典是 falsy**，拼错的键则让两个
`in want` 判断全部落空。即"索引名已登记"与"选项真的在被比"之间还隔着一层，
与 B3-CB-2 的"扫了、没比、报健康"是**同一病理**（只是下沉到索引一级），
而且这一类恰好是最危险的一类：同名不同选项会让 `create_index` 抛 `OperationFailure`、
`ensure_index` 吞成 `return False` ⇒ **整个仓储 `_db` 永久为 None**。

**处置：本批内修**（`34b0faf6`，R5）。理由：这不是"顺手发现的新 finding"，而是**本批交付物
自身的缺陷**——本批的存在意义就是消灭这一类假保障，把一个刚被证明有假绿洞的守卫当作
"完成"交出去是不诚实的。（§0 的 `NEW_FINDING_OUT_OF_SCOPE` 规则针对的是范围外的新问题；
本条在范围内、且不需要改任何生产代码。）

**修法**：新增 `_option_table_key_errors()` —— 登记条目的**选项键集**必须与代码声明一致：

- **只比键、不比値**：值写错走"鸣笛"方向（运行期报 `option_conflicts`），不是假绿；
  TTL 按设计只比"有没有"、不比秒数；动态声明（`unique=desired_unique`）整体跳过。
- 附两条锚点：`test_blank_option_entry_is_really_a_runtime_blind_spot`（**直接调用运行期
  `_option_mismatches`**，把"空/错键 ⇒ 静默跳过"固化下来，红了就说明 R5 的必要性论证需重写）
  与 `test_guard_flags_blanked_and_misspelled_option_keys`（三种变异 in-suite 灵敏度）。
- 变异复验（独立 worktree，HEAD）：`{}` → 🔴 1 failed；`{"unicorn": True}` → 🔴 1 failed；
  还原 → ✅ 37 passed。
