## 2. Root Cause

### 2.1 F1 —— 资源生命周期所有权错误（不是"抽象味道"）

```
Agent.__init__  → LLMAdapter(model=config.llm.model) → LLMFactory.create → AsyncOpenAI(A)
_start_task_system → raw_llm = self._llm.get_raw_client()  ← A
                   → AgentInfra.llm = A（engine 的 Planner/Executor/Evaluator +
                                        DelegationPreparer 都读它）
Agent.switch_llm(B) → LLMAdapter.switch_model()
                   → self._backend = 新 backend（客户端 B）
                   → self._closing_backends.try_spawn(旧 backend.close())  ← 后台关掉 A
```

**A 由主 LLM 适配器创建/关闭，却被工作流长期持有**——没有任何一条 close 路径通知
工作流（`AgentInfra` 是纯 dataclass，`WorkflowEngine` 公开面只有 `constraints`）。
于是热切换之后工作流握着一个**已关闭**的 `AsyncOpenAI`，任何后台任务 LLM 调用抛
`APIConnectionError ← RuntimeError: Cannot send a request, as the client has been closed.`

关键判据是 `is_closed()` 的翻转（Batch 1.5 与本批各自独立复现）：

```
captured.is_closed()  [切换前]  False
llm.switch_model("openai/gpt-4o") + 等后台 close 落定
captured.is_closed()  [切换后]  True      ← 修复前
```

**"谁拥有"这件事在修复前是 mixed 的**：client 维度=启动时跟随主运行时（之后冻结成
悬垂引用），模型名维度=独立 env（`TASK_SYSTEM_MODEL`，回退 `deepseek-v4-pro`）。
修复把 client 维度改成**工作流自有**，模型名维度**保持独立**（那是有意的，不在本批动）。

### 2.2 F2 —— 工具没有运行期句柄，且启动期快照必然过期

```python
# core/tools/runtime_config/plugin.py（修复前）
config = ctx.get("config")            # ← AppConfig（bootstrap/YAML）
lines.append(f"模型: {config.llm.model}")
parts.append(f"TTS: {'启用' if tts_cfg.enabled else '禁用'} ({tts_cfg.model})")
```

根因不是"读错了一个字段"，而是**结构性的**：`ToolContext.services` 里根本没有运行期
句柄（实测键集：`_bus/_fsm_state/_session_msg_count/_started_at/_token_tracker/
_tool_count/_tool_manager/_tool_names/config/desktop_bridge/scheduler/session`），
agent 对象完全不可达。而工具 ctx 建在 `_STARTUP_STEPS` 的**第 2 步**
（`tool_context`），真正决定这些值的步骤排在它之后（`service_state` 第 5、
`tts` 第 6），运行期还会被 `switch_*` / `set_service` 改写 ——
**启动期写任何快照都必然过期**，所以只能注入可调用的活口。

为什么它长期存活：**冷启动时 B == R**，这个谎只在切换之后才看得见。

### 2.3 F4 —— 覆盖只写进了"下一行就会被替换掉"的那个对象

```python
# app.py（修复前）
config.server.port = args.port          # 写进 config
asyncio.run(run_agent_service(config=config, config_path=args.config, ...))

# core/agent/server.py::run_agent_service（修复前）
while True:
    if config_path is not None:
        config = ConfigLoader(AppConfig, yaml_path=config_path).load()   # ← 整个换掉
```

丢失点**两处**（同一形态）：`run_agent_service` 每轮开头（主犯，实测每轮都重载）与
`run_server` 的原地重启重载（`rebuild_on_restart=False`，生产无调用方）。
`--cli` / `--check` 两条**不经** `run_agent_service` 的路径反而生效 ⇒ 同一个 flag 在
不同模式下行为不同。

Pattern C（"argparse default 被误当显式覆盖"）实测**当前不存在**——修复前的
`default=config.tts.enabled` 取自刚加载的 config，"没传"时是恒等赋值；但那是
**潜在雷**（改成朴素 `store_true` 就会静默关掉 YAML 里打开的 TTS）。

## 3. Ownership Map（运行时资源所有权）

图例：`create` = 谁构造／`owner` = 谁负责其生命周期／`close` = 谁关闭／
`reconnect` = 谁重建连接／`switch` = 谁替换。

| 资源 | create | owner | close | reconnect | switch |
|---|---|---|---|---|---|
| **Main LLM**（`LLMAdapter` + 其 backend/client） | `Agent.__init__`（`agent.py:268`）→ `LLMFactory.create` | `LLMAdapter`（`Agent._llm`） | `_stop_llm_and_tts` → `LLMAdapter.close()`（3s 预算）；`switch_model` **后台**关旧 backend（`_closing_backends`，`close()` 时 drain） | `Agent.start()` 首行 `_llm.reconnect()`（重建 client） | `Agent.switch_llm` → `LLMAdapter.switch_model`（先建后换） |
| **Task LLM**（工作流的 `LLMBackend` + raw client）**← F1** | `_start_task_system` → `_build_task_llm_backend`（`LLMFactory.create("<主 provider>/<TASK_SYSTEM_MODEL>")`） | **工作流**（`Agent._task_llm_backend`） | `_stop_task_system` → `backend.close()`（`_TASK_LLM_CLOSE_BUDGET` = 3s 叶子预算；关闭后立刻置 None ⇒ 恰好关一次） | 每次 `start()` 重新构造（**不** reconnect 复用） | 不随主 LLM 热切换；`TASK_SYSTEM_MODEL` 每次 start 重求值 |
| **STT backend** | `run_server` 启动段 / `switch_stt` | `Agent._stt` | `_stop_llm_and_tts`；`switch_stt` 关被替换下来的旧后端 | 无（每次 switch 新建） | `Agent.switch_stt`（先建 + 1s 连通性测试，成功才替换） |
| **TTS backend** | `_start_tts` / `switch_tts` | `Agent._tts`（`_cognitive.configure(tts=…)` 同步引用） | `_stop_llm_and_tts`；`switch_tts` 关旧后端 | 无 | `Agent.switch_tts`；门控投影唯一写点 `_sync_tts_gate` |
| **OutputManager** | `Agent.__init__`（+ `ConsoleChannel`） | `Agent._output` | `_stop_output` | — | channel 增删由 WS 生命周期管 |
| **WorkflowEngine** | `_start_task_system` | `Agent._task_system` | `_stop_task_system` → `engine.stop()`（外层 `_TASK_SYSTEM_STOP_BUDGET` = 20s ≥ 内部最坏 ≈17s，S2-A3 不变量） | — | 每次 `start()` 重建（`/restart` 整只 Agent 重建） |
| **ToolManager / ToolAdapter** | `Agent.__init__`（ToolAdapter）→ `_start_tool_context` → `ToolAdapter.start` → `manager.load_all` | `Agent._tool_adapter` | `_stop_tool_adapter` → `ToolAdapter.shutdown()`（并把 `_started` 复位 ⇒ 同实例 restart 时 `start()` 会**重新合并** `extra_services`，C4/P1-07） | — | `POST /tools/reload`；`switch_*` 不涉及 |

**F1 修复的本质**：Task LLM 从"Main LLM 的借出品"（owner = `LLMAdapter`）变成
**独立资源**（owner = 工作流生命周期）。修复后"谁 create / 谁 close"同一方，
"长期持有者"与"关闭者"不再分离。

## 5. F1 Workflow Lifecycle

| 维度 | 修复前 | 修复后 |
|---|---|---|
| **ownership** | mixed：client = 主 LLM 适配器的借出品（owner = `LLMAdapter`），模型名 = 独立 env。**A 创建/关闭、B 长期持有** | 工作流**自有**：`_start_task_system` 建、`_stop_task_system` 关（`Agent._task_llm_backend`）。模型名仍独立（有意） |
| **create 的凭据来源** | 直接取主适配器当时那个 raw client | `LLMFactory.create("<主 provider>/<TASK_SYSTEM_MODEL>")`；连接参数（base_url/api_key/出站守卫）按**主模型标识**经 `_resolve_switch_params` 解析（custom 条目的参数挂在 provider 条目上，裸模型名对不上任何条目）——**复用**既有实现，不抄第四份 SSRF 守卫 |
| **switch behavior** | 主模型热切换 → 工作流的 client **被关闭** ⇒ 任何后台调用硬失败（`APIConnectionError`）；**在途**请求同样被杀（探针用真实本地端点实测） | 主模型热切换只关它自己换下来的 backend，碰不到工作流；工作流的 client 与 model 均不变，在途请求不被取消、切换后同一 client 仍可用 |
| **restart behavior** | 同实例 `stop()`→`start()` 与 `/restart`（整只新 Agent）**本来就不泄漏**（`start()` 重跑 `_start_task_system` 重新捕获）——F1 只在"不重启的热切换"上发生 | 每次 `start()` 建**全新** task LLM；`stop()` 关掉旧的（恰好一次，幂等） |
| **close 语义** | `_stop_task_system` **不关**任何 LLM（所有权在主 LLM） | 关**自己那个**；仍**不碰**主 LLM 的 client（那条不变式原样保留，测试两半都钉） |
| **shutdown 顺序** | — | `_SHUTDOWN_STEPS`：`stop_task_system`（第 10 步）先于 `stop_llm_tts`（第 19 步）；且 `_stop_task_system` 内部先 `WorkflowEngine.stop()`（等在途任务落定，内部最坏 ≈17s）**再**关 task LLM |

### 7.2 优先级矩阵（§19 要求"先写出真实优先级"）

```
显式 CLI 覆盖  >  env  >  YAML  >  dataclass 默认
```

- `env > YAML > 默认` 由 `Module/config/loader.py::load()` 实现
  （`_instantiate_defaults()` → `_merge_yaml()` → `_override_from_env()`）；
  env 名 = `get_env_name(fld) or resolve_env_name(prefix + field_name)`
  ⇒ `SERVER_HOST`（显式）/`SERVER_PORT`/`TTS_ENABLED`/`STT_ENABLED`/`AGENT_CHARACTER`（推导）。
- **CLI 与 env 的相对顺序沿用现状语义**（本批没有发明新顺序）：`app.py` 一直是在
  `ConfigLoader.load()` **之后**写这几个字段的，`--cli` / `--check` 模式下实测 CLI 赢 env。
  本批只是把同一顺序搬到"重载之后"，并把它变成文档 + 测试。
  等价矩阵（`test_cli_overrides.py::TestPrecedenceMatrix`，真 `ConfigLoader` + 真 YAML）：
  `8765`（默认）/ `9000`（YAML）/ `7000`（env 压 YAML）/ `9999`（CLI 压 env）/ `9999`（CLI 压 YAML）。
- **区分"CLI 默认值"与"用户显式传的值"**：5 个 flag 的 argparse `default` 改为
  `SUPPRESS` ⇒ "没传"= 属性不存在 = 不进覆盖表。实测 `--help` 输出**逐字节不变**
  （本 parser 未启用 `ArgumentDefaultsHelpFormatter`，help 里本来就没有 `(default: …)`）。
  修复前 `default=<config 值>` 的写法虽然"碰巧"没造成 Pattern C，但把两者混为一谈
  ⇒ 一旦有人"清理"成朴素 `store_true`，YAML 里打开的 TTS 会被静默关掉。

### 7.3 `/restart` 语义（本批裁定）

**显式 CLI 覆盖 = 进程生命周期的意图，`/restart` 保留**；YAML-only 的值仍按既有规则
每轮重读。理由：`/restart` 会**重新 bind**，若覆盖被重置，服务会在用户没要求时换端口。
两条都测试（`test_overrides_preserved_across_restart` / `test_yaml_wins_when_no_flag_is_passed`），
两条重启路径都覆盖（rebuild 走 `run_agent_service`；原地走 `_reload_config_from_disk`）。

### 7.4 修法

```
app.py                     build_parser() / collect_cli_overrides() / CLI_OVERRIDES 表
                           default=argparse.SUPPRESS（只收集显式传入的）
core/config/app_config.py  apply_config_overrides(config, overrides)  ← 覆盖层唯一施加点
core/agent/server.py       run_agent_service(..., config_overrides=…)：每轮重载后重新施加，
                           并把覆盖表交给 agent_factory
core/agent/server.py       AgentServer._reload_config_from_disk()：原地重启重读后同样重新施加
core/agent/agent.py        Agent.__init__(..., config_overrides=…) 存下来供上面那处用
```

`apply_config_overrides` 对未知路径 **fail-fast**（`AttributeError`）——静默失效正是本缺陷的形态。

## 10. Remaining Risks

只列真实剩余风险，按严重度：

1. **🔴 引擎"规划失败"路径不推终态事件（与 F1 正交，本批未修）。**
   实测：`_plan_with_retry` 耗尽两次尝试 → `task_state.fail(PLANNING_FAILED)` 并返回
   `None` → `plan_and_validate` 见 `None` 直接 `return` → `sub_agent.run` 早退 →
   `_run_and_cleanup` 视作**正常返回** ⇒ `push_mailbox_event` **调用 0 次**、mailbox 空。
   后果：用户进程内**收不到任何**"任务失败"通知；停机时 `_stop_mailbox` 把它落库成
   **"任务因服务重启被中断，未产生结果"**（错误归因）。任何规划失败都这样，不限于
   client 关闭。**修它要动 mailbox 契约（终态推送的触发点），不属本批。**
   > 附带：`test_task_system_model.py::test_engine_path_degrades_to_failed_task` 的
   > docstring 声称"用户看到『任务执行失败: …』"——该表述对**规划失败**路径不成立
   > （用例只断言 `task_state`，没断言 mailbox）。本批**未**改这句 docstring（改它要
   > 连带决定是否补推送），已在 Follow-up 登记。
2. **🟠 `/debug/api` 的 `tts_ok`/`stt_ok` 语义是"后端对象存在"，不是"服务启用"。**
   实测 `set_service('tts'/'stt', False)` 后仍报 `True`，前端渲染成 ✓/✗。
   `DebugData` 契约只有 `llm_model`，没有 stt/tts 的 model/enabled。字段意图
   （health vs enabled）**没有任何文档裁定** ⇒ 需先裁定，且补字段要跑 `make gen-types`。
3. **🟠 `TASK_SYSTEM_MODEL` 只能填裸模型名 ⇒ 换不了 provider；且本批把它变成了
   "重启依赖"的行为（Challenger H3，LOW–MEDIUM）。**
   未设该 env 时，task LLM 的 provider 取自 **start 时刻的主模型**。若主模型是
   `openai/gpt-4o`，构造出来的是 `OpenAICompatBackend(model="deepseek-v4-pro",
   base_url=api.openai.com)` ⇒ 每次后台调用必 400。**不比修复前更糟**——修复前用的是
   主 raw client + 同一个 `model=`，出站请求逐字节相同——但**新的是**：热切换主模型到
   另一 provider 之后任务系统**仍能工作**（它有自己的 client），只有**重启**才会按当时
   的主 provider 重建并开始 400。即"修复前前后都坏"变成"重启前好、重启后坏"。
   未改行为（§28：provider-neutral 属 Follow-up），只把日志/文档措辞改准。
4. **🟡 F5 `/api/providers/test` 的 STT 缺省模型仍读 config**（llm/tts 读 runtime）。
   无测试钉住，可安全修；不在本批范围。
5. **🟡 Workflow model 零 reporter**：用户在 banner / debug / capabilities /
   `get_runtime_config` 四处都看不到后台任务用哪个模型。补它需要一个 reporter，
   属 Follow-up（本批没有为它新增 UI 面）。
6. **🟡 `_start_tool_context` 的 `extra_services` 依赖 `ToolAdapter.shutdown()` 复位
   `_started`**（C4/P1-07）。实测该复位存在，故同实例 restart 会重新合并 `config` 等
   对象；若将来有人"优化"掉那个复位，`services["config"]` 会变成旧对象
   （只影响服务地址行的报告）。**无当前缺陷**，仅记录耦合。
7. **⚪ 本批的测试成本**：`test_cli_overrides.py` 里 9 条子进程用例约 12s（已把
   parser 的 7 个 argv 变体合并进**一个**子进程；逐 flag 起进程会把 Quick 档拖长几十秒）。

## 11. Keep As-Is

**这一节是刻意存在的**——避免"修 bug = 顺手重构"。

1. **`TASK_SYSTEM_MODEL` 保持 `intentional external env-only config`**（Batch 1.5 分类）：
   本批**没有**删它、**没有**合并进主 LLM、**没有**为它加 YAML 键或 AppConfig 字段。
   只把它的读取点从 `default_factory` 的 lambda 提成具名函数 `resolve_task_system_model()`
   ——**同一个文件、同一个 env 名、同一个回退值**，因为 F1 需要"先知道模型名再建 backend"，
   而两处各写一次 `os.getenv` 会让"模型名从哪来"重新变成不可判定（Batch 1.5 的
   `test_env_var_has_exactly_one_production_read` 仍然为绿）。
2. **`AgentInfra.llm` 的字段类型不变**（仍是 `AsyncOpenAI`，不是 callable/resolver）：
   方案 B（动态 resolver）实测**修不了在途请求**（探针用真实本地端点证明 `close()` 会杀掉
   已发出的请求），等于把"全程有效"降级成"每次调用边界有效"——不是原不变式的恢复。
3. **`switch_llm` 不重绑工作流**（方案 C 被否）：`WorkflowEngine._infra` 是私有、无公开重绑
   API（新增它就是扩公共面），且重绑后仍会把裸名 `deepseek-v4-pro` 发给新 provider 的端点。
4. **会话切换不重放模型热切换（K4）**：F2 的快照刻意**不**读 `session.service_state`
   的模型字段——激活一个从未切过模型的会话时它为空，而适配器仍在跑上一个模型。
   自述必须报"此刻真的在用"的那个。
5. **`AppConfig` 仍是 bootstrap/configured defaults**：本批**没有**把它改成运行期可变真相
   （F2 用的是只读投影 `ServiceRuntimeState`）。写回 config 有技术反证：会让
   `run_agent_service` 的 `model_changed_in_file` 恒判"文件变了" ⇒ 热切换在下次重启被静默切回。
6. **`--tts` / `--stt` 仍是单向 flag**（`store_true`，无法用它关掉 YAML 里打开的开关）：
   加 `--no-tts` 是**新功能**，不在本批。`SUPPRESS` 改造保持了"没传就不动"的语义。
7. **`run_agent_service` 保持"每轮重载 YAML"**：这是 `/restart` 重读 YAML 的既有契约
   （`test_restart_rebuild.py` 钉着它），F4 选择叠加覆盖层而不是"首轮不重载"。
8. **`rebuild_on_restart=False` 的原地重启路径保留**（生产无调用方）：本批只是让它也遵守
   "重读之后重新施加覆盖"，没有删它。
9. **`config.yaml` / `providers.yaml` 分工不变**、**prompt budget 留在 `Module/` 侧不变**、
   **`RoutingS`/`_BACKENDS` 缓存不变**（Batch 1.5 的 K1/K13/K10 结论继续有效）。
