## 1. 结论

`core/` 当前组织方式总体健康：底层 schema/config/utils 是稳定叶子，包内测试与 README 覆盖完整，运行时模块级 import 环几乎不存在，lint/pyright/quick 测试全绿。主要风险集中在四个包级运行时依赖环、若干高复杂度枢纽模块，以及 core 层抽象不足导致的高扇出耦合。这些问题目前不阻断开发，但在 `core/input`、`core/cognitive` 继续扩张前应安排整改。

| 编号 | 优先级 | 问题 | 当前影响 |
|---|---:|---|---|
| CORE-MOD-P1-01 | P1 | `core.agent ↔ core.input` 包级运行时依赖环 | 组合根与传输层互依，agent 生命周期必须函数内 import 规避环；input 内基础设施被 agent 反向消费，边界已经不适配 |
| CORE-MOD-P1-02 | P1 | `core.adapter ↔ core.memory` 包级运行时依赖环 | PromptAssembler 放错层（应用胶水在 adapter），MemoryConsolidator 反向依赖具体 LLMAdapter |
| CORE-MOD-P1-03 | P1 | `core.monitoring ↔ core.status` 包级运行时依赖环 | status 为取 `EventPriority` 而函数内 import monitoring；该环修复成本低 |
| CORE-MOD-P1-04 | P1 | 复杂度集中在 5–6 个枢纽文件/函数 | loop/ws/upload/gc 的单一函数承担 35–55 个决策分支，变更回归面过大 |
| CORE-MOD-P2-01 | P2 | `core.input` 体量过大且职责混合 | 33 个文件 / 8787 LOC（约 27%），同时承担传输、REST 业务和 agent 生命周期依赖的基础设施 |

| CORE-MOD-P2-03 | P2 | `core.input ↔ core.input.debug_routes` 父子包互依 | 风险较低；debug_routes 复用父包私有 `_common`，需要收敛共享 helper |

### 2.2 依赖分析方法

- 用 AST 解析全部生产 import，区分顶层/函数内运行时 import 与 `if TYPE_CHECKING` 类型 import。
- 包级和模块级分别求 SCC、fan-in / fan-out。
- 用 AST 估算函数圈复杂度（近似 McCabe；含布尔短路与推导式计权）。
- 用 Ca/Ce 计算 Martin instability（I），用 ABC/抽象方法占比估 abstraction（A）。

### 2.3 已确认健康的基线

- 运行时**模块级** SCC 只有 1 个：`core.schema.types ↔ core.schema.utils`。该环已通过 `types.py:5-14` 的 `_normalize_iso_ts` 函数内延迟 import 打破 eager 环，运行时安全；建议保持现状，不在无必要情况下重排。
- `core.schema` fan-in 124 / fan-out 34，且 fan-out 主要是 stdlib、pydantic 和 `Module`（契约类型权威），是最稳定的叶子层。
- `core.config`、`core.utils`、`core.version`、`core.hitl` 均为叶子。
- 非 `__init__/__main__` 生产文件中相对导入为 0（Ruff TID252 实跑通过）。
- `core/agent` 生命周期已按 `_lifecycle_persistence/services/tools/task_system` 拆成四个 mixin，组合根职责总体清晰。
- `core/input` 的 REST 已按 provider/tts/upload/tools/chat/attachment/session 拆分，方向正确，只是包仍太大。

### 2.4 包级运行时依赖环清单（核心问题）

| 环 | 方向与 import 引用数 | 严重度 |
|---|---|---|
| `core.agent ↔ core.input` | agent→input：11；input→agent：1 | 高 |
| `core.adapter ↔ core.memory` | adapter→memory：2；memory→adapter：1 | 中高 |
| `core.monitoring ↔ core.status` | monitoring→status：2；status→monitoring：6 | 中（修复成本低） |
| `core.input ↔ core.input.debug_routes` | input→debug_routes：1；debug_routes→input：5 | 低 |

如果把 `TYPE_CHECKING` 类型 import 也计入，13 个 core 包会构成一个巨型 SCC；这不会造成 import 时循环，但说明包边界的“概念耦合”比运行时物理耦合更广。

## 3. Findings

### CORE-MOD-P1-01：`core.agent ↔ core.input` 边界反转

#### 3.1 现状

`core.agent` 在生产代码中运行时依赖 `core.input` 的 11 处：

| 位置 | 依赖 |
|---|---|
| `core/agent/_lifecycle_services.py:91` | `core.input.custom_providers.resolve_model_params` |
| `core/agent/_lifecycle_persistence.py:319,339` | `core.input.idempotency.get_store` |
| `core/agent/server.py:58,403` | `core.input.custom_providers.resolve_model_params` |
| `core/agent/server.py:191,242,301,359` | `core.input.capabilities.broadcast_capabilities` |
| `core/agent/server.py:377,389` | `core.input.server.create_app` 及启动守卫 |

反向 1 处：

- `core/input/server.py:18`：`from core.agent import Agent`。

#### 3.2 问题

1. `AgentServer.run_server()` 是组合根的一部分，但它直接 import `core.input.server.create_app` 来装配 aiohttp 应用，形成“组合根 → 传输层 → 组合根”的包级环。
2. `idempotency`、`custom_providers`、`capabilities` 本质是运行时基础设施/provider 元数据，不依赖 HTTP/WS；把它们放进 `core.input` 后，`core.agent` 的生命周期被迫反向依赖传输层。
3. 代码已出现多处函数内 import 来规避循环（`server.py` 的 `create_app`/`assert_secure_bind`、`_lifecycle_persistence.py` 的 `get_store`、`capabilities.py` 内部亦有同类先例）。函数内 import 只是把环从 import-time 挪到 call-time，没有解决边界问题。

#### 3.3 建议方案

1. 将 `core.input.idempotency`、`core.input.custom_providers`、`core.input.provider_registry`、`core.input.rate_limiter` 迁出 `core.input`：
   - 持久化类：迁 `core/storage`（或新建 `core/runtime_state`）；
   - provider 元数据/自定义 provider：新建 `core/providers`；
   - 限流：迁 `core/middleware` 或保留在新基础设施包。
2. 将 `capabilities.broadcast_capabilities` 中与传输无关的组装逻辑与 WS 广播逻辑分离；agent 只依赖组装结果，广播经 OutputManager 或注入的回调完成。
3. 把 `run_server` 的服务装配移出 `core/agent/server.py`：
   - 推荐 `app.py` 只做 `create_app(agent)` → `web.run_app(...)` 的薄装配；
   - `AgentServer.run_server()` 改为接受/注入 `create_app` 工厂，或在 `app.py` 完成 restart 循环编排。
4. 目标依赖方向固定为：`core.input → core.agent`，禁止反向。

#### 3.4 验收标准

- AST 依赖图中不再存在 `core.agent → core.input` 的运行时边。
- `core.agent` 内不再出现 `from core.input...`（`TYPE_CHECKING` 也应尽量清零）。
- `make lint`、`make pyright`、`pytest -m "unit or service" core/` 保持全绿。
- 启动、`/restart`、自定义 provider 重启恢复、幂等 reconcile、capabilities 重播四条路径的既有测试不回归。

### CORE-MOD-P1-02：`PromptAssembler` 放错层，adapter/memory 形成环

#### 3.1 现状

- `core/adapter/prompt_assembler.py:30-31` 运行时依赖 `core.memory.session.SessionMemory` 与 `core.memory.long_term.LongTermMemory`。
- `core/memory/consolidator.py:25` 运行时依赖 `core.adapter.llm_adapter.LLMAdapter`。
- 形成 `adapter → memory → adapter` 包级环。

#### 3.2 问题

1. `adapter` 在项目语义中是“封装 `Module/` 后端”的薄适配层；`PromptAssembler` 创建 12 个 PromptSection、注入 `CharacterEngine`/记忆数据，是应用级胶水，不应与 LLM/TTS 后端适配器同层。
2. `MemoryConsolidator`/`MemoryReflector` 是记忆域组件，却反向依赖具体 `LLMAdapter`；替换 LLM 后端或测试时只能 mock 具体类，无法依赖协议。
3. 该环虽未造成 import-time 失败，但会持续诱导后续开发把“应用编排逻辑”继续塞进 adapter。

#### 3.3 建议方案

1. 把 `PromptAssembler`、`MessageBuilder` 迁出 `core/adapter`：
   - 推荐新建 `core/prompt/`，或并入 `core/cognitive/`（PromptAssembler 只被认知管线消费时）。
   - `core/adapter/__init__.py` 保留过渡期 re-export shim，待调用点全部迁移后删除。
2. 记忆域的 LLM 调用改为依赖窄接口：
   - 短期：把 `LLMAdapter` 的消费接口抽象为 `core/prompt/` 或 `Module/llm/protocol` 下的协议（如 `complete_json()` 一类），由 Agent 注入；
   - 中期：`MemoryConsolidator`/`MemoryReflector` 不 import `core.adapter`。
3. 目标依赖：`adapter → Module`；`memory → storage/schema`；`cognitive → memory + adapter`，不允许 memory 反向依赖 adapter。

#### 3.4 验收标准

- AST 依赖图中 `core.adapter ↔ core.memory` 环消失。
- 记忆提取/去重相关测试无需修改业务断言即可通过（允许改构造/mock 方式）。
- `core/adapter/README.md` 与 `core/README.md` 更新职责描述。

### CORE-MOD-P1-03：`status` 为取 `EventPriority` 反向依赖 `monitoring`

#### 3.1 现状

- `core/monitoring/idle_monitor.py:14,46` 运行时依赖 `core.status.agent_fsm.AgentFSM` 与 `core.status`（`FSMBackedStatus` 回退构造）。
- `core/status/fsm.py:116,128,142,155,168,203` 在 `enter_*`/`finish_turn`/`handle_interrupt` 中函数内 `from core.monitoring.event_bus import EventPriority`。
- 形成 `monitoring → status → monitoring` 环。

#### 3.2 问题

1. `EventPriority` 实际定义在 `core/schema/agent.py`，`core.monitoring.event_bus` 只是 re-export；status 为取这个符号绕到 monitoring 是多余的。
2. 该环让状态机实现（应是最稳定组件之一）依赖监控包，层级上不合理。
3. 这是四个环中修复成本最低的一个，应优先处理。

#### 3.3 建议方案

1. `core/status/fsm.py` 改 `from core.schema.agent import EventPriority`，删除 6 处函数内 import。
2. 保持 `core.monitoring → core.status` 单向（IdleMonitor 依赖状态机/状态接口是合理方向）。
3. 若后续进一步解耦，可把 `EventBus` 下沉到 `core/events`，由 status 和 monitoring 共同依赖；但在当前规模下，先改 EventPriority 来源即可消除环。

#### 3.4 验收标准

- AST 依赖图中 `core.status → core.monitoring` 运行时边归零。
- `core/status` 与 `core/monitoring` 测试全绿。
- 无行为变化：STATE_CHANGE 事件的优先级仍为 `EventPriority.STATE_CHANGE`。

### CORE-MOD-P1-04：高复杂度枢纽模块集中

#### 3.1 现状（AST 估算圈复杂度）

| 函数 | 位置 | 估算 CC | 函数跨度 |
|---|---:|---:|---:|
| `upload_handler` | `core/input/upload_routes.py:109` | 55 | 265 / 473 行 |
| `handle_ws` | `core/input/ws_handler.py:164` | 51 | 309 / 1166 行 |
| `run_attachment_gc` | `core/storage/attachment_gc.py:106` | 47 | 193 / 298 行 |
| `_route_v2_text` | `core/input/ws_v2.py:253` | 41 | 299 / 731 行 |
| `_finalize_turn` | `core/cognitive/loop.py:940` | 35 | 185 / 1552 行 |
| `_execute_tool_round` | `core/cognitive/loop.py:760` | 33 | 177 / 1552 行 |
| `LongTermMemory.search` | `core/memory/long_term.py:639` | 30 | 111 / 787 行 |
| `DebugInfo.collect` | `core/debug/info.py:141` | 30 | 223 / 363 行 |
| `create_app` | `core/input/server.py:151` | 27 | 335 / 485 行 |
| `query_search` | `core/storage/message_repo.py:365` | 26 | 99 / 580 行 |
| `CognitiveLoop.process` | `core/cognitive/loop.py:389` | 24 | 204 / 1552 行 |
| `build_messages` | `core/adapter/message_builder.py:22` | 24 | 78 / 141 行 |

#### 3.2 问题

1. `loop.py` 的 `process/_think_loop/_execute_tool_round/_finalize_turn/_dispatch_stream_event` 各自 70–204 行，单文件 1552 行；认知管线的 stream、tool、finalize、dispatch 四个阶段事实上已可独立成 mixin，但还挤在一个类里。
2. `ws_handler.handle_ws` 同时覆盖握手、v1/v2 分发、二进制、replay、voice 会话和错误路径；虽然 `_WS_HANDLERS` 注册表已经拆了消息级分发，但函数主体仍是“一个函数读懂整个协议”的形态。
3. `upload_handler`、`run_attachment_gc`、`DebugInfo.collect` 都是“大管道函数”，每个新增规则都在同一函数内继续加分支。
4. 这些文件的回归测试都不少，但单测保护的是行为，不是函数边界；继续增长会显著抬高认知成本和改动冲突概率。

#### 3.3 建议方案

按“先切阶段、再抽 helper、最后定阈值”的顺序：

1. `core/cognitive/loop.py`：
   - 拆 `_stream_llm_response` + `_dispatch_stream_event` → `StreamPhaseMixin`；
   - 拆 `_execute_tool_round` + `_handle_submit_task` 相关 → `ToolPhaseMixin`（`tools.py` 已有雏形）；
   - 拆 `_finalize_turn` → `FinalizeMixin`；
   - `process/_think_loop` 只保留阶段编排。
2. `core/input/ws_handler.py`：
   - 握手/replay 拆 `ws_lifecycle.py`；
   - v1 文本/命令分发与 v2 协议继续下移，`handle_ws` 只做 transport framing 与错误兜底。
3. `upload_routes.py`：把 multipart 解析、逐文件 kind 配对、魔数校验、MIME 规范化拆成纯函数，`upload_handler` 只编排。
4. `attachment_gc.py`：四条规则（软删超时物理删 / active 文件缺失软删 / 未关联超期软删 / 磁盘孤儿清理）各拆一个纯策略函数。
5. `debug/info.py`：按 16 个 panel 拆 collector，`collect()` 只做 merge。
6. 建议后续门禁阈值：新函数 CC ≤ 15；生产文件 ≤ 600–800 行（旧文件用里程碑逐步降，不要求一次性达标）。

#### 3.4 验收标准

- 上述拆分不改变公开行为；对应测试全绿。
- `make check-types`、`make pyright`、`make lint` 全绿。
- 每个拆出的模块有明确 docstring 说明阶段职责。

### CORE-MOD-P2-01：`core.input` 体量过大且职责混合

#### 3.1 现状

`core.input`（含 `debug_routes`）33 个文件 / 8787 LOC，占 `core/` 生产代码约 27%，承担三类职责：

1. **传输层**：`server.py`、`ws_handler.py`、`ws_v2.py`、`audio_buffer.py`、`voice_sessions.py`、`wakeword.py`；
2. **REST 业务**：`session_routes.py`、`attachment_routes.py`、`provider_routes.py`、`tts_routes.py`、`upload_routes.py`、`tools_routes.py`、`chat_routes.py`；
3. **被 agent 生命周期消费的基础设施**：`idempotency.py`、`custom_providers.py`、`provider_registry.py`、`rate_limiter.py`、`capabilities.py`。

#### 3.2 问题

第三类模块是 `CORE-MOD-P1-01` 的根因。它们被 `AgentLifecycle`/`AgentServer` 依赖，但放在 input 包里，使 input 无法成为“只依赖 agent 的传输边界”。同时 33 个文件的包在新增路由或基础设施时，容易让开发者无意识地继续横向扩张。

#### 3.3 建议方案

- 先执行 CORE-MOD-P1-01 的搬迁；`core.input` 只保留 1+2。
- 若 REST 持续增长，可进一步拆 `core/input/rest/`（session/attachment/provider 等）与 `core/input/ws/`，但先不要为拆而拆；优先处理基础设施搬迁。
- `debug_routes` 的共享 helper 收敛到公开的 `core/input/_common.py` 子集，禁止跨包使用下划线私有模块。

### CORE-MOD-P2-02：core 层抽象不足，高扇出包处于 pain zone

#### 3.1 现状

| 包 | Ca | Ce | I | A | 备注 |
|---|---:|---:|---:|---:|---|
| `core.agent` | 2 | 19 | 0.90 | 0.00 | pain zone；作为组合根高扇出可部分接受 |
| `core.cognitive` | 2 | 10 | 0.83 | 0.00 | pain zone；认知管线核心却无协议 |
| `core.input` | 3 | 11 | 0.79 | 0.00 | pain zone；传输层依赖具体类 |
| `core.input.debug_routes` | 2 | 5 | 0.71 | 0.00 | pain zone |
| `core.task` | 2 | 4 | 0.67 | 0.00 | — |
| `core.adapter` | 6 | 7 | 0.54 | 0.00 | 依赖集中在具体 LLM/TTS 适配器 |
| `core.status` | 4 | 4 | 0.50 | 0.40 | 唯一有较完整接口边界的核心包 |
| `core.storage` | 7 | 3 | 0.30 | 0.08 | `Repository` ABC 使用正确 |

（Ca/Ce 为运行时包级唯一依赖数；A 为 ABC/抽象方法占比。）

#### 3.2 问题

1. `Module/` 层有完整 Protocol-Registry-Backend 模式，但 `core/` 消费时几乎都绑定 `LLMAdapter`、`TTSStreamManager`、`ToolAdapter` 等具体类。
2. `Agent` 的 39 个公开 property 很好，但 `CognitiveLoop`、`SessionManager`、`LongTermMemory` 等核心域对象之间仍是具体类互连。
3. 测试目前靠 mock 具体类完成，没有通过协议约束“最小依赖面”，后续替换 LLM/TTS 或把记忆域独立出来成本会偏高。

#### 3.3 建议方案

- 先不要大规模引入 Protocol（会制造抽象噪音）。优先在已被环影响的边界引入：
  1. 记忆域消费的 LLM 能力接口（配合 CORE-MOD-P1-02）；
  2. status 与 monitoring 之间的事件/状态查询接口（配合 CORE-MOD-P1-03）；
  3. `AgentServer.run_server` 的 app 工厂注入（配合 CORE-MOD-P1-01）。
- 其余具体类耦合保持现状，等第二个消费者出现再抽象（YAGNI）。

---

### CORE-MOD-P2-03：`core.input ↔ core.input.debug_routes` 父子包互依

#### 3.1 现状

- `core/input/server.py:28` 运行时依赖 `core.input.debug_routes.register_debug_routes`。
- `debug_routes` 的 `__init__.py`、`archive.py`、`character.py`、`ltm.py` 运行时依赖父包 `core.input.errors` / `core.input._common`（共 5 处）。

#### 3.2 问题

父子包互依通常可接受，但 `debug_routes` 依赖父包的下划线私有模块，意味着 debug API 与 input 内部实现绑定。若后续按 CORE-MOD-P2-01 拆分 REST，这些私有依赖会变成迁移阻力。

#### 3.3 建议方案

- 把 `_common` 中 debug 需要的部分提升为公开模块（如 `core/input/shared.py`）或移动到 `core/input/debug_routes/_shared.py`。
- 明确 `debug_routes` 允许依赖父包公开 API，禁止依赖 `_common/_errors` 之外的私有实现。
- 该问题不单独排期，跟随 CORE-MOD-P1-01 / P2-01 一起处理。

### CORE-MOD-P3-01：`core/tools/*` 测试与生产代码混放

#### 3.1 现状

- `core/tools/filesystem`、`memory`、`reminder`、`runtime_config`、`self_state`、`time`、`web` 下存在 `test_*.py`（8 个文件）。
- `core/tools/web/mock_plugin.py` 位于生产目录，虽然未注册进 `ALL_PLUGINS`，但按目录语义会被当作生产插件。
- 其余 `core/` 包测试统一放在 `tests/` 子目录，风格不一致。

#### 3.2 建议方案

- 将插件测试统一迁到各插件 `tests/` 或全部收敛到 `core/tools/tests/`。
- `mock_plugin.py` 移到 `core/tools/tests/` 或 `core/tools/web/tests/`。
- 保持 `make test-tools`（`pytest core/tools/ -v`）可继续发现全部插件测试。

## 4. 建议处理顺序

1. **CORE-MOD-P1-03**：只改 `EventPriority` 来源，预计半天内可闭环，先消除一个环并建立“依赖图可验证”的基线。
2. **CORE-MOD-P1-01**：独立一个批次，包含模块搬迁 + `run_server` 装配下移 + 回归；不建议与功能需求混做。
3. **CORE-MOD-P1-02**：紧随其后做 PromptAssembler/MessageBuilder 搬迁与记忆域接口收窄。
4. **CORE-MOD-P1-04**：按文件逐项拆，每个文件一个提交，先 `loop.py`/`ws_handler.py`，再 upload/gc/debug。
5. **P2/P3**：跟随上述批次顺手收敛；文档更新放在结构稳定之后。

每个批次的共同 DoD：

- `ruff check core/` 通过；
- `conda run -n Elysia pyright` 0 errors；
- `conda run -n Elysia python -m pytest -m "unit or service" core/` 全绿；
- AST 依赖图复测，确认目标环消失；
- 更新对应 README 与本文档状态。
