## 3. Root Cause

### 3.1 主缺陷 —— "正常返回"的出口逃出了异常兜底

```
_plan_with_retry 两次尝试均失败
  → task_state.fail("规划失败（2 次尝试均未产出可用 Plan）: …", PLANNING_FAILED)
  → return None                                    ← 只写内存，**不 push**
plan_and_validate:  if plan is None: return None   ← 无 push（修复点）
SubAgent.run:       if graph is None: return       ← **正常返回，不抛异常**
_run_and_cleanup:   except Exception 不触发         ← 它只兜"抛异常"
                    finally → _cleanup_task()      ← 注册表摘除，mailbox 只剩 QUEUED
```

三段各自都"没错"，合起来漏掉了终态：

1. `_plan_with_retry` 的职责被理解为"判定失败并记录原因"——它确实写了
   `task_state.fail(...)`，所以看起来"终态已经产生了"；
2. `plan_and_validate` 的另外两条失败出口（校验 ABORT、fix_plan 耗尽）**都**
   push 了 FAILED，所以"规划失败会推事件"这个印象并非空穴来风——只是漏了第一条；
3. 引擎侧唯一的兜底是 `except Exception`，语义是"SubAgent 抛异常了"，
   而这条路径的语义是"SubAgent 正常地告诉我规划失败了"。**语义不匹配**。

`SubAgent.run()` 里那句注释 `return  # 校验 ABORT，已在 _plan_and_validate 中处理`
是这个误解的化石：它只对**校验 ABORT** 成立。

### 3.2 归因错误 —— 同一条终态缺失在两条恢复路径上各自被"补一个原因"

| 路径 | 修复前记录的内容 | 真实原因 |
|---|---|---|
| 优雅停机 | `status="interrupted"`，`"任务因服务重启被中断，未产生结果"` | 规划失败（进程没被打断，原因**已经**产生了） |
| 硬杀 replay | `INTERRUPTED_BY_HARD_KILL_TEXT`（"任务因服务进程异常终止被中断，未产生结果"） | 同上 |

两条都不是"缺字段"，而是**缺事件**：`_stop_mailbox` 的 stranded 分支与
`_replay_task_result_wal` 的"只有派发记录"分支，都是在**没有终态可读**时
才回退到通用文案。终态事件一旦产生，两条路径自然读到真实原因——所以不需要扩
schema、不需要加 `phase` 字段（§15 的约束自然满足）。

### 3.3 Challenger 攻出的 4 个反例（根因分别如下）

| 反例 | 根因 |
|---|---|
| **C1** 校验器自身抛异常 | `PlanGraph.from_plan()` 在 node_id 重复时 `raise ValueError`，而它排在 `DUPLICATE_ID` 那条校验**之前**；`plan_and_validate` 的两处 `validate()` 调用**都没有 try** → 冒到引擎级通用兜底。安全网也救不了：它的闸门是"还没有终态**事件**"，而通用兜底**已经**推了一个 FAILED。 |
| **C2** RESUME 派发失败 | 派发失败分支随后就 `_cleanup_task()` 销毁任务，而安全网对 `PAUSED` 提前返回（前提是"保留 mailbox 等 resume"）——那个前提在这条路径上**不成立**。 |
| **C3** fix_plan 耗尽报 internal_error | `_abort_error_code` 的兜底值是 `INTERNAL_ERROR`，而 `MISSING_CONTRACT`（planner 漏写 `output_contract`）不在 `plan_quality_types` 里；且该分支**手搓 data**、绕过规划失败的 push 实现点。 |
| **C4** 跨重启终态被覆写 | `_background_tasks.pop()` 排在 `await _persist_task_result(...)` **之后**，而 `_stop_mailbox` 的 `cancel_and_drain` 恰好能在这个 await 上掐断轮询 ⇒ 条目仍在 ⇒ stranded 分支落库 `interrupted` 覆写真实终态；启动 replay 再把 `interrupted` 当权威、`wal.forget()` **删掉**真正的终态。 |

### 3.4 R2 —— 一处"偶然正确"被当成了机制

`_run_and_cleanup` / `_run_resume` 的 `except CancelledError` 原先**无条件**写
`CANCELLED`。它能"看起来正确"只是因为 `finalize()` 从写 `COMPLETED` 到推事件之间
恰好没有 await（`CheckpointManager.save` 是纯内存）。**那是偶然性质，不是机制**：
一旦 checkpoint 引入真实 I/O，一个已经完成的任务就会被改判成 CANCELLED，而此刻
`_terminal_pushed` 还是 False、唯一性守卫拦不住它。`finalize.py` 的原注释把这个
保护归因于"顺序"，也是错的（已一并更正）。

## 4. New Invariants

本批正式建立（每条都有可执行用例钉住，见 §7）：

- **T1 — Accepted task eventually reaches a terminal state.**
  `submit()`/`resume()` 返回过 mailbox 的任务，必然到达
  `COMPLETED` / `FAILED` / `CANCELLED` 之一，绝不永久停在
  `queued` / `pending` / `planning` / `running`，也不静默消失。
  **机制**：① 每条规划失败出口自己 push（唯一实现点）；②
  `_finalize_unterminated()` 作为**共享终态边界**兜住任何漏推的出口；
  ③ 派发失败分支（包装协程从未创建、finally 够不着）显式调它。
- **T2 — Exactly one logical terminal outcome per task.**
  幂等性由 mailbox 既有的终态唯一性守卫（first-terminal-wins）提供：安全网与
  所有 push 点共用它，所以"补一个终态"结构上不可能变成"第二个终态"。
  另加两道：取消**不得**覆写已落定终态（R2）；停机 stranded 分支不得覆写
  已落库的真实终态（C4）。同一终态的 replay 仍允许（at-least-once 不变）。
- **T3 — Terminal state survives process boundaries.**
  所有终态事件（含本批新增的出口）都经 `push_mailbox_event`
  → 唯一性守卫 → **同步 WAL sink** → 邮箱 → Agent 轮询落 repo。**不新增任何
  fast-path**。落库未完成时 WAL 必留副本（C4 的用例直接断言这一点）。
- **T4 — Failure attribution matches the actual phase.**
  规划期的**任何**失败（重试耗尽 / 解析失败 / 校验器崩溃 / 校验 ABORT /
  fix_plan 耗尽 / fix_plan 异常）→ `planning_failed`（结构不合法时为
  `plan_too_large`），**不得**是 `internal_error` / "任务执行异常" / `timeout`；
  取消是 `cancelled`；停机中断只在**确实没有终态**时才出现。

**不变的东西**（明确不动）：delivery 仍是 **at-least-once**、`TaskResultData`
不扩字段、`WorkflowEvent` 形状不变、前端公共协议不变。

## 8. Remaining Risks

只列**修复后仍成立**的风险。

1. **`accepted → consumed` 窗口**（先于本批存在，**已声明的取舍**）。
   `_handle_task_result` spawn 出宣告回合后立即写 `delivered=True` 且 WAL 已清，
   而回合真正读 `task_result_context` 之前进程若死，用户收不到那条宣告。
   源码自己把 `consumed` 标注为"进程内，不可观测"，at-least-once 的边界刻意画在
   `accepted`。本批不动。
2. **`WAITING_APPROVAL` 不在安全网的常规覆盖内**（**本批刻意划定**）。
   它是可恢复挂起态而非终态；v1 下不可达（`needs_approval()` 恒 False、
   `Evaluator` v1 不产 `ASK_APPROVAL`）。Challenger 尝试强行打开 `needs_approval`
   时观察到的是 **`Orchestrator.run` 活锁**（只有 600s 预算能打破它）——那是
   v2 审批域的独立问题，见 Follow-up。
3. **`error_type` 在终态呈现这一跳被丢弃**（G2）。
   `terminal_payload` 只取 `data['error']` 文本；`TaskResultData` 没有能装机器码的
   字段。**归因没有丢**（文本含"规划失败…"），但下游拿不到结构化阶段。
   按 §15 本批**刻意不扩协议**。
4. **`_build_wake_up_message` 对所有终态一律说"已完成"**（G4/G5）。
   `core/cognitive/loop.py` 的唤醒文案硬编码"已执行完毕 / 请告知用户任务已完成"，
   即便 `is_error=True`、`result` 是"任务执行失败: …"。**先于本批存在**，且对
   **所有失败类型**同等成立；修它要动认知 prompt 模板，超出本批范围。
5. **reminder 结果无任何持久化**（G6）。`core/tools/reminder/plugin.py` 直接
   `bus.post(TaskResultData(...))`，不写 WAL 也不写 repo；`mark_delivered` 无
   upsert，对它是静默 no-op。进程重启即丢（不只是硬杀）。
6. **两处 FAILED push site 的 data 缺 `task_id`**（G7）。`replan.py`、`orchestrator.py`
   各一处只推 `{error, error_type}`。当前无害（消费者用 `mailbox.task_id` /
   注册表 key），但 `WorkflowEvent.data` 无 shape 校验。
7. **`ExecutionPhase` 从未进入结果面**（G8）。本批靠 `error_type` 的枚举语义承担
   阶段归因，未新增字段。
8. **`plan_too_large` 承载了不止"太大"**（R5）。`CYCLE` / `MISSING_DEPENDENCY` 等
   结构问题仍映射到 `PLAN_TOO_LARGE`——仍是**规划期**码（不再是 `internal_error`），
   但语义偏弱。改它需要新枚举值 ⇒ 触契约可达性门禁，留 Follow-up。
9. **若启用审批，`Orchestrator.run` 会活锁**（R7，Challenger 实测）。
   与终态闭环正交的 v2 域问题。
10. **GAP-4（未证实）**：理论上"任务在协程体首次执行前就被取消"可能绕过
    except/finally。Challenger 与主 Agent 均**未能复现**（`_task_futures` 与
    `create_task` 在同一同步块内登记，`stop()` 的首个挂起点已让包装协程启动）。
    作为**未证实的残余窗口**记录。
