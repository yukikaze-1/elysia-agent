### 3.1 真实拓扑

```text
  Electron renderer  http://localhost:5173/
  backend endpoint   http://127.0.0.1:18765
  local CDP          127.0.0.1:9223（仅联调时）
```

Windows PowerShell 的推荐 SSH 隧道：

```powershell
ssh -N -L 18765:127.0.0.1:8765 -R 19223:127.0.0.1:9223 <ubuntu-user>@192.168.1.18
```

- `-L` 让 Windows Electron 的 `127.0.0.1:18765` 指向 Ubuntu backend `8765`。
- `-R` 仅供 Ubuntu 上的自动化通过 `127.0.0.1:19223` 连接 Windows Electron CDP。
- 不要把后端改绑 `0.0.0.0:8765`；不需要向局域网暴露业务端口。
- 不要把固定 CDP 端口写入产品配置或打包启动参数。

### 3.2 Electron 自动化

普通 Chrome/浏览器打开 `http://localhost:5173` 不等价于 Electron 联调。必须覆盖 Electron Main、Preload、Renderer、IPC、safeStorage 和真实 BackendAdapter。

之前的自动化方式是：

1. Windows Electron 在回环 `9223` 开 CDP；
2. SSH 反向转发到 Ubuntu `19223`；
3. Ubuntu 使用 `/home/yomu/elysia-frontend/node_modules/playwright` 的 `chromium.connectOverCDP("http://127.0.0.1:19223")`；
4. 选择 URL 为 `http://localhost:5173/`、标题为 `Cyrene` 的 page。

如果接手模型有浏览器控制 skill，可用它；如果默认 Chrome 扩展只连接普通 Chrome，应改为直接 Playwright CDP，不要误操作错误浏览器。

### 6.1 P0：采集启动失败导致前后端语音状态分裂

旧行为：

```text
voice.record.start(A)
-> 后端进入 RECORDING
-> PcmCapture.start 失败
-> 前端 fire-and-forget voice.discard(A) 并回 idle
-> 旧后端返回 CONTRACT_VALIDATION: 录音中，先 stop 再 discard
-> 前端本地允许 start(B)
-> 旧后端返回 VOICE_SESSION_CONFLICT: 已有活动语音会话
```

这条序列已通过真实协议捕获，不是纯代码推断。旧后端只有收到原 A 的 stop 或连接断开后才恢复。

### 6.2 P1：空/过短录音删除产生迟到伪错误

准确现象：

- 空/过短录音 stop 后，旧后端自动回 IDLE，不发 transcript；
- 前端待发送条显示未识别，点击删除后 UI 实际能正常清掉，并不会卡死；
- 旧后端随后异步发 `VOICE_RECORDING_NOT_FOUND: 无活动录音`；
- `onChatError` 收到 `backendCode=VOICE_RECORDING_NOT_FOUND`，同时 real-backend 映射 `voice.error`。

不要再把此问题描述成“删除按钮卡死”。真实问题是错误噪声、审计污染和 Mock 未覆盖服务端状态机。

### 6.3 P1：STT 等待期错误显示“未识别”

旧前端 stop 后立即进入 `record_pending`，但没有显式等待状态；字幕尚未返回时组件已显示“未识别，请重试”。旧 45 秒 timer 只是再次清空本来就为空的字段，没有可观察状态变化。

## 10. 下一轮必须执行的定向真实复验

### 10.1 R1：采集启动失败后免重连恢复（P0）

目标：证明新后端接受 RECORDING 态 discard，前端不会与后端分裂。

步骤：

1. 在真实 Electron 中让一次普通录音的 `getUserMedia`/capture start 确定性失败；可临时拒绝权限或在 CDP 中临时替换 `getUserMedia` 为 `NotAllowedError`，测试后必须恢复原函数；
2. 确认 UI 显示本地麦克风错误并回 idle；
3. 不 disconnect、不 reconnect；
4. 立即再次启动普通录音并正常 stop；
5. 随后分别启动/停止 realtime、启动/取消 dictation；
6. 监听 `onChatError` / `onChatEvent`、控制台和 UI。

通过标准：

- 没有 `CONTRACT_VALIDATION: 录音中，先 stop 再 discard`；
- 没有 `VOICE_SESSION_CONFLICT`；
- 三种模式均无需重连即可再次启动；
- 后端无残留录音会话，连接保持 connected。

### 10.2 R2：空/过短录音删除与重录（P1）

建议使用确定性静音 MediaStream，避免 SenseVoice 偶发把环境噪声识别为文字。

步骤 A：

1. 普通录音 start 后立即 stop，确保空/过短；
2. stop 后立即观察待发送条；
3. 在 45 秒内点击删除；
4. 立即开始一条新录音。

通过标准：

- 等待期显示“正在识别…”，不提前显示“未识别，请重试”；
- 等待中试听/删除/重录可用，确认发送禁用；
- 删除后无 `VOICE_RECORDING_NOT_FOUND` / `CONTRACT_VALIDATION`；
- 新录音立即可开始，旧录音迟到事件不污染新录音。

步骤 B：

1. 再做一条确定性空录音；
2. 不删除，等待满 45 秒；
3. 观察文案翻转。

通过标准：

- 0~44.999 秒为“正在识别…”；
- 只有 timeout 后才显示“未识别，请重试”；
- 确认发送始终禁用；
- 删除/重录后 timer 清理，迟到字幕不会复活旧录音。

### 10.3 R3：实体麦克风正常主链

用户已同意实体麦克风测试。

1. 设置页运行 3 秒“测试麦克风”，确认录音、试听、无错误；
2. 聊天页录制 4~6 秒清晰短句；
3. 确认出现非空字幕和可用的确认发送按钮；
4. 测试目的若只验证链路，可点击删除，不必把内容发送进聊天；
5. 检查连接仍为 connected。

### 10.4 R4：阶段 4 快速回归

P0/P1 定向项通过后，至少快速检查：

- DeepSeek/SenseVoice/MiniMax Profile 连接测试；
- TTS preview 能播放到 ended；
- AI 回复自动朗读能播放到 ended；
- dictation final 写草稿、上滑 cancel；
- realtime partial/turn/stop；
- 普通录音非空字幕、删除和确认门；
- 设置持久化、断开重连后的语音 idle 清理。
