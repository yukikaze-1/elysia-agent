## 2. Confirmed Findings

每条给出 Finding / Evidence / Impact / Root cause。**🔴 = 本批已修，🔵 = 未修**。

### 🔴 A. `ConfigLoader.load()` 是库级 env 副作用 + 顺序依赖

- **Evidence**：真实脚本实测一次 `load()` 注入 **14 个键**（`DEEPSEEK_API_KEY`、
  `MILVUS_URI`、`MONGODB_URI`、`ALLOW_INSECURE_REMOTE`、`SERVER_AUTH_TOKEN` …）。
  机制：`env_path=None` → `load_dotenv()` → `find_dotenv()` 从
  `Module/config/loader.py` 所在目录**向上走**到仓库根 → 命中 `.env`。
  **顺序依赖实测**（两个 pytest 用例，同一 argv）：冷进程 `_loaded=False` → 键被
  `.env` 复活 → **1 failed**；热进程（先跑过另一条 config 用例）→ **3 passed**。
- **Impact**：库 API 隐式改进程全局状态且关不掉；同一段测试代码在进程内"第一条"与
  "第 N 条"下结果不同（假绿/假红），`pytest -n N` 下每个 worker 的历史还各不相同。
- **Root cause**：库路径调用 `load_dotenv()`，且一次性开关 `EnvManager._loaded` 是
  **类级**跨调用共享状态。

### 🔴 B. 插件类级 `SafetyProfile` 被就地改写（生产缺陷）

- **Evidence**：`ToolPlugin.safety` 是**类属性**（`Module/tool/protocol.py:429`），
  `SafetyProfile` 是可变 dataclass。实测 `WebFetchPlugin().safety is
  WebFetchPlugin.safety` → **True**；`_load_safety_config` 后
  `WebFetchPlugin.safety.max_concurrency` **0 → 3**，且 `object.__new__(cls)` 建出的
  新实例读到 3。一次 `-m "unit or service"` 跑完，**6/8 个 xdist worker** 的类默认值
  被改写（`WriteFilePlugin.read_dirs` null → `[...]`）。
- **Impact**：`read_dirs` 是**会话模板读白名单**（`Module/tool/safety.py::_read_dir_paths`
  + `_expand_session_template`）。类默认被某一份 YAML 放宽 ⇒ **跨会话放宽读范围** ——
  正是该函数上方那条 warning（"读白名单的类默认值必须是会话模板"）要防的情形。
  测试侧同一根因导致**确定性**顺序翻转：`pytest A B` → 1 failed；`pytest B A` → 30 passed。
- **Root cause**：`setattr(instance.safety, key, value)` 落在进程级共享对象上。

### 🔴 C. 测试代码里的 28 处裸 `os.environ` 写（永不还原 + 取值依赖进程历史）

- **Evidence**：其中 **2 处是模块级**（`test_task_ownership.py`、
  `test_user_identity_persistence.py` —— 收集期即执行，后者还为它挂 `# noqa: E402`），
  `test_phase3.py` 21 处散在用例体内。实测同一 `setdefault` 两种结果：

      [cold] after setdefault : value_is_test=True   len=4   prefix='test'
      [warm] after setdefault : value_is_test=False  len=35  prefix='sk-d6c…' ← 开发者真实 key

- **Impact**：测试不控制自己的输入；真实凭据进入测试进程；同类泄漏实测把
  `test_phase2.py` 的 13 个 `.env` 键永久留在环境里。
- **Root cause**：`setdefault` 只在缺失时写 + 根 conftest 引导保证 `.env` 恒在
  ⇒ **"缺失才设"的条件恒假**（这正是 Challenger 判"修法未达成目标"的那一条，已按
  无条件覆盖改正）。

### 🔴 D. `vectordb/tests/conftest.py` 的 session 级 env 泄漏

- **Evidence**（无 `.env` 树、同 commit、同一进程）：

      pytest core/tests/test_clean_db.py                                  -> 2 failed, 39 passed
      pytest Module/database/vectordb/tests/ core/tests/test_clean_db.py  -> 95 passed
      pytest core/tests/test_clean_db.py Module/database/vectordb/tests/  -> 2 failed, 93 passed

- **Impact**：目录级 conftest 做**永不还原的进程级**写入 ⇒ 越界泄漏 + 结果依赖
  `--dist loadfile` 的调度（**偶发红**而非稳定红，故在 CI 中长期存活）。
- **Root cause**：`scope="session"` + 裸 `os.environ.setdefault`；且被泄漏方
  （`test_clean_db`）依赖 ambient env 而非自控前提。

### 🔴 E. `real_env` fixture 缺 `import os` —— **本批引入的 CI 级回归**

- **Evidence**：`core/tests/test_phase1.py:34` / `test_phase2.py:49` 的 `real_env` 用
  `os.environ`，而两个模块**都没有模块级 `import os`**（原文件只有函数内
  `import os as _os`）⇒ 5 条用例 `NameError` ERROR，其中 **2 条在 `make test-normal`
  的集合里**，而 `ci.yml:130-134/185-187` 正是 `cp .env` + `source .env && make test-normal`
  ⇒ **CI 会红**。`make test-quick` **看不到**（integration ⊄ Quick）。
- **Impact**：若不修，本批直接把 CI 变红。
- **Root cause**：进程内新写 fixture 复用了已被删除的函数局部导入。
  **由 Challenger 独立发现**（主 Agent 只自查出 `test_phase2.py` 一处）。

### 🔵 F1. 工作流/任务系统是**第 4 个模型权威**，且握着**已关闭**的 client

- **Evidence**：`AgentInfra.llm_model` = `os.getenv("TASK_SYSTEM_MODEL",
  "deepseek-v4-pro")`，唯一构造点 `_lifecycle_task_system.py:227-237` **不传**
  `llm_model=` ⇒ 恒取默认。主 Agent 用真 `LLMAdapter` 独立复现：
  `captured.closed=False` → `switch_model` → `await drain` → **`captured.closed=True`**，
  调用抛 `APIConnectionError`；`switch_model` 在 `llm_adapter.py:206-209` 后台关旧 backend，
  而 `AgentInfra.llm` 只在 `Agent.start()` 捕获一次、无人重绑。
- **Impact**：热切换模型后，**任何后台任务的 LLM 调用都硬失败**；且第三半
  `supports_thinking` 能力门控**不随 client 走**（门控在
  `Module/llm/openai_compat.py:160`，而工作流直接调 raw client ⇒ 恒发 DeepSeek 专有的
  `thinking`/`reasoning_effort`；`Module/workflow_engine/core/` 该门控 **0 命中**）。
- **Root cause**：模型权威有 4 个且互不同步；raw client 绕过了 provider 归一化层。
- **为什么本批不修**：Challenger 复核后确认"只换 client 不换 `llm_model`"是**平移不是修复**
  （跨 provider 会把 `APIConnectionError` 换成"未知模型"），且需 ≥3 文件 + 新公开 API
  （`WorkflowEngine._infra` 是私有）+ `DelegationPreparer` 另抄一份 client。**与
  `TASK_SYSTEM_MODEL` 取值不可分**，属设计决策 → Batch 2 首项。

### 🔵 F2. `get_runtime_config` 工具把 **YAML 当 runtime** 报给用户

- **Evidence**：`core/tools/runtime_config/plugin.py:80-100` 读 `config.llm.model` /
  `config.{tts,stt}.model|enabled`。切换后实测：工具说
  `deepseek/deepseek-v4-flash`，而其余所有消费者说 `deepseek/deepseek-v4-pro`；
  `set_service('tts', False)` 后它仍报"TTS: 启用"。
- **Impact**：**agent 主动告诉用户错误的自身模型/开关状态**——本批最"用户可见"的一条。
- **Root cause**：`ToolContext.services` 无 runtime 句柄，插件只能抓到 `config`。
- **为什么本批不修**：Challenger 判"成本明确偏高"——模型是**会话相关**的，必须进
  `loop.py` 每轮重绑热路径，不是一处注入。不用"视成本"留白，**明确不修**。

### 🔵 F4. `app.py` 的 5 个 CLI 覆盖在 server 模式**全被丢弃**

- **Evidence**：`app.py:121-125` 写 `config.server.host/port`、`tts.enabled`、
  `stt.enabled`、`agent.character`，`:137-139` 把它们连 `config` 一起传给
  `run_agent_service`；而 `server.py:219-221` **首轮就**
  `ConfigLoader(AppConfig, yaml_path=config_path).load()` 整个覆盖掉。实测
  `--port 9999` → 实际绑 **8765**。
- **Impact**：5 个 flag 静默失效（`--cli` 模式不受影响）。
- **Root cause**：`config_path is not None` 时首轮即重载，丢弃传入的 config。
- **本批尝试并**回退**：主 Agent 实现"首轮复用传入 config"后

  "CLI 覆盖 vs 每轮重载"谁优先，属**设计决策**，不是本批该顺手改的（§20）。
  commit 里留下了指向 F4 的注释。

### 结论：**Keep As-Is（零生产 diff）**

窄修法逐条排除：*wire from an existing config source* —— **不存在**这样的源

后台调用 400 —— 那正是被禁止的"跟随主模型"行为变更本身。*remove the dead env read* ——
会删掉一个可用旋钮，收益只有字面诚实。

**只加测试**（`Module/workflow_contract/tests/test_task_system_model.py`，15 条）：
① 生产代码**恰好一处读、零处写**（守卫活性已用**变异实验**反证：临时加第二个读点 →
FAIL，删除 → 恢复绿）；② 回退值必须是**裸模型名**、`Module/workflow_engine` 生产代码
不得出现 `model="<字面量>"`（AST 守卫，已用合成样本反证命中）。另 3 条是**当前契约
快照**，docstring 写明"若将来采纳'跟随主模型'建议，本用例随之改"。

## 11. Keep As-Is Decisions

**这一节是刻意存在的**——避免"审计 = 必须改代码"。以下均为**行为明确、测试可信、
只是看起来怪**，或**前提根本不成立**：

1. **K1 `providers.yaml` vs `config.yaml` 的分工 —— Keep As-Is；强制合并是错的（§12）。**
   二者是**不同的设置**：`config.yaml` = "哪个模型在用"（部署级）；`providers.yaml` =
   传输层 + 能力位 + 目录（provider 级、随仓发行）。`providers.yaml` **没有 `model` 键**
   （实测）；它的 `models:` 列表只喂 `/api/providers` 下拉框。**该区域真正的缺陷是 F8 的死
   字段，不是两个文件。**
2. **K2 LLM 模型链（runtime / persisted / `prefer_config_model`）—— Keep As-Is。**
   三者协调一致（探针 B、C1–C4）；冷启动永不文件优先（`previous is None`）——由构造不可判定。
3. **K3 "LLM provider" —— Keep As-Is（负结论）**：不存在独立的 provider 设置，
   它就是 model id 的前缀。
4. **K4 会话切换不重放模型热切换 —— Keep As-Is**：有意为之，且已被
   `provider_routes.py:42-48`（把运行期后端作为第一真相源纳入判定）缓解。
5. **K5 STT/TTS enabled 三态 —— Keep As-Is**：单一派生点 + 单一门控写点，所有消费者读
   派生属性（探针 B 核对）。唯一异类是 F2。
6. **K6 `TokenTracker` —— Keep As-Is，且任务书的前提不成立。**
   全仓**没有任何成本估算/价目表**（`grep cost|pricing|usd` 在 `core/monitoring/` +
   `token_repo.py` + `schema/token.py` = **0 命中**，`TokenUsage` 只有 token 计数 + model
   字符串）。它记录的是**当轮实际适配器模型**（`streaming.py:162`），故不可能分歧。
   "它按哪个模型定价？"**没有指称对象**。
7. **K7 `Module/_common/config_test_helpers.py` —— Keep As-Is，前提不成立**：
   它只生成测试类，从不实例化 `AppConfig`。
8. **K8 `stop()`→`start()`（持久化 == config 时）—— Keep As-Is**：
   `_apply_service_state` 提前 return 会把**已关闭**的后端留在适配器里，但
   `Agent.start()` 无条件先 `_llm.reconnect()`（`lifecycle.py:217` → `openai_compat.py:313-333`），
   无活缺陷。
9. **`TASK_SYSTEM_MODEL` —— Keep As-Is**（§5，零生产 diff + 15 条不变式测试）。
10. **provider 配置缓存（`_PROVIDERS` / 4 个 `_BACKENDS`）—— Keep As-Is。**
    生产只**读**（`cfg = _BACKENDS[provider]` + `provider_cfg.get(...)`），
    仓库内**零测试写**（AST + grep）。⚠️ 但 Challenger 指出"无人利用 ⇒ Keep As-Is"
    **不是好理由**：`load_provider_defaults` 返回**浅拷贝**，嵌套 dict 与 `_PROVIDERS`
    共享，且无 reset helper —— 已按"潜在风险"记入 §12 而非以此理由放行。
11. **`EmbeddingFactory._instances` / `model_manifest._MANIFESTS` / `sticker_registry._registry` /
    `preflight._COUNTS` / `idempotency._store` / `personality._SCHEDULED`** —— Keep As-Is：
    各有既有治理机制（逐项证据见 §6.4）。
12. **`Module/tool/tests/conftest.py` 的 `importlib.reload` + `sys.modules` harness** ——
    Keep As-Is：有明确的 pyc mtime 处理与 sys.modules 清理，实测干净。
13. **`prompt budget` 留在 `Module/` 侧** —— Keep As-Is（Batch 1 审计已裁定；放 core 会让
    R1 变红）。
