## 2. BE-STAGEH-01：修复 generation 与 reset-evolution 的并发竞态

### 2.1 真实复现结果

真实 custom instance 在 `stateVersion=20` 时进入 `generation.started`。生成尚未结束时调用：

```http
POST /api/character-instances/{instanceId}/reset-evolution
Content-Type: application/json

{"expectedStateVersion":20}
```

后端没有返回预期的 409，而是成功重置并把状态推进到 21。本轮 generation 随后继续完成，又把同一 instance 推进到 22。也就是说，破坏性 reset 与 generation 收尾对同一人格状态发生了并发写入。

该结果不是缺少测试夹具，而是已经复现的真实后端 FAIL。

### 2.2 当前代码根因

- `core/character/service.py::reset_evolution()` 只检查 `runtime.lock.locked()` 和 reflector/compression locks；
- 同文件已经存在 `_runtime_is_busy()`，它还检查 `runtime._busy`，但 reset 没有复用；
- `CharacterRuntimeRegistry.mark_busy()` 存在，但生产代码没有调用者，当前 `_busy` 不是可靠的 generation lease；
- generation 整个生命周期并不持续持有 `runtime.lock`；
- `core/input/character_routes.py::_character_mutation_guard()` 已用于 update/rollback，但 reset 路由未使用；
- 现有 `test_reset_evolution_rejects_busy_runtime_before_mutation` 只手工持有 `runtime.lock`，没有覆盖真实 generation busy 状态。

### 2.3 必须满足的不变量

1. 同一 instance 的 generation/反思/压缩未完成时，reset 必须立即拒绝并返回 409 `CHARACTER_BUSY`；不得排队后静默执行。
2. busy 生命周期必须覆盖 generation 的后处理：消息终态、mood/state 更新、反思/压缩和最后一次状态持久化完成后才能释放。
3. busy 检查与取得 reset 写权限必须共用一个原子边界，不能先检查再在无保护状态下执行。
4. reset 成功时只进行一次 CAS、只递增一次 `stateVersion`，并保持现有 `resetFields` 精确范围。
5. generation 被取消、异常或客户端断开时，busy lease 必须在 `finally` 中释放，不能永久卡死 instance。
6. 不同 instance 的领域模型仍应允许独立演化；不能把全局锁扩散成未来永久架构，尽管当前 Agent 的生成入口仍是全局串行。

### 2.4 推荐实现

推荐在 `CharacterRuntime`/registry 建立显式 operation lease，而不是继续依赖动态 `setattr(runtime, "_busy", ...)`：

```text
CharacterRuntime
  operation_lock / state_lock
  active_operations 或明确的 busy kind
  begin_generation() / end_generation()
  try_begin_destructive_mutation()
```

可接受的最小落地方式：

1. generation 在解析出 `characterInstanceId` 后，通过 registry/runtime 在同一把短锁下登记 busy；
2. 登记保持到该 turn 的所有状态收尾结束，并由 `finally` 释放；
3. reset 在同一把短锁内检查 busy 并登记 destructive mutation，busy 时抛 `CharacterBusyError`；
4. reset 持有 mutation lease 后再取得 `runtime.lock`、检查 `expectedStateVersion`、构造 candidate、Mongo CAS、更新内存 runtime；
5. route 层可同时让 `_instance_reset_evolution()` 使用 `_character_mutation_guard()`，作为当前单 Agent 的第一道快速拒绝，但不能只修 route——领域 service 仍须独立守住不变量；
6. `reset_evolution()` 至少复用 `_runtime_is_busy()`，不要维护第三份不同的 busy 判定列表。

不要采用以下“修复”：

- 只在测试中手工 acquire `runtime.lock`；
- 让 reset 等待 generation 结束后自动执行；用户提交时看到的 stateVersion 已可能失效；
- 仅检查 Agent FSM，而不校验具体 runtime/instance；
- reset 成功后让 generation 用内存旧快照无 CAS 覆盖新状态；
- 为了避免竞态而跳过 generation 的状态落库。

### 2.5 必补测试

- service test：`runtime` 显式 generation-busy 时 reset 抛 `CharacterBusyError`，persist 未调用，内存和 stateVersion 不变；
- route test：真实 process/generation guard 被占用时返回 409，body 为 `CHARACTER_BUSY`、`retryable=true`；
- gated concurrency test：用两个 `asyncio.Event` 卡住 generation，在 started 后调用 reset，断言 409；释放 generation 后仅 generation 的预期 CAS 生效；
- cancellation test：generation cancel/异常后 lease 释放，随后用当前 stateVersion reset 可以成功；
- race test：两个相同 expectedStateVersion 的 reset 最多一个成功，另一个返回 `CHARACTER_STATE_CONFLICT`；
- regression：update/rollback 的现有 busy、pending revision 和 `follow_latest` 测试继续通过。

### 2.6 复验通过标准

真实 Electron 触发 generation 后，以当前 stateVersion 调 reset：

- HTTP 409；
- `code=CHARACTER_BUSY`；
- `retryable=true`；
- reset 前后 Mongo 与 REST stateVersion 不变；
- generation 完成后状态只按正常生成路径推进；
- 再以最新 stateVersion 重试 reset，才返回 200 并原子递增一次。

## 3. BE-STAGEH-02：让 UserIdentity 成为真正的持久化事实源

### 3.1 真实复现结果

同一服务进程内，`PUT /api/me` 的初始化、更新和 revision CAS 均正常。仅重启后端服务进程、不清数据库后，再次 `GET /api/me`，原先已经初始化并推进的档案回到：

```json
{
  "initialized": false,
  "revision": 1,
  "defaultCharacterId": null
}
```

这会让角色在服务重启后“不再认识我”，属于情感陪伴主路径的数据丢失。

### 3.2 当前代码根因

- `core/profile/profile_store.py::UserIdentityStore` 只有进程内缓存和可选 JSON 文件；
- `core/agent/agent.py` 使用无 `storage_path` 的 `UserIdentityStore()`，因此 `_persist()` 实际不写任何位置；
- `core/input/server.py` 正确复用了 Agent 内同一个 store，但共享的仍是易失内存对象；
- 当前 archive 默认角色回退也通过同步内存 store 做 revision CAS；
- 架构设计已经冻结“Mongo profile 为权威”，当前生产装配尚未兑现。

### 3.3 目标结构

建议新增：

```text
core/storage/user_identity_repo.py
  UserIdentityRepository

core/profile/profile_service.py（或收敛现有 profile_store）
  bootstrap/get/update_if_revision
  持有当前用户的只读缓存，但 Mongo 是权威
```

Repository 至少提供异步接口：

```python
async def connect() -> bool
async def get(user_id: str) -> UserIdentity | None
async def bootstrap_if_absent(identity: UserIdentity) -> UserIdentity
async def update_if_revision(
    user_id: str,
    expected_revision: int,
    updates: dict[str, object],
) -> UserIdentity | None
async def health_check() -> bool
async def close() -> None
```

Mongo collection 推荐为 `user_identity_profiles`，至少建立 `user_id` 唯一索引。字段命名应与其他 repository 一样在 domain camelCase 与 Mongo snake_case 之间显式映射。

### 3.4 持久化与生命周期要求

1. 首次空库启动使用 `config.agent.user_name` 原子 `setOnInsert` 一个 `initialized=false`、revision 1 的 bootstrap profile；并发启动不能创建两个或覆盖 winner。
2. 已有 profile 启动时必须读取 Mongo，不能重新套用 config 默认值。
3. 更新使用 Mongo 原子 CAS：filter 至少包含 `user_id + revision=expectedRevision`；更新字段与 revision/updatedAt 在同一原子操作完成。
4. Mongo 不可用时 fail-closed，不能悄悄创建新的内存身份并让聊天继续使用错误人格上下文。
5. Agent、REST、session binding、Prompt/TurnCharacterContext 和 archive 默认角色回退必须共享同一份权威 profile service/snapshot。
6. `Agent.__init__` 是同步的，不能在构造器里阻塞跑异步 Mongo。应把 connect/bootstrap/load 放入 `Agent.start()` 或已有异步生命周期阶段，并在完成前让 readiness/角色写入 fail-closed。
7. 关闭服务时按 repository 生命周期 close；不能依赖进程退出刷新内存。
8. `PUT /api/me` 当前“省略 nullable 字段即清空/回 bootstrap 默认”的冻结语义保持不变。
9. 归档默认 custom 时，defaultCharacterId 回退和 profile revision 必须走同一个 durable CAS；失败不能只归档角色却向前端谎报档案已更新。若暂时无法跨 collection transaction，必须有可恢复的明确补偿/重试状态，不能静默半成功。
10. 当前开发决策是不迁移旧数据：空库缺 document 时 bootstrap 即可，不要新增扫描旧会话或猜测用户身份的 migration。

### 3.5 测试要求

- repository：唯一 bootstrap、读取、CAS 成功、CAS 冲突、nullable 字段、Mongo 不可用 fail-closed；
- service：初始化只允许 false→true，不能通过 update 改回 false；只读字段不可被输入覆盖；
- lifecycle：构造并启动 Agent A，更新 profile 后关闭；用同一测试 Mongo 构造 Agent B，档案字段和 revision 完全一致；
- prompt：重启后的 TurnCharacterContext 使用持久化 displayName/preferredAddress/pronouns/timezone；
- archive：默认 custom 归档后，持久化 defaultCharacterId 回退，重启后仍一致；
- route：旧 expectedRevision 仍返回 409 `USER_PROFILE_REVISION_CONFLICT` 和 currentRevision。

### 3.6 复验通过标准

在不清 Mongo 的条件下：初始化档案 → 修改至少两次 → 记录 revision → 完整停止并重启后端服务 → 重启 Electron。`GET /api/me`、设置 UI、Prompt 所用用户身份和默认角色均保持一致；revision 不回到 1，新一轮 generation 仍使用原角色 instance，不产生人格副本。

## 4. BE-STAGEH-03：实现无状态 Character Preview

### 4.1 当前状态

路由和 DTO 已存在，但 `core/character/service.py::preview()` 在校验后固定抛 `CharacterPreviewUnavailableError`，真实请求始终得到 503 `CHARACTER_PREVIEW_FAILED`。前端已经正确展示并允许重试，但没有任何成功路径。

### 4.2 冻结 API

请求保持：

```http
POST /api/characters/preview
Content-Type: application/json

{
  "draft": { /* 完整 CharacterDraft */ },
  "userMessage": "用于预览的一条输入"
}
```

成功响应保持：

```json
{
  "ephemeral": true,
  "reply": "示例回复",
  "model": "可选模型标识",
  "usage": {
    "input": 0,
    "output": 0,
    "total": 0
  }
}
```

不得改变请求包装层；普通 create/update 使用顶层 draft，而 preview 必须保留 `{draft,userMessage}`。

### 4.3 推荐分层

给 `CharacterService` 注入窄的无状态推理 port，例如：

```python
class CharacterPreviewPort(Protocol):
    async def generate(
        self,
        *,
        draft: CharacterDraft,
        user_identity: UserIdentity,
        user_message: str,
    ) -> CharacterPreviewResult: ...
```

实现时：

1. 先复用 `CharacterService.validate()`；无效 draft 抛带完整 issues 的 `CharacterValidationError`；
2. 从 draft 构造仅存在于内存的 Definition/Revision 或 runtime profile，复用现有角色 profile compiler；
3. 使用当前持久化 UserIdentity snapshot；
4. 组装 Framework 安全边界与 authored C1/C2/C3/C6/C7，但使用明确的 preview/no-history 模式；
5. 调用当前活动 LLM adapter 的无工具、非流式或内部流式聚合接口；
6. 把 provider 输出归一化为冻结的 `CharacterPreviewResult`；
7. 用量若记录，必须标识 `purpose=character_preview`，不得进入任何 conversation token aggregate。

### 4.4 绝对零副作用边界

一次 preview 无论成功、失败、超时还是客户端 abort，都不得：

- 创建或激活 session；
- 创建 CharacterInstance；
- 写 message/generation archive；
- 读取或写入会话历史、LTM、relationship、角色演化 state；
- 推进 definition revision 或 instance stateVersion；
- 触发 reflector/compression/mood；
- 触发 TTS、audio frame、expression、Live2D directive；
- 调用工具或 Desktop tool；
- 改变 Agent 当前活动会话/角色。

不要通过创建“临时真实会话”再删除来实现 preview；异常中断会留下孤儿副作用。PromptAssembler 如果当前必须接收 SessionMemory，应新增显式 preview 投影/模式，而不是把真实 SessionManager 塞进去。

### 4.5 错误与取消

- draft 无效：400 `CHARACTER_VALIDATION` + `details.issues`；
- provider/运行时暂时不可用：502/503 `CHARACTER_PREVIEW_FAILED`，按原因设置 retryable；
- 上游超时：稳定公开错误，不返回 provider body/Prompt/traceback；
- 客户端 HTTP abort：best-effort cancel 上游任务，且仍满足零副作用；
- 不允许 echo `userMessage` 或返回固定字符串冒充真实预览。

### 4.6 测试与复验

- fake preview adapter 的成功、失败、超时、取消和 usage 映射；
- 无效 draft 不调用 adapter；
- 调用前后分别统计 session/message/generation/instance/state/revision，全部不变；
- event sink 断言没有 audio/expression/directive/state 事件；
- route 使用真实 DTO 返回 `ephemeral is True`；
- 真实联调先成功 preview，再由前端透明代理只注入一次 503，第二次原样转发并成功，以关闭 H-84 的“服务恢复后重试”分支。后端无需为 H-84 暴露生产故障注入端点。

## 5. BE-STAGEH-04：统一保存校验错误契约

### 5.1 真实差异

包含保留 Framework 标签的 structurally-valid draft：

- `/api/characters/validate` 正确返回 200、`valid=false`，issue code 为 `CHARACTER_RESERVED_CONTENT`，path 指向 `/promptProfile/corePersonality`；
- create/update 保存失败时，后端当前把顶层 code 也改为 `CHARACTER_RESERVED_CONTENT`；
- 冻结的保存语义要求顶层统一为 400 `CHARACTER_VALIDATION`，具体原因保留在 `details.issues[]`。

### 5.2 当前代码根因

`core/input/character_routes.py::_character_error_response()` 在收到 `CharacterValidationError` 后，只要任一 issue 是 `CHARACTER_RESERVED_CONTENT`，就把顶层 code 改成了同名 code。

### 5.3 要求

将 `CharacterValidationError` 的 HTTP 映射固定为：

```json
{
  "code": "CHARACTER_VALIDATION",
  "message": "角色内容校验失败",
  "retryable": false,
  "details": {
    "issues": [
      {
        "severity": "error",
        "code": "CHARACTER_RESERVED_CONTENT",
        "path": "/promptProfile/corePersonality",
        "message": "安全公开说明"
      }
    ]
  }
}
```

- 顶层 code 不再根据 issue code 改写；
- 所有 domain validation issue 均保留 JSON Pointer path；
- `/validate` 的无效结果仍是 HTTP 200，不改成异常；
- create/update/rollback 中由内容校验产生的失败均遵循同一信封；
- Pydantic 请求结构错误可以继续使用顶层 `CHARACTER_VALIDATION`，但不得回显原始 body；
- 更新冻结架构设计的错误码说明，明确 `CHARACTER_RESERVED_CONTENT` 是 validation issue code；若保留在顶层错误码表，必须标注它不用于 CharacterValidationError 的保存信封，消除 §11 与错误表的歧义。

### 5.4 必补测试

- `_character_error_response(CharacterValidationError(issues=[reserved]))` 的顶层 code 必为 `CHARACTER_VALIDATION`；
- `details.issues[0].code/path` 完整保留；
- 多个 error/warning issues 不改变顶层 code；
- validate 200 与 save 400 使用相同 issue shape；
- 错误响应不包含 draft 文本、Prompt、绝对路径或 traceback。

## 6. BE-STAGEH-05：提供真实 `pinned` instance 联调夹具

### 6.1 当前状态

领域模型、Mongo 字段和 fake repository 测试已经支持 `revisionPolicy=pinned`；`core/character/tests/test_service_stage_h.py` 也验证了更新 Definition 后 pinned 不动。但产品 API 没有创建 pinned instance 的入口，开发数据库又按决策不保留 legacy migration 数据，因此 Windows 真实联调无法构造 H-44。

### 6.2 推荐方案

不要为了测试给正式前端增加 revision policy UI，也不要开放无鉴权的生产 API。推荐增加一个显式 opt-in 的开发 seed 命令，例如：

```text
scripts/dev/seed_stage_h_pinned.py
```

要求：

- 只有显式 `STAGE_H_FIXTURES=1` 且非生产配置时运行；
- 使用正式 `CharacterRepository`、`CharacterRevisionRepository`、`CharacterInstanceRepository` 和 `SessionRepository`；
- 基于一个本轮新建 custom definition 创建 owned、非 canonical 或明确测试用途的 pinned instance；
- 创建一条持久化 session binding 指向该 instance；
- 幂等：重复执行返回同一测试记录或明确拒绝，不生成无限副本；
- 输出脱敏 JSON，仅含 characterId、instanceId、conversationId、revisionPolicy、revision；
- 提供对应 cleanup，只删除带固定 fixture 标识的新数据；
- 不扫描、不修改、不迁移任何旧会话。

若项目已有受保护 debug fixture 框架，也可接入该框架，但必须默认关闭、受 admin auth 保护且打包生产不注册。

### 6.3 真实验收

1. seed custom revision 1 的 pinned instance/session；
2. 同时保留同角色的 follow_latest instance；
3. 从真实前端或 REST 把 Definition 更新到 revision 2；
4. follow_latest 下一轮使用 revision 2；
5. pinned 下一轮仍使用 revision 1；
6. 两者 generation/message audit tuple 分别正确，stateVersion 没有串写；
7. 清理 fixture 后正式 active catalog 不残留测试角色。

如果产品决定 V1 完全不验收 pinned，应明确修改冻结设计和 Stage H 门槛，把它标为“后续版本范围”，而不是在没有真实证据时标 PASS。

## 7. BE-STAGEH-06：明确单用户范围，不制造假的“第二账号”

### 7.1 代码事实

当前 `AGENT_ACCESS_TOKEN` 只判断请求是否为获准的产品客户端，并不映射用户身份：

- request 上没有稳定的 user principal；
- `UserIdentity.userId` 固定为 `usr_local_default`；
- character create/clone/list 等路径直接使用 `usr_local_default`；
- 部分 get/update/archive 路径按 characterId 读取，没有 current owner 参数；
- 安全文档明确当前是单用户 Demo token，多用户 owner filtering 属后续范围。

因此再配置一个有效 token，并不会得到第二个用户。用第二 token 注入 `ownerUserId=usr_other` 后声称完成 403/404 验收会是假绿。

### 7.2 本阶段推荐决策

Stage H 保持单用户产品范围：

- 把 H-83 的“无权访问其他 owner 数据”标为 `N/A — V1 single-user`；
- 保留未知 character/instance、archived 角色和安全 404/409 的既有真实联调结果；
- 在多角色架构设计、Stage H 交接和安全文档中统一注明：owner 字段是未来多用户隔离预留，当前 access token 不等于 user principal；
- 不增加“第二账号测试 token”夹具；
- 不删除 repository 中已有 owner 字段和查询能力。

### 7.3 如果决定现在支持多用户

这不是夹具任务，而是一项独立架构工作，至少包括：

- access token/session → stable principal/userId 映射；
- request context 全链传播 current user；
- `/api/me` 按 principal 读写；
- character get/list/create/update/archive/clone/revisions/rollback 全部 owner filter；
- instance、session、message、memory、attachment 全部按 owner 校验；
- 防枚举策略统一 403 或 404；
- 两个真实 principal 的正反向集成测试；
- token 轮换、撤销、审计与数据生命周期。

除非产品负责人明确扩大范围，否则不要把这项工作塞进 Stage H 修复提交。

## 8. 共同实现约束

1. **不改冻结 wire 命名。** `characterRevision`、`stateVersion`、`expectedRevision`、`expectedStateVersion`、`statePolicy` 等保持现状。
2. **不引入旧数据迁移。** 当前开发数据库允许从新 schema/空数据继续；本文只新增正常 bootstrap 或显式测试 seed。
3. **不增加 Mock 成功回退。** Mongo/LLM 不可用时使用稳定公开错误，不能返回本地伪造角色、预览或档案。
4. **不记录敏感正文。** 日志不得记录 UserIdentity 自由文本、CharacterDraft Prompt、preview userMessage、provider body、token 或绝对路径。
5. **保持现有通过项。** clone、archive default fallback、follow_latest、rollback、状态流和 generation identity 不得回归。
6. **分批提交。** 推荐每个 BE-STAGEH 任务独立 commit；持久化、并发、preview 不堆在一个提交里。
7. **同步文档。** 实现完成后更新本清单状态、角色架构设计的实现状态、`core/profile/README.md`/`core/character/README.md` 和必要的数据库文档。
8. **契约产物按需更新。** 以上正式 API DTO 已冻结，正常实现不应改变 schemaHash；若确需调整 `frontend_contract`，必须重新生成、执行 drift check，并把 commit/schemaHash 交给前端，不能只改 Python route。

## 11. 最终复验矩阵

| 顺序 | 场景 | 后端成功标准 | 前端复验 |
|---:|---|---|---|
| 1 | generation 中 reset | 409 `CHARACTER_BUSY`，状态不变 | H-81 |
| 2 | generation 后合法 reset | 200，stateVersion 原子 +1，resetFields 正确 | H-81 成功支路 |
| 3 | 档案更新后服务重启 | `/api/me` 字段/revision/default 保持 | H-72 |
| 4 | 保留内容 validate/save | validate 200 invalid；save 400 `CHARACTER_VALIDATION` + issues | H-80 |
| 5 | character preview | 200 `ephemeral=true`，所有持久化计数不变 | H-40 |
| 6 | preview 一次临时失败后恢复 | 503 安全失败，第二次 200；draft/binding 不变 | H-84 |
| 7 | pinned 与 follow_latest 对照 | 更新后分别保持旧 revision/采用新 revision | H-44 |
| 8 | owner 隔离 | 单用户 N/A，或另立多用户完整验收 | H-83 |

只有 P0 两项、preview、保存错误契约以及 pinned 范围/证据全部闭合，且 H-83 有明确书面决策后，才能宣布多角色 Stage H 完成。
