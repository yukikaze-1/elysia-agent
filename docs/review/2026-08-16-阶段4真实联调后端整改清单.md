## 3. BE-S4-RUN-P0-01：`voice.discard` 必须成为可取消且幂等的录音终止原语

### 3.1 真实现象 A：采集启动失败后后端录音会话残留

普通录音当前顺序是：

```text
voice.record.start accepted
-> Renderer PcmCapture.start()
-> getUserMedia / AudioContext / graph 初始化失败
-> 前端发送 voice.discard
```

真实协议复验结果：

1. 后端接受 `voice.record.start`，状态进入 `RECORDING`；
2. 收到同一个 `recordingId` 的 `voice.discard`；
3. 后端返回 `CONTRACT_VALIDATION: 录音中，先 stop 再 discard`；
4. 前端 Main 已按 fire-and-forget 语义清除本地 active voice；
5. 再次发送新 `voice.record.start`，后端返回 `VOICE_SESSION_CONFLICT: 已有活动语音会话`；
6. 只有补发原 recordingId 的 `voice.record.stop` 或断开连接，后端状态才恢复。

这不是测试注入专属问题。任何真实的麦克风权限拒绝、设备拔出、`AudioContext` 不可用或采集图初始化失败，只要发生在后端已接受 start 之后，都会走相同路径。

### 3.2 真实现象 B：空结果后的迟到 discard 产生伪错误

后端当前对以下结果直接 `_reset_recording()` 回 IDLE，且不发 `voice.transcript`：

- 总 PCM `< 640B`；
- STT 返回空串/纯空白；
- STT 关闭、超时或异常（错误帧后重置）。

前端会保留本地待发送录音供试听/删除/重录。用户点击删除时仍会发送 `voice.discard`。真实空录音复验中：

- 前端待发送条显示“未识别，请重试”；
- 点击删除后前端本地 UI 正常清除，并未卡死；
- 后端随后异步返回 `VOICE_RECORDING_NOT_FOUND: 无活动录音`；
- `onChatError` 收到 `backendCode=VOICE_RECORDING_NOT_FOUND`，同时 real-backend 映射出 `voice.error`。

所以这里的准确问题是**无意义错误、日志/审计噪声和竞态契约**，不是“前端删除按钮卡死”。

### 3.3 直接根因

文件：`core/input/voice_sessions.py`

- `start_recording()` 将 `_mode` / `_rec_state` 置为 `RECORDING`；
- `discard_recording()` 在 `_rec_state == RECORDING` 时明确抛 `CONTRACT_VALIDATION`；
- 空/过短/空转写调用 `_reset_recording()` 后清除 `_recording_id`；
- 迟到或重复 discard 因 `_mode != RECORDING` 抛 `VOICE_RECORDING_NOT_FOUND`。

现有规范也冻结了“IDLE discard -> NOT_FOUND”和“RECORDING 必须先 stop”，因此生产代码、测试和协议文档目前彼此一致，但与真实客户端取消需求不一致。必须同步改语义，不能只改一个测试。

### 3.4 冻结后的目标行为

`voice.discard{recordingId}` 统一定义为“不转写、不提交、不生成用户消息的取消操作”：

| 后端当前状态 | recordingId | 目标行为 |
|---|---|---|
| `RECORDING/RECORDING` | 匹配当前录音 | 立即清 PCM 并回 IDLE；成功，不要求先 stop |
| `RECORDING/TRANSCRIBING` | 匹配当前录音 | 取消在途 STT、清状态并回 IDLE；成功 |
| `RECORDING/PENDING` | 匹配当前录音 | 丢弃字幕/情绪/events 并回 IDLE；成功 |
| `IDLE` | 任意迟到或重复 discard | 幂等成功，不发 `VOICE_RECORDING_NOT_FOUND` |
| 当前存在另一条普通录音 | recordingId 不匹配 | 拒绝，且绝不能取消当前录音 |
| 当前是 realtime/dictation | 任意 recordingId | 保持当前会话不变并返回明确错误；不得误清其它模式 |

补充约束：

1. discard 成功后不得调用 STT、不得发 `voice.transcript`、不得触发 generation；
2. 在途 `_in_flight_stt` 必须取消并正确收尾，迟到 task 不得复活 PENDING；
3. 重复/迟到 discard 是幂等成功，不需要新增成功 ACK；保持当前 send-only wire 形状；
4. 错误 recordingId 不能借幂等语义取消一条仍然活跃的其它录音；
5. 连接关闭的既有清理仍保留；
6. 不通过让前端先 `stop` 来规避：`stop` 的语义是“请求转写”，不应作为采集启动失败的取消替身。
