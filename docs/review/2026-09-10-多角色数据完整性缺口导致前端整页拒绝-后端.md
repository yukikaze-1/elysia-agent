# 多角色数据完整性缺口导致前端整页拒绝（2026-09-10）

**记录日期：** 2026-09-10

**文档状态：** 生效中

**发现来源：** 前端侧真实联调（Electron 客户端连 `192.168.1.18:8765` 后端，`character_profiles=true`）。用户报告「已连接后端但无法新建会话」。

**适用版本：** 后端 `200d4b52`（`main`），`frontend_contract` 与本仓一致（WS v2 33/33、REST 16/16 通过）。

---

## 1. 结论

`character_profiles=true` 时，前端对**会话列表**与**消息历史**实行**整页/整批拒绝**（一条不合格即拒绝全部）。本次两条真实数据缺口各自触发了该拒绝，使多角色功能在数据层面不可用：

| # | 缺口 | 范围 | 用户可见症状 |
|---|---|---|---|
| A | 会话存在但 `character_binding` 为空 | 50 条会话 | 侧栏「暂无会话」+「角色模式的会话响应缺少角色绑定」；**新建会话也失败** |
| B | assistant 消息缺 `character` 快照 | 14 条消息（103 条中） | 聊天区空白 +「消息所属会话或角色身份校验失败，请重试」 |

**两者均已现场修复**（§4），用户确认修复后列表与历史可读。

**共同根因（§5）：** 后端缺少「多角色数据完整性」自检。`character_profiles` 是**全局能力开关**，一旦为 `true`，前端就以「全库每条会话/每条 assistant 消息都必须带角色身份」为前提 fail-closed；但后端没有任何环节检查该前提是否成立——历史数据、测试残留、异常中断产生的记录都会直接抵达前端并触发整页拒绝。**单个坏记录 → 整个功能面不可用。**

## 2. 发现 A：会话 `character_binding` 为空

### 2.1 证据

`GET /api/sessions` 真实响应（Bearer 认证，50 条）：

```
character 字段分布：
  49  key absent            ← 前端视为「缺少角色绑定」
   1  object keys: characterId, characterInstanceId, characterRevision, displayName, presentation
```

`default` 库 `sessions` 集合：

```
total=51  with character_binding=51  WITHOUT=0
```

注意此处**不能只看「字段是否存在」**：51 条文档全部**有** `character_binding` 键，但其中 50 条是**空对象 `{}`**。

```js
// 键集分布 —— 真实判定口径
[1 docs]  keys: character_id,instance_id
[50 docs] keys: (空)
```

### 2.2 那 50 条是什么

全部为**测试残留**，无一为用户真实会话：

| 标题 | 条数 | 特征 |
|---|---|---|
| `lease` / `burst` / `active` | 12 / 12 / 12 | `messageCount=0`，`conv_<hex>` id |
| `test-isolation-<uuid>` | 11 | `messageCount=0` |
| `A` / `B` / `conv_x` | 3 | `title="hello"`，`messageCount=2` |

唯一真实会话为 `default`（`hi~爱莉希雅`，236 条消息，`chr_builtin_elysia`）。

### 2.3 为什么新建会话也失败

会话列表被整页拒绝后，前端 `conversation.items` 为空 → 默认角色选择器无值 → 新建流程的前置校验（`CHARACTER_REQUIRED`）不通过。**新建本身的契约是正确的**（见 §3），失败纯粹是被列表那道门挡在门外。

---

## 3. 对照：新建路径本身是对的

`core/input/session_routes.py` 的 create 分支：

```python
resolved = await request.app["character_session_binding_service"].resolve_for_create(wire.characterId, ...)
summary = await agent.session_manager.create(title=..., character_binding=resolved.binding)
resp = _to_contract_summary(summary, agent.active_session_id, resolved.snapshot)
```

`_to_contract_summary(...)` 会把 `character` 一并写入响应。用户修复后成功新建会话（侧栏出现第二条），**旁证该路径正确**。

## 4. 发现 B：assistant 消息缺 `character` 快照

### 4.1 证据

`GET /api/sessions/default/messages`（第一页 50 条，assistant 18 条）：

```
assistant WITHOUT character: 2      ← 修复前
```

两条问题消息：

| message_id | timestamp | 特征 |
|---|---|---|
| `msg_3dff13ed4553428ca73584eba4` | 2026-09-10T16:01:09Z | **有正文**（含 `<mood>`/`<inner_voice>`），`metadata={}`，`character=null` |
| `msg_f57a4f7f7dc54fe5b596ff975a` | 2026-09-10T15:13:14Z | **空 assistant 消息**（`text=''`），疑似中断的生成残留 |

`message_archive` 全量统计：**14 条** assistant 消息 `character: null`（不止首页那 2 条）。**任何一条进入当前页即导致整页拒绝**，所以只修首页两条不够——下一页会再次触发。

### 4.2 关键对照：`sessions` 内嵌消息是完整的

同一会话在 `sessions` 文档内嵌的 `messages` 数组里，assistant 消息**带完整 `character`**（snake_case）：

```json
"character": {
  "character_id": "chr_builtin_elysia",
  "character_instance_id": "chi_builtin_elysia",
  "character_revision": 1,
  "display_name": "Elysia",
  "presentation": { "avatar_asset_id": null, "live2d_model_id": null, "theme_color": null }
}
```

即**写入路径已具备盖戳能力**（`core/cognitive/finalize.py::_turn_character_snapshot`），缺戳的是 Stage H 之前/异常路径产生的历史记录。

### 4.3 序列化链路（供定位）

```
message_archive doc
  → MessageRepository._doc_to_message()        # core/storage/message_repo.py:80
       └─ validate_message_legacy_compat(doc)  # message_adapter.py —— 不处理 character
  → _archive_to_client(msgs)                    # core/input/_common.py:100
       └─ entry.pop("character") → character_snapshot_to_wire(...)
            └─ 为 None 时**省略** character 键   # ← 前端据此判定「缺角色身份」
```

`character_snapshot_to_wire` 对 `None` 返回 `None`，`_archive_to_client` 随即不写 `character` 键——所以**修复必须落在数据层**（补 doc），仅改序列化层会把「未知归属」伪造成一个具体归属。

## 5. 根因与建议

### 5.1 根因

`character_profiles` 是**全局能力声明**，但配套的数据完整性没有任何门禁：

1. **没有写入期强制**：`sessions.character_binding` / `message_archive.character` 都允许 `{}` / `null` 落库。
2. **没有启动期自检**：服务启动时未扫描「是否存在不满足 `character_profiles` 前提的历史数据」。
3. **没有读出期评估**：`GET /api/sessions` 与 `.../messages` 不区分「本会话确实无角色」（legacy 语义）与「本该有却缺失」（数据缺口），两者都以 `null`/省略键下发。
4. **测试与生产共用数据库**（见 §6），把 1–3 的后果放大成「功能整体不可用」。

前端行为**符合契约**（`docs/02` 与 `frontend_contract` 明示 `character_profiles=true` 后角色身份必填），故本次不建议改前端；否则等于把后端的数据缺口静默吞掉，后续更难定位。

### 5.2 建议（按优先级）

| 优先 | 措施 |
|---|---|
| ★★★ | **测试库隔离**：`pytest` 写 `test_elysia` 或独立 database，禁止写 `default`（详见 §6） |
| ★★★ | **启动期自检**：`character_profiles=true` 时扫描并告警——「有 `character_binding={}` 的会话 N 条」「有 `character=null` 的 assistant 消息 M 条」。**这是把本次故障从「用户报障」提前到「启动日志」的关键一步** |
| ★★☆ | **写入期兜底**：`session_repo.save()` / `MessageRepository` 落库前断言 assistant 消息必备 `character`（profiles 开启时）；缺失则记 `RAW_FRAME_INVALID` 同级告警而非静默落库 |
| ★★☆ | **读出期区分语义**：响应中区分「该会话无角色绑定」（legacy，合法）与「绑定字段存在但为空」（数据缺口）。前者可继续省略，后者应显式报错以便定位 |
| ★☆☆ | 迁移脚本：对存量数据按会话绑定补齐消息角色戳（本次已手工执行，可固化为 `scripts/` 下的幂等迁移） |
| ★☆☆ | **禁止空 assistant 消息落库**：本次 14 条缺失消息中有 1 条为空正文（`msg_f57a4f7f…`，`text=''`），疑似中断/失败的生成仍被归档。空 assistant 消息既无展示价值，又会作为「缺身份」的载体扩大整页拒绝的触发面，建议在 finalize/归档路径过滤 |

|---|---|
| `sessions` 50 条测试会话（`active`/`burst`/`lease`/`test-isolation-*`） | `default.sessions` |
| `character_versions.session_id = "test_default_type"` | `default.character_versions` |

这些不是本次前端故障的直接原因（直接原因是缺角色戳的 14 条消息），但**同类污染会反复制造 §2/§4 的缺口**。

## 7. 现场处置记录

### 7.1 已执行

| 操作 | 范围 | 备份集合 |
|---|---|---|
| 删除无绑定的测试会话 | 50 条 | `default.sessions_deleted_backup_20260910` |
| 补齐 assistant 消息角色戳 | 12 条（另 2 条先前单独处理） | `default.message_archive_backfill_backup_20260910`（12）/ `default.message_archive_backup_20260910`（2） |

补戳所用值（与该会话 `character_binding` 一致，**非伪造**）：

```json
{ "character_id": "chr_builtin_elysia", "character_instance_id": "chi_builtin_elysia",
  "character_revision": 1, "display_name": "Elysia",
  "presentation": { "avatar_asset_id": null, "live2d_model_id": null, "theme_color": null } }
```

选择依据：前端 `acceptArchivedMessage` **只比对 `characterId` + `characterInstanceId`**；`characterRevision` 仅要求为 ≥1 整数（注释明示「archived messages may refer to any immutable content revision」）。该会话自建即绑定 `chi_builtin_elysia`，Stage H 前不存在多角色共会话，故归属唯一且真实。

### 7.2 修复后验证

全量完整性核查（`default` 库）：

```
A. sessions 绑定完整性
   incomplete（character_id / instance_id 缺失）: 0
   悬空引用                                     : 0

B. sessions 内嵌 messages（detail 响应来源）
   assistant 共 2 条 | character 为 null: 0

C. message_archive（分页响应来源）
   总 236 条 | assistant 103 条 | character 为 null: 0
   其余 133 条为 user/tool，本无此要求

接口复验
   GET /api/sessions                  → 2 条，均带 character
   GET /api/sessions/default/messages → 首页 50 条（assistant 18）WITHOUT character: 0
```

用户确认修复后会话列表与历史均正常。

触发路径（后端日志时间线，2026-09-11 02:21–02:22）：

```
02:21:23  WS desktop 客户端已连接 (conn_339732cb2dff)
02:21:23  WS activate_session: 已切到会话 default          ← 恢复列表后自动激活
02:22:05  SessionMemory: loaded session conv_226b8fa82a44 (0 messages)
02:22:05  WS activate_session: 已切到会话 conv_226b8fa82a44  ← 用户新建并切换
```

用户执行**会话切换**时，前端走 `activate()` → `applyPendingReplay()` → `acceptArchivedMessages()`；
`default` 会话的历史消息因缺角色戳被整批拒绝，故报「消息所属会话或角色身份校验失败，请重试」。
该日志时段内后端**无** `session character snapshot 解析失败` 告警（此类告警仅出现在清理前的
03:15–03:30 时段），与「会话绑定本身有效、问题在消息侧」一致。

> **核查方法说明**：悬空引用检测按 `character_instances.instance_id` 比对（内置角色定义在 `characters/` 目录而非 Mongo `characters` 集合，故**不能**用该集合判定内置角色是否有效——初次核查据此误报 `chr_builtin_elysia` 为悬空，已修正）。判据以「接口能正常解析出快照」为准。

### 7.3 回滚

三个备份集合均在 `default` 库内，按 `_id` 或 `message_id` / `session_id` 原样回插即可。备份文档已剥离 `_id` 以避免与现存文档冲突。

## 8. 给前端的说明（跨仓信息同步）

前端此处的严格行为**不是缺陷**，但存在值得双方知晓的脆弱性：

- `conversation.store.parseConversation` / `parseConversationPage`：一条会话缺绑定 → **拒绝整页**（不半写入）
- `message.store.acceptArchivedMessages`：一条 assistant 消息缺身份 → **拒绝整批**（注释明示「Partially accepting it would advance a cursor while silently losing one history item」）

设计理由成立（避免游标推进但静默丢历史）。但**运维后果**是：单条脏数据可让整个会话面板或聊天区不可用，且用户看到的是一句协议错误而非「数据缺失」。若后端短期无法保证数据完整性，可考虑在前端增加**显式的数据缺口提示**（区分「协议违约」与「历史数据待迁移」），但这属于体验优化，不应改变 fail-closed 判定。
