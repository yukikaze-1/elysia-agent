## 1. 结论

当前后端不是“缺少模块化”的状态。2026-08-16 的
[`core/ 模块化与组织健康评估`](2026-08-16-core模块化健康评估.md)
已经关闭 9 项主要问题：运行时包级反向依赖、输入层职责混杂、复杂度枢纽、测试布局和文档漂移均已集中治理。当前代码仍保持以下健康基础：

- `Module/`、`core/`、`frontend_contract/` 的顶层职责可辨认；
- `core/agent` 已按生命周期领域拆为 mixin，`Agent` 作为组合根是合理的；
- `core/cognitive` 已把 streaming/tool/finalize 阶段拆开；
- `core/input` 的 REST 路由已按 provider、TTS、上传、工具、聊天、附件、会话拆分；
- `Module/workflow_engine` 已有独立契约层 `Module/workflow_contract`，内部模块化充分；
- 本轮未发现需要通过“全仓搬目录”解决的新架构失控迹象。

下一轮真正值得治理的不是继续按文件行数拆分，而是以下三类增量问题：

1. **概念边界不清：** `core/task` 实际只是即时工具调用 Worker Pool，却占用了通用“Task”语义，并保留大量没有生产消费者的早期预留能力；
2. **应用边界偏薄：** HTTP/WS 传输层仍会直接触达 Repository、Agent 组件图以及 `ToolAdapter._manager` 私有实现；
3. **边界纪律缺少自动门禁：** 当前边界主要靠文档和人工 review 维持，仍有跨包私有导入、路由间私有调用等小型泄漏。

因此推荐的总方向是：

```text
当前：
HTTP / WebSocket
      ├── Agent（组合根 + 大量直通 property）
      ├── Repository
      └── ToolAdapter._manager（私有实现）

目标：
app.py / Agent（只负责装配）
              │ 注入
HTTP / WebSocket
              ↓
Application Use Cases（窄用例边界）
              ↓
Cognitive / Session / Tool / Attachment
              ↓
Adapter / Storage / Module
```

这是一轮“收窄边界”的治理，不是一次架构重写。

### 3.2 不应混为一谈的三类“任务”

| 类型 | 用户是否可见 | 生命周期 | 正确归属 |
|------|--------------|----------|----------|
| 单轮普通工具调用 | 通常只显示工具卡片 | 秒级到分钟级，跟随当前生成，可中断 | 即时工具调用 Dispatcher |
| WorkflowEngine 长流程 | 可后台执行、暂停、恢复、HITL | 跨多个节点和步骤 | `Module/workflow_engine` |
| 产品任务中心条目 | 用户可查询历史、筛选、重试、查看产物 | 持久化产品实体 | 未来 `TaskService`，当前暂缓 |

当前 `core/task` 的命名和预留字段横跨了上述三种语义，但生产用途只覆盖第一种。

## 4. 详细问题

### ARCH-INC-P1-01：`core/task` 应从通用任务系统收窄为即时工具调度

#### 现状证据

- `core/task/scheduler.py::dispatch_tool_calls()` 是生产主路径，由 Agent/CognitiveLoop 用于并行执行当前轮次的工具调用；
- `dispatch_background()` 没有生产调用方；
- `TaskType.BACKGROUND` 只被 `core/task` 自身消费；
- `depends_on`、`children_ids`、`run_in_background`、`progress` 等字段是预留能力，没有形成产品闭环；
- `parent_id` 实际接收 `RequestId`，但现有父任务关联按 `TaskId` 字典查询，代码已明确注释该分支恒不命中；
- checkpoint 只保存可序列化的 pending BACKGROUND，而当前 background 入口接收协程对象；协程又会因不可序列化被主动跳过，因此没有实际生产恢复闭环；
- `core/task` 与 `Module/workflow_engine`、未来 TaskService 同时使用“任务”术语，已经造成设计讨论中的概念冲突。

#### 推荐目标

建议将其定义为“即时工具调用运行时”，参考命名：

```text
core/tool_runtime/
├── call.py         # QueuedToolCall + 状态
├── dispatcher.py   # ToolCallDispatcher：队列、Worker、重试、超时、取消
└── tests/
```

推荐语义调整：

- `TaskScheduler` → `ToolCallDispatcher`；
- `Task` → `QueuedToolCall`；
- `parent_id` → `request_id`，明确只是关联当前生成/请求；
- 保留 priority、Future 绑定、并发 Worker、retry、timeout、cancel；
- 删除或冻结无生产消费者的 BACKGROUND、DAG、任务树、progress、checkpoint；
- DebugInfo 如仍需 pending/running/total，可保留兼容只读指标，不再称为产品任务历史。

#### 非目标

- 不把普通工具调用送入 WorkflowEngine；
- 不创建产品 TaskRecord；
- 不接任务中心 REST/WS API；
- 不改变 `tool.started/tool.completed`、Desktop `tool.request/tool.status` 等现有 wire 契约。

#### 验收标准

- 普通工具调用的并发、顺序、重试、超时和 cancel 传播行为不变；
- 生产代码不再出现含义不明的 BACKGROUND/DAG 预留路径；
- 文档能明确回答“即时工具调用、Workflow、产品任务”的归属；
- Debug 面板不把即时 Worker 队列误导为完整任务中心。

### ARCH-INC-P1-02：在传输层和运行时组件之间补一层窄应用用例边界

#### 现状证据

`core/input` 仍存在以下模式：

- 会话路由直接调用 `agent.message_repo`、`agent.session_repo`、`agent.generation_registry`；
- 附件与上传路由直接调用 `agent.attachment_repo`；
- 工具路由、管理端点和 WS handler 多处访问 `agent.tool_adapter._manager`；
- WS 和 REST 都能触发会话切换、消息提交等相近用例；
- `Agent` 公开了约 39 个直通 property，input 层因此可以逐步演变成对整个组件图的 Service Locator 使用者。

Repository 直连并非一律错误；简单 CRUD 可以保持薄。但以下逻辑已经具有“应用用例”特征：

- 会话删除前的附件引用释放；
- 会话激活与忙状态门禁；
- 历史、搜索、资源扫描、generation 状态组合查询；
- 工具列表、热重载、审批、Desktop 状态组合；
- 附件 URL 签发和有效期规则。

#### 推荐目标

不建立庞大的通用 Service 层，只提取已有第二消费者或复杂业务规则的窄用例：

```text
core/application/
├── sessions.py            # SessionCommands / SessionQueries
├── tools.py               # ToolControlService
├── attachment_signing.py  # 签发/验证/过期规则
└── settings.py            # 模型/STT/TTS 模式切换（出现复用时再迁）
```

首批建议只做：

1. `ToolControlService`：工具列表、reload、pending approvals、submit approval、runtime 状态；
2. `SessionApplicationService`：CRUD/activate，以及资源、搜索、generation 等组合查询；
3. `AttachmentSigningService`：把 `_sign_url` 从 route 文件移出，统一签发与验证规则。

HTTP/WS handler 只负责：

1. 读取和校验协议输入；
2. 调用一个应用用例；
3. 将结果转换为 `frontend_contract`；
4. 映射错误码和 HTTP/WS 响应。

#### 约束

- Service 不接收整个 `Agent` 后再继续做 Service Locator；应注入最小依赖或明确 callable；
- 不为每个 endpoint 创建一个类；按稳定业务能力聚合；
- 不引入全局 DI 容器；仍由 `app.py`/Agent 组合根显式装配；
- 单纯的 Repository CRUD 不必强制包一层无行为代理。

#### 验收标准

- `core/input` 生产代码不再访问 `tool_adapter._manager`；
- Session/Tool 的核心用例能脱离 aiohttp 进行 service 单测；
- REST/WS 共享用例不各自复制业务规则；
- Agent 对外 property 数量不再因新增 endpoint 线性增长。

### ARCH-INC-P1-03：把人工边界纪律固化为自动检查

#### 现状证据

当前总体依赖方向健康，但仍有明确的小型边界泄漏：

- `core/cognitive` 导入 `Module.tool.safety._safe_arg_summary`；
- `core/desktop/bridge.py` 导入 `core.storage.desktop_call_repo._ACTIVE_STATES`；
- vision 插件导入 `core.schema.adapters.message_adapter._resolve_image_source`；
- `attachment_routes.py` 从 `upload_routes.py` 导入 `_sign_url`；
- input/server/debug 多处穿透 `tool_adapter._manager`；
- `Module/database/documentdb/__main__.py` 运行时导入 `core.utils.new_message_id`；
- `Module/bench/bench.py` 作为开发工具依赖 `core`，需要明确豁免或迁位。

这些问题本身优先级不高，但说明边界依赖人工记忆。上一轮已清理的反向依赖也可能随着功能增长重新出现。

#### 推荐检查规则

新增轻量 AST/import 检查，建议至少覆盖：

1. `Module/` 生产模块禁止依赖 `core/`，`__main__`/bench 如保留必须显式 allowlist；
2. `core.agent`、`core.storage`、`core.memory` 等不得反向依赖 `core.input`；
3. 禁止跨包导入下划线私有符号；同一子包内部的 `_common/_utils` 可按 allowlist 处理；
4. 检测新增 eager import SCC；
5. 允许 `TYPE_CHECKING` 类型边，但单独报告概念耦合，不与运行时硬环混为一谈。

不建议把“文件不得超过 600 行”设成硬门禁。文件长度只能作为审查提示，职责和复杂度才是决策依据。

#### 配套 API 收口

- `_safe_arg_summary` → 正式公开的 `summarize_tool_arguments()`；
- `_ACTIVE_STATES` → `is_active_desktop_call_state()` 或公开不可变集合；
- `_resolve_image_source` → 独立 Attachment/Image Source Resolver；
- `_sign_url` → `AttachmentSigningService`；
- ToolAdapter 增加正式的管理门面，禁止下游读取 `_manager`。

### ARCH-INC-P1-04：建立正式数据库迁移机制

#### 现状

- MongoDB 索引主要在各 Repository `connect()` 中 ad-hoc 创建；
- Milvus collection 名称、维度和创建逻辑由 Repository/Backend 硬编码；
- 仓库中没有统一 migrations 目录、schema version 或 migration ledger；
- 旧文档兼容主要依靠读取时 fallback，而不是可审计迁移；
- Milvus 维度或索引参数未来变化时，没有安全 upgrade path；
- 部分清理接口具有破坏性，不能用“启动时自动修复”替代正式迁移。

#### 推荐目标

该问题应单独设计，不与普通模块搬迁一起实施：

- MongoDB 建立 `schema_migrations` 记录集合；
- 迁移函数有稳定 ID、幂等、可重复检查；
- 启动默认只检测兼容性并 fail-fast/warn，不静默执行破坏性升级；
- 提供显式 `--migrate`/独立脚本和 `--dry-run`；
- Milvus 建立 collection manifest，记录维度、metric、index preset 和版本；
- 维度变化采用新 collection + 数据重建/切换，不允许自动 replace 清空；
- 每条迁移有备份要求、回滚/补偿说明和真实数据验证清单。

这是运营安全问题，优先级高于继续美化目录，但风险也高，必须独立 spec。

### ARCH-INC-P2-01：WebSocket handler 按消息领域继续物理拆分

#### 现状

`core/input/ws_handler.py` 约 1155 行。上一轮已把连接建立、消息循环和关闭清理拆成函数，`handle_ws()` 本身复杂度已明显降低；当前问题不再是单个巨型函数，而是一个文件继续聚合：

- connection/replay；
- v1/v2 消息校验与限流；
- text/interrupt；
- model/service/TTS voice；
- tool approval/status；
- record/realtime/dictation/audio cancel 等语音子协议；
- session activation。

多数 `_dispatch_*` 还重复接收 `data, agent, msg, channel, audio_buf, ws, voice_mgr, sent_message_ids, limiter, rate_key` 等参数，说明连接上下文没有形成稳定对象。

#### 推荐目标

```text
core/input/ws/
├── connection.py
├── router.py
├── context.py            # WsRequestContext + handler Protocol
└── handlers/
    ├── chat.py
    ├── session.py
    ├── service.py
    ├── tool.py
    └── voice.py
```

`router.py` 保留统一 TypeAdapter 校验、限流和 handler registry；领域 handler 只消费 `WsRequestContext` 与对应 Pydantic 消息。

#### 约束

- 不改变 v1/v2 分流；
- 不改变 ACK、错误码、重试提示和幂等时序；
- 不把 voice connection state 错误提升为全局单例；
- 不为了降低行数拆出无语义的 `helpers2.py`。

### ARCH-INC-P2-02：物理拆分 WebSocket 契约，保留单一联合装配点

#### 现状

`frontend_contract/ws_message.py` 约 1073 行，集中定义内容 Part、会话回放、generation、通用消息、语音、客户端命令、工具生命周期和两个判别联合。它仍然是正确的契约单一事实源，但物理冲突面已经较大。

#### 推荐目标

```text
frontend_contract/ws/
├── common.py
├── content.py
├── session.py
├── generation.py
├── tool.py
├── voice.py
└── messages.py      # ClientMessage / ServerMessage 唯一联合装配点
```

`frontend_contract/ws_message.py` 可保留兼容 re-export，生成器只从统一装配点收集。拆分必须保证：

- class 名称、字段、Literal、Optional/null 语义不变；
- ClientMessage/ServerMessage 联合顺序和 discriminator 不变；
- TS、JSON Schema、raw TS 和 golden frames 无意外差异；
- 不把内部 `core.schema` 类型引入零依赖 wire 契约层。

### ARCH-INC-P2-03：统一后台协程的所有权、异常观察和退出收尾

#### 现状

生产代码中存在多种后台协程模式：

- Agent 生命周期字段持有的长期任务；
- VoiceSessionManager 持有的 STT/ACK/idle 任务；
- Character/Reflector 的 fire-and-forget；
- session save、adapter close、reminder 等 `ensure_future/create_task`；
- CognitiveLoop 自行维护 after-response task 集合。

其中很多局部实现是正确的，但异常回调、强引用、shutdown cancel、超时 drain 方式不统一。该问题属于运行时资源治理，不属于产品任务中心。

#### 推荐目标

提供一个很小的、按 owner 实例化的 `BackgroundTaskSet`/`TaskOwner`：

- `spawn(coro, name=...)` 保存强引用；
- done callback 统一记录未处理异常；
- `cancel_all()`；
- `drain(timeout=...)`；
- owner stop 后拒绝继续 spawn；
- 不持久化、不出现在任务中心、不经过 WorkflowEngine。

不要建立一个全局万能 Supervisor；Agent、Voice、Personality 等组件分别拥有自己的 TaskSet，生命周期归属才清楚。

### ARCH-INC-P2-04：ToolManager 先补公开门面，内部拆分等待真实变更需求

`Module/tool/manager.py` 约 840 行，目前同时负责：

- plugin load/setup/shutdown；
- execute/execute_stream 与 inflight 跟踪；
- schema/ref 展开；
- runtime/metadata export；
- HITL 控制；
- reload/discover/drain/teardown；
- history/debug/capability 状态。

这些职责最终可以收敛为：

- `ToolRegistry`：插件、别名、schema、metadata；
- `ToolExecutionRuntime`：execute/stream/inflight/cancel/history；
- `ToolPluginLifecycle`：load/reload/setup/teardown；
- `ToolManager`：兼容门面。

但热重载涉及锁窗口、旧实例排空、延迟 teardown 和并发身份复核，当前测试保护较多。立即拆内部类的风险高于收益。推荐顺序是：

1. 先让 ToolAdapter/ToolControlService 提供完整公共接口；
2. 消除外部 `_manager` 穿透；
3. 等下一轮工具生命周期或插件发现机制改动时，再在门面后拆内部组件。

`Module/tool/safety.py` 虽然约 842 行，但职责围绕安全管线、HITL、验证、截断和超时，现阶段不建议仅按行数拆分。

### ARCH-INC-P3-01：低优先级位置与死代码清理

建议独立清理，不和功能/架构主批混做：

- `Module/bench/` 自身已注明未来迁 `tools/bench/`，且是 Module→core 的 dev 例外；
- `Module/database/documentdb/__main__.py` 为生成 ID 依赖 `core.utils`，可改为 Module 内独立 CLI helper；
- `Module/database/graphdb/` 只有 stub，应明确标记 optional/placeholder，或在确认无近期计划后归档；
- `OutputManager.stream()`、LoggerFactory 等长期无消费者代码，应先用引用审计确认，再删除或迁入 legacy；
- 清理完成后同步 `CLAUDE.md`、模块 README 和根架构文档，避免目录说明继续保留已不存在的能力。

## 5. 推荐实施顺序

### 批次 A：边界门禁与公共 API 收口（低风险）

1. 建立 import/architecture 检查；
2. 补齐 ToolAdapter 公共管理接口；
3. 提升/迁移 `_safe_arg_summary`、`_ACTIVE_STATES`、`_resolve_image_source`、`_sign_url`；
4. 消除 input 层对 `tool_adapter._manager` 的访问；
5. 不改变任何 wire 或运行时行为。

### 批次 B：即时工具运行时语义收窄（中风险、高收益）

1. 冻结 `core/task` 真实生产能力；
2. 改名为 tool runtime/dispatcher；
3. 删除无消费者的 background/DAG/progress/checkpoint 预留；
4. 保持 Debug 指标与工具取消语义；
5. 更新架构文档，明确三类任务边界。

### 批次 C：应用用例边界（中风险）

1. `ToolControlService`；
2. `SessionApplicationService`；
3. `AttachmentSigningService`；
4. REST/WS 改走 service；
5. 只在出现第二消费者时再增加 settings/chat 等用例模块。

### 批次 D：WS 与契约物理拆分（中风险）

1. `WsRequestContext` + handler protocol；
2. 按 chat/session/service/tool/voice 拆 handler；
3. 按领域拆 `frontend_contract/ws_message.py`；
4. 统一装配点和旧 import re-export；
5. wire/schema/golden 必须零意外漂移。

### 批次 E：运行时与存储治理（独立风险轨）

1. 按组件 TaskSet；
2. 数据库 migration spec；
3. Mongo migration ledger + dry-run；
4. Milvus collection manifest 和非破坏升级；
5. ToolManager 内部拆分仅在真实需求触发时进行。

## 6. 明确不做

本轮架构治理不应包含：

- 实现或接线产品任务中心；
- 把所有工具调用统一塞入 WorkflowEngine；
- 因 `Agent`/`CognitiveLoop` 文件长而再次机械拆类；
- 继续拆已经高度模块化的 WorkflowEngine；
- 仅因行数拆 `Module/tool/safety.py`；
- 引入全局 DI 容器、通用 Repository 基类或大规模 Protocol 化；
- 让 application service 接收完整 Agent 后继续穿透内部组件；
- 在普通启动流程中自动执行破坏性数据库迁移；
- 在同一提交里同时做目录迁移、协议变更和产品功能开发。
