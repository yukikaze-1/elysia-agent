**日期：** 2026-08-19（Asia/Shanghai）

## 2. 方案定案（D6）

| # | 决策 | 定案 |
|---|---|---|
| D6-01 | **采用方案 B**：wire 双轨，前端领域层单轨统一 | Desktop = `tool.request/tool.status` 执行握手；Backend（含 `submit_task`）= 新增 `tool.started/tool.completed` 展示生命周期；前端 `toolStore` 只存统一 `ToolCallRecord` |
| D6-02 | **新增 `tool.started` / `tool.completed` 两个 Server→Client v2 帧**；v2 不再发 `action{tool_executing/tool_done}`，v1 的 `action` 行为保持不变 | 契约见 §3；后端发射点统一到 `CognitiveToolPhase` |
| D6-03 | **前端权威键 = LLM `tool_call_id`**，跨三来路唯一：`tool.started/completed.callId`、归档 `tool_call_id`、`tool.request.sourceCallId` 同值 | Desktop 桥 `call_*` 只用于 `tool.request/tool.status` 执行协议与幂等，不充当领域主键 |
| D6-04 | **`generation.completed` 不扩展 `tool_calls`**；归档（assistant `tool_calls` + tool 结果消息）是历史/回放的唯一持久权威 | 前端实时 `toolStore` 为易失视图；重连 replay / 翻历史由归档重建 |
| D6-05 | **`finishReason` 现状冻结**：成功路径仍恒 `"stop"`，枚举保留 `tool_calls` 值但不承载语义；前端不得用 `finishReason` 判断本回合是否含工具 | 若未来需要「本轮工具摘要」另开决策，不与阶段 6 捆绑 |
| D6-06 | **Desktop 终态由前端本地状态机裁决**（`requested→awaiting_permission→running→completed/failed/rejected/cancelled/timeout`）；后端 `tool.completed` 按 `sourceCallId` 与服务端归档确认合并，不重复建卡 | 对齐 `docs/04` §4 单向前进状态机 |
| D6-07 | **`tool.request.sourceCallId` 为必填**，由 desktop plugin 从 `ctx.call_id` 透传；`requestId=ctx.trace_id` 一并透传 | 后端保证桥登记文档 `_build_request_frame` 恒带两字段，防前端再猜关联 |
| D6-08 | **Backend Runtime 只展示、绝不回环请求客户端**；`tool.request/tool.status` 只属于 Desktop Runtime | 拒绝方案 C（后端工具走双工） |

## 3. 契约冻结（后端 `frontend_contract/ws_message.py`）

### 3.1 新枚举

```python
class ToolRuntime(StrEnum):
    BACKEND = "backend"
    DESKTOP = "desktop"
    LOCAL_WORKER = "local_worker"
```

`ToolRequestMessage.runtime` 由 `str` 收敛为 `ToolRuntime`（wire 值不变；`runtime` 恒 `desktop` 的既有发送点不破坏）。

### 3.2 `tool.started`（Server→Client，v2）

```text
type: "tool.started"
callId: str            # LLM tool_call_id（归档 tool_call_id 同值，前端权威键）
toolName: str
runtime: ToolRuntime
inputSummary?: str     # 服务端脱敏摘要（P0 用 _safe_arg_summary：key+类型/长度，不传原始 arguments）
generationId?: str
conversationId?: str
```

### 3.3 `tool.completed`（Server→Client，v2）

```text
type: "tool.completed"
callId: str            # LLM tool_call_id（与 started 同值）
toolName: str
runtime: ToolRuntime
success: bool
outputSummary?: str    # 截断后的公开结果摘要（不传完整文件内容；长度上限见 §7 未拍板项）
error?: {code, message}
errorType?: str        # ErrorType 值
durationMs?: float
truncated?: bool
generationId?: str
conversationId?: str
```

### 3.4 `tool.request` 增量

- 新增必填 `sourceCallId: str`（LLM `tc.id`，即 `ctx.call_id`）；
- `requestId` 保持 optional，但 Desktop 桥必须从 `ctx.trace_id` 填充；
- `runtime` 用 §3.1 的 `ToolRuntime` 收敛。

### 3.5 产物与门禁

- 新模型加入 `ServerMessage` 判别联合；
- `make gen-types` 再生成 `frontend/src/types/contract.generated.ts` + `contract.schema.json` + `contract.raw.ts`；
- `make gen-frames`（若 golden frames 覆盖新帧）+ `make check-types` 零 churn；
- `make lint` / `make pyright` 全绿。

## 5. 前端需要更新的点（F-6 任务清单，镜像见前端仓库决策记录）

1. raw wire：`RawFrame` 增 `tool.request/tool.started/tool.completed/action`（`action` 作过渡期「已知忽略」兼容帧）；`RawClientFrame` 增 `tool.status`；raw-schema `.strict()` + manifest schemaHash 同步。
2. FrameMapper：三帧 → 领域事件 `tool.request/tool.started/tool.completed`；`action` 在 real-backend 显式 no-op；`BackendEventSchema` 镜像（缺镜像 preload 会丢帧）。
3. RealBackend：`tool.request` 交 Main 工具服务（Renderer 只收脱敏公开事件）；`tool.status` 仅由 Main 用缓存的 `toolName/toolVersion/runtime/paramHash` 组装发送。
4. Main：静态工具注册表 + 本地风险重算 + 黑名单/沙盒/授权决策 + 四工具执行器 + `POST /api/uploads/desktop/{callId}`（`X-Client-Connection`）+ 审计 + `callId` 幂等/超时/取消/重连。

7. Mock backend：backend 工具两帧夹具 + desktop 工具 `tool.request` 发帧/`tool.status` 收帧模拟。
8. 门禁：typecheck/lint/test/test:integration/build + `check:contract`（WS 计数随新帧增长）。

## 6. 依赖与顺序

- **后端先冻结契约**（B-6-01）并 push；前端 pull 后跑 `check:contract` 才会看到新帧计数——前端 raw/领域批与后端 B-6-02~06 可并行，但契约模型合并必须在前。
- 联调前置：后端运行版本含 `tool.started/completed` 与 `sourceCallId`；前端版本含 Main 工具服务；桌面四工具真机验证仍需 Windows Electron（阶段 6 真实联调轮）。
- 旧后端（只发 `action`）过渡：前端按「已知忽略」吞掉 `action`，不告警；但不因此把 `action` 当工具状态源。
