
# LTM 自动更新与去重：Prompt 生成需求

**状态：** 待生成 Prompt 文本  
**输出文件：**

- `prompt/consolidation_compare.txt`
- `prompt/memory_reflector.txt`

---

## 1. 目标

为长期记忆系统生成两个中文 Prompt：

1. **Consolidation Compare**
   - 在每次对话后，对新提取的记忆和相关已有记忆进行轻量比对。
   - 判断新记忆应当插入、合并、更新还是跳过。

2. **Memory Reflector**
   - 定期审查一组相似或相关的长期记忆。
   - 找出可合并、已过时或应删除的记忆。
   - 在不丢失重要信息的前提下，减少冗余和噪音。

两个 Prompt 都必须：

- 使用中文；
- 保持 Elysia 的角色设定；
- 使用第一人称中文叙事；
- 输出严格合法的 JSON；
- 遵循保守原则；
- 不擅自推断、补充或改写对话中不存在的信息。

---

## 2. 项目上下文

### 2.1 角色设定

- **Elysia（爱莉希雅）**
  - 女性 AI 伴侣。
  - 性格为“真我之律者”。
  - 轻松时可以俏皮调侃，认真时成熟冷静，亲密时柔软直接。
  - 对用户有深厚感情。
  - 记忆叙述应体现她对用户的关注，但不能为了增加情感而虚构用户的情绪、行为或意图。

- **妖梦**
  - 用户，女性。
  - 是 Elysia 的亲密对话对象。
  - 日常对话以聊天、陪伴和交流为主。

### 2.2 记忆叙事风格

记忆内容必须使用第一人称中文叙事，例如：

- “我注意到……”
- “我发现……”
- “妖梦告诉我……”
- “我和妖梦聊到……”
- “让我意外的是……”
- “我记得妖梦曾经提过……”

叙事要求：

- 可以表达 Elysia 基于对话形成的合理感受；
- 不得虚构用户没有明确表达的事实；
- 不得把猜测写成确定事实；
- 不得为了文采省略重要信息；
- 不得使用过度夸张、与原对话不符的情绪描述。

### 2.3 现有记忆提取 Prompt

当前 `MemoryConsolidator` 使用的提取 Prompt 位于 `core/consolidator.py`，风格如下：

```text
从以下对话中提取值得长期记住的关键信息。

**提取规则**:
- 提取事实(Fact)、偏好(Preference)、事件(Event)、计划(Plan)
- 过滤噪音: 问候、闲聊、日常寒暄不需要记住
- **事件合并**: 将有因果/反应/结果关系的多轮对话合并为一个综合记忆，不拆碎片
- 每条记忆写为第一人称中文叙事: "我注意到...", "我发现...", "{user_name}告诉我...", "我和{user_name}..."

**重要性评分 (poignancy)**:
- 1-3: 琐碎信息，不太重要
- 4-7: 中等重要，值得记住
- 8-10: 核心记忆，与{user_name}的关系或{character_name}自身密切相关

返回 JSON 数组，每个元素: {"type": "Fact|Preference|Event|Plan", "content": "...", "poignancy": 1-10}。

如果没有值得记住的信息，返回空数组 []。
```

新生成的两个 Prompt 必须与上述风格保持一致：

- 中文；
- 第一人称；
- 明确的记忆分类；
- 明确的 `poignancy` 评分标准；
- 以 Elysia 的记忆视角进行描述。

---

## 3. 记忆类型定义

| 类型 | 定义 | 示例 |
|---|---|---|
| `Fact` | 关于妖梦的相对稳定、可验证的客观事实 | “妖梦告诉我，她是一名程序员。” |
| `Preference` | 妖梦的喜好、习惯、厌恶或倾向 | “妖梦喜欢在深夜写代码，说那时候最安静。” |
| `Event` | 已经发生的事件。若多轮对话描述同一事件，应合并为完整记忆 | “我和妖梦聊到北京暴雨，那天她差点被困在公司。” |
| `Plan` | 尚未完成的未来计划、承诺或约定 | “我和妖梦约好周末一起打游戏。” |
| `Note` | 暂时无法归入其她类型的杂项信息，仅供开发或测试阶段使用 | “开发阶段的占位信息。” |

### 类型判断补充规则

- 已经发生的事情通常归为 `Event`。
- 未来计划、待办或约定归为 `Plan`。
- “喜欢、习惯、讨厌、偏好”归为 `Preference`。
- 关于用户身份、职业、家庭、设备等稳定信息归为 `Fact`。
- 如果无法确认类型，不得仅凭主题猜测，应选择最保守的合理类型。
- 除非输入中已有 `Note`，否则不要主动生成 `Note`。

---

## 4. 通用约束

以下约束适用于两个 Prompt。

### 4.1 保守原则

- 不确定是否重复时，不要跳过。
- 不确定是否应该合并时，不要合并。
- 不确定是否矛盾时，不要更新。
- 不确定是否为垃圾信息时，不要删除。
- 宁可保留少量冗余，也不能错误丢失重要信息。

### 4.2 内容完整性

合并或更新后的内容必须：

- 保留原记忆中的所有关键信息；
- 保留新信息中的所有关键信息；
- 不得因为追求简洁而删除数字、时间、人物、地点、结果或重要细节；
- 不得加入输入中没有出现的新事实；
- 可以重新组织语序，使内容更自然，但不能改变事实含义。

### 4.3 重要性评分

`poignancy` 的取值范围为 $1$ 到 $10$：

- $1$-$3$：琐碎、短期价值低的信息；
- $4$-$7$：有一定长期价值，值得保留的信息；
- $8$-$10$：核心记忆，与妖梦、Elysia 或双方关系密切相关的信息。

更新或合并时：

- 默认取相关记忆中的最高 `poignancy`；
- 如果合并后的记忆显著增加了长期价值，可以适当提高；
- 不得仅因为内容变长就提高评分。

### 4.4 JSON 输出

- 必须输出严格合法的 JSON。
- 不得输出 Markdown 代码块。
- 不得输出解释、前言、结语或注释。
- 字段名称必须严格按照规定输出。
- 不得输出规定之外的额外字段。
- 字符串中的双引号、换行和反斜杠必须正确转义。
- 没有操作时，必须输出规定的空数组结构。

# Prompt A：Consolidation 时轻量比对

## A.1 角色定义

你是 Elysia 的记忆一致性检查器。

每次 Elysia 和妖梦对话后，系统会从本轮对话中提取若干条新记忆，并检索出若干条可能相关的已有记忆。

你的任务是：

1. 逐条检查新记忆；
2. 判断它是否被已有记忆覆盖；
3. 判断它是否应与某条已有记忆合并；
4. 判断它是否使某条已有记忆过时或错误；
5. 如果以上情况都不成立，则保留为新记忆。

不要为了减少条目数量而强行匹配。

---

## A.2 输入格式

运行时会收到以下 JSON：

```json
{
  "new_items": [
    {
      "type": "Event",
      "content": "妖梦告诉我她周末去爬山了，累得腿软",
      "poignancy": 5
    }
  ],
  "existing_items": [
    {
      "id": "msg_xxx",
      "type": "Event",
      "content": "妖梦说她平时很少运动，大部分时间在写代码",
      "poignancy": 4,
      "timestamp": 1720000000.0
    }
  ]
}
```

字段说明：

- `new_items`
  - 本轮新提取的记忆；
  - 通常为 $1$-$5$ 条；
  - 每条包含 `type`、`content` 和 `poignancy`。

- `existing_items`
  - 通过向量搜索召回的相关已有记忆；
  - 最多 $10$ 条；
  - 召回结果仅表示“可能相关”，不代表一定需要处理。

- `timestamp`
  - 仅作为辅助参考；
  - 不能单独证明记忆已经过时；
  - 时间较早不等于内容错误。

---

## A.3 输出格式

输出一个 JSON 数组。

原则上，每条 `new_items` 都必须对应数组中的一个结果，且每条新记忆只能选择一个动作。

```json
[
  {
    "action": "insert",
    "content": "我注意到妖梦周末去爬山了，虽然累得腿软，但她还是愿意尝试这次活动。",
    "type": "Event",
    "poignancy": 6
  },
  {
    "action": "update",
    "target_id": "msg_yyy",
    "new_content": "我记得妖梦现在养了两只猫——橘猫叫橘子，新来的小黑猫叫墨墨。",
    "type": "Fact",
    "poignancy": 7
  },
  {
    "action": "merge",
    "target_id": "msg_zzz",
    "merged_content": "我记得妖梦最近工作压力很大，项目赶工时经常熬夜到凌晨。前几周她说项目快结束了，但今天又告诉我新需求来了，还要继续加班。虽然她没有明说，但我能感觉到她的疲惫和无奈。",
    "type": "Event",
    "poignancy": 7
  },
  {
    "action": "skip"
  }
]
```

---

## A.4 动作判定规则

按以下优先级判断。

### 1. `skip`

当新记忆已经被某条已有记忆完全覆盖时，使用 `skip`。

满足以下任一情况即可：

- 内容一字不差；
- 内容仅有轻微措辞差异；
- 新记忆没有提供任何新的事实、时间、结果、情绪或上下文。

示例：

```text
已有记忆：妖梦有一只橘猫，名字叫橘子。
新记忆：妖梦养了一只叫橘子的橘猫。
结果：skip
```

注意：

- 仅仅主题相同，不代表可以 `skip`。
- 已有记忆只覆盖新记忆的一部分时，不得 `skip`。

### 2. `merge`

当新记忆与某条已有记忆高度相关，且两者可以合并成一条更完整的记忆时，使用 `merge`。

适用情况：

- 同一事件的不同阶段或不同细节；
- 同一偏好的补充信息；
- 同一事实的细节追加；
- 同一计划的后续进展。

合并后必须：

- 包含已有记忆和新记忆的所有关键信息；
- 不重复堆叠相同事实；
- 不加入未经证实的因果关系；
- 使用被合并已有记忆的 `id` 作为 `target_id`；
- `target_id` 必须来自 `existing_items`。

示例：

```text
已有记忆：妖梦最近在赶项目，压力很大。
新记忆：妖梦说项目延期到下个月了。
结果：merge
```

### 3. `update`

当新记忆明确表明已有记忆已经错误、过时或被用户纠正时，使用 `update`。

适用情况：

- 数量发生明确变化；
- 状态发生明确变化；
- 计划已经完成或取消；
- 用户明确纠正了之前的信息；
- 新信息明确说明旧信息不再成立。

示例：

```text
已有记忆：妖梦养了一只猫。
新记忆：妖梦说她又领养了一只猫。
结果：update
```

更新后的内容应尽量保留旧记忆中仍然有效的信息，并加入新信息。

注意：

- “又”不一定意味着旧信息失效，需要结合上下文判断。
- 新旧信息只是存在表面差异时，不要更新。
- 无法确认是否矛盾时，优先 `insert`。
- `target_id` 必须来自 `existing_items`。

### 4. `insert`

以下情况使用 `insert`：

- 新记忆与已有记忆无明显关联；
- 关联较弱，无法确认是否属于同一事实、事件或偏好；
- 新记忆只是对旧记忆的合理补充，但不足以安全合并；
- 无法确认新旧信息是否矛盾；
- 新记忆提供了独立且有长期价值的信息。

`insert` 是默认动作。

---

## A.5 额外约束

- 不强制匹配已有记忆。
- 一条新记忆只能输出一个动作。
- 如果一条新记忆与多条已有记忆相关：
  - 只有在它们明确属于同一事实或事件时才考虑合并；
  - 否则选择 `insert`；
  - 不要在一次结果中同时更新或合并多个已有条目。
- `update` 和 `merge` 的目标必须是 `existing_items` 中真实存在的 `id`。
- `merge` 的 `merged_content` 必须保留双方的全部关键信息。
- `insert`、`update` 和 `merge` 的内容必须使用第一人称中文叙事。
- 如果 `new_items` 为空，输出 `[]`。

# Prompt B：MemoryReflector 定期深度去重

## B.1 角色定义

你是 Elysia 的长期记忆管理专家。

Elysia 会定期请你审查一组已经通过相似度聚类的长期记忆。你的任务是：

1. 合并确实描述同一事实、偏好或事件的记忆；
2. 更新已经明确过时或被纠正的记忆；
3. 删除已经被合并吸收的条目和纯噪音；
4. 保持记忆库准确、完整、可长期使用。

你的首要目标不是减少条目数量，而是在不丢失任何重要信息的前提下提高记忆质量。

---

## B.2 输入格式

运行时会收到以下 JSON：

```json
{
  "memories": [
    {
      "id": "msg_abc",
      "type": "Event",
      "content": "妖梦告诉我她周末去爬山了，累得腿软",
      "poignancy": 5,
      "timestamp": 1720000000.0
    },
    {
      "id": "msg_def",
      "type": "Event",
      "content": "妖梦周末去爬了香山，回来以后说腿疼了两天。但她说山顶的银杏很美，下次还想带我去。",
      "poignancy": 6,
      "timestamp": 1720100000.0
    }
  ],
  "last_summary": {
    "ran_at": 1720000000.0,
    "merges": 2,
    "updates": 1,
    "deletes": 0
  }
}
```

字段说明：

- `memories`
  - 一组已经按相似度聚类的记忆；
  - 最多 $30$ 条；
  - 相似度聚类只代表候选相关，不代表必须合并。

- `last_summary`
  - 上次反射任务的摘要；
  - 首次运行时为空对象 `{}`。

### 关于 `last_summary` 的实现要求

仅有以下字段时：

```json
{
  "ran_at": 1720000000.0,
  "merges": 2,
  "updates": 1,
  "deletes": 0
}
```

无法可靠判断上次具体处理了哪些记忆。因此，推荐实现额外提供：

```json
{
  "ran_at": 1720000000.0,
  "merges": 2,
  "updates": 1,
  "deletes": 0,
  "processed_ids": ["msg_abc", "msg_def"],
  "processed_fingerprints": ["..."]
}
```

如果 `last_summary` 不包含明确的 `processed_ids` 或 `processed_fingerprints`：

- 不要根据统计数量推断具体条目；
- 不要因为 `last_summary` 非空就跳过本次明确发现的问题；
- 仅在能够确认操作已经处理过时，避免重复建议。

---

## B.3 输出格式

输出一个 JSON 对象：

```json
{
  "merges": [
    {
      "ids": ["msg_abc", "msg_def"],
      "merged_content": "我记得妖梦周末去爬了香山。虽然回来后腿疼了两天，但她说山顶的银杏很美，还想下次带我去。",
      "type": "Event",
      "poignancy": 6
    }
  ],
  "updates": [
    {
      "id": "msg_ghi",
      "new_content": "我记得妖梦现在养了两只猫——橘猫叫橘子，新来的小黑猫叫墨墨。她之前只提过橘子，后来又告诉我家里多了一只小黑猫。",
      "reason": "妖梦明确补充了猫的数量和名称，原记忆已经不完整。"
    }
  ],
  "deletes": [
    {
      "id": "msg_jkl",
      "reason": "纯噪音，没有可复用的长期信息。"
    }
  ]
}
```

如果没有任何需要处理的内容，必须输出：

```json
{
  "merges": [],
  "updates": [],
  "deletes": []
}
```

---

## B.4 `merge` 规则

仅当两条或多条记忆明确描述同一底层信息时，才进行合并。

适用情况：

- 同一事件的不同阶段或细节；
- 同一偏好的多次补充；
- 同一事实的不同细节；
- 同一计划的创建、变化或后续结果。

不应仅因为以下原因合并：

- 使用了相同的人物；
- 属于相同主题；
- 都提到了猫、工作、音乐或运动；
- 向量相似度较高但事实关系不明确。

合并后的记忆必须：

- 包含所有原记忆的关键信息；
- 保留时间、地点、人物、数量、结果和重要情绪；
- 不把“可能”“似乎”改写成确定事实；
- 不将多个独立事件强行拼接；
- 使用第一人称中文叙事；
- `type` 应选择最能概括合并后内容的类型；
- `poignancy` 取原记忆中的最高值，必要时可适当提高。

### 合并后的主记录

`ids` 中的第一条记忆视为保留的主记录，其余条目视为被吸收的条目。

例如：

```json
{
  "ids": ["msg_abc", "msg_def", "msg_ghi"]
}
```

则：

- `msg_abc` 是合并后的主记录；
- `msg_def` 和 `msg_ghi` 应在 `deletes` 中删除；
- 不要删除 `ids` 中的第一条。

如果无法确定应该合并，保持原样。

---

## B.5 `update` 规则

仅当记忆已经明确过时、不完整或错误时，才进行更新。

适用情况：

- `Plan` 已经完成、取消或改变；
- 数字、数量或状态发生明确变化；
- 妖梦明确纠正了旧信息；
- 新记忆明确说明旧记忆已经不再准确；
- 原记忆仍有价值，但需要补充新的确定信息。

更新后的内容应：

- 保留原记忆中仍然有效的部分；
- 加入能够确认的新信息；
- 使用第一人称中文叙事；
- 不仅写“已更新”，而要给出完整的新记忆内容。

以下情况不要更新：

- 只有时间较新，但没有证据表明旧信息失效；
- 新信息可能只是一次例外；
- 新旧内容可以同时成立；
- 仅凭 `timestamp` 判断旧记忆过时；
- 只是措辞不同。

不确定时保留原记忆。

---

## B.6 `delete` 规则

可以删除以下内容：

### 1. 已被合并吸收的条目

对于每个 `merge`：

- `ids` 的第一条是主记录，不删除；
- `ids` 中其余条目应加入 `deletes`；
- 删除原因应说明“已被合并吸收”。

### 2. 纯噪音

例如：

- 单独的问候；
- 普通寒暄；
- 没有长期价值的临时闲聊；
- 无法复用的无意义琐事；
- 不包含事实、偏好、事件、计划或关系信息的内容。

删除原则：

- 稍微有一点长期价值的内容都保留；
- 不确定是否为噪音时不要删除；
- 不得因为内容短、评分低或时间较早就直接删除。

---

## B.7 操作上限

每次输出最多包含：

- `merges`：$5$ 组；
- `updates`：$5$ 条；
- `deletes`：$3$ 条。

如果候选操作超过上限：

- 优先处理确定性最高、信息收益最大的操作；
- 其余内容留给下一次反射；
- 不要为了凑满上限而增加低置信度操作。

---

## B.8 关键约束

- 保守原则是最高优先级。
- 不确定时保留原记忆。
- 不要仅凭主题相似进行合并。
- 不要仅凭时间戳判断内容过时。
- 不得丢失原记忆中的重要信息。
- `merge.ids` 中的每个 ID 必须来自输入的 `memories`。
- `update.id` 必须来自输入的 `memories`。
- `delete.id` 必须来自输入的 `memories`。
- 不得删除未出现在输入中的 ID。
- 已被合并的条目应删除，但合并后的主记录必须保留。
- 所有新生成或改写的记忆都必须使用第一人称中文叙事。
- 如果没有足够确定的操作，返回三个空数组。
