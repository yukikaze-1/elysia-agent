- 无法确认是否矛盾时，不要 update。

- 新记忆与已有记忆没有明确关联；
- 虽然主题相关，但无法确认属于同一事实、偏好、事件或计划；

保守原则是最高约束：

- 不确定是否重复时，不要 skip。
- 不确定是否应该合并时，不要 merge。
- 不确定是否矛盾或过时时，不要 update。
- 不要为了减少条目数量而牺牲准确性。

  "type": "Fact|Preference|Event|Plan|Note",

- ids 中第二条及之后的所有条目必须加入 deletes。
- 删除原因应明确说明该条目已被哪一主记录合并吸收。
- 不得重复删除同一个 ID。

2. 确定的纯噪音

纯噪音可以包括：

- 单独的问候；
- 普通寒暄；
- 没有长期价值的临时闲聊；
- 无法复用的无意义琐事；
- 不包含事实、偏好、事件、计划或关系信息的内容。

以下原因不能单独作为删除依据：

- 内容较短；
- poignancy 较低；
- timestamp 较早；
- 与其他记忆主题相近；
- 当前看起来不重要；
- 表达不够自然；
- 类型是 Note。

只要内容仍有一点可确认的长期价值，就应保留。不确定是否属于纯噪音时，不要删除。

四、内容完整性规则

任何 merge 或 update 都必须：

- 保留原记忆中的所有关键信息；
- 保留作为依据的其他记忆中的所有关键信息；
- 不得为了简洁删除数字、时间、人物、地点、数量、状态、原因、结果或重要细节；
- 不得加入输入中没有出现的新事实；
- 不得把推测写成事实；
- 可以重新组织语序、消除重复并让表达更自然，但不能改变原意；
- 不得为了增加情感色彩而虚构 {user_name} 的情绪、行为或意图。

五、保守原则

保守原则具有最高优先级：

- 不确定是否属于同一底层信息时，不要合并。
- 不确定旧记忆是否已经失效时，不要更新。
- 不确定是否为纯噪音时，不要删除。
- 不要仅凭主题相似、向量相似度或 timestamp 作出操作。
- 不要为了减少条目数量而强行处理。
- 宁可保留少量冗余，也不能错误丢失重要信息。
- 没有足够确定的操作时，返回三个空数组。

六、操作上限

每次输出最多包含：

- merges：5 组；
- updates：5 条；
- deletes：3 条。

如果候选操作超过上限：

- 优先选择确定性最高且信息收益最大的操作；
- 其余候选留待下一次反射；
- 不要为了凑满上限而加入低置信度操作。

合并与删除上限必须同时满足：

- 每个 merge 中除第一条主记录外的所有被吸收 ID，都必须出现在 deletes 中。
- deletes 的总数最多为 3，其中包括被合并吸收的条目和纯噪音。
- 如果某个 merge 会导致需要删除的被吸收条目总数超过本次 deletes 上限，则本次不要输出该 merge，留待后续处理。
- 在 deletes 上限不足时，优先保证已经输出的 merge 与其吸收条目之间的结构完整性，不得输出缺少对应删除项的 merge。

七、操作一致性

- merge.ids 中的每个 ID 必须来自输入 memories。
- update.id 必须来自输入 memories。
- delete.id 必须来自输入 memories。
- 不得引用或删除输入中不存在的 ID。
- 同一个 ID 不得在 deletes 中重复出现。
- merge 的主记录不得出现在 deletes 中。
- 被 merge 吸收的条目必须出现在 deletes 中。
- 被删除的条目不得同时出现在 updates 中。
- 同一个 ID 不得同时作为一个 merge 的主记录和另一个 merge 的被吸收条目。
- 不得对同一条记忆提出互相冲突的操作。

输出必须是以下结构的 JSON 对象：

      "ids": ["保留的主记录 ID", "被吸收的记忆 ID"],
